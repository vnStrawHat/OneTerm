# 07 — External catalog script

> Part of [Terminal auto-completion design](../auto-completion.md). The script that
> turns raw upstream documentation into the common JSON catalogs embedded by the
> `completion` engine crate.

## 1. Purpose

The `external` source ([02](02-data-sources.md) §4) starts as **raw docs**, not
usable catalogs. This script downloads the raw sources and generates the minimal
JSON ([02](02-data-sources.md) §5) as **one file per command**. It produces only the
`external` categories — currently `cmd` and `coreutils` (a `powershell` source may
be added later). The `manual` categories (`windows`, `linux`, `common`) are
**hand-authored**, not generated by this script.

The generated files are committed under `crates/completion/assets/external/<source>/`;
the raw downloads are **not** committed (they land in a git-ignored scratch dir).

The script must provide at least two subcommands: **`download`** and **`generate`**.

## 2. Location, language, and invocation

- **Location:** `scripts/completion-catalog.py` (Python 3, matching the existing
  `scripts/*.py` tooling like `check-english.py` and `verify-dependency-graph.py`).
  A PowerShell wrapper `scripts/completion-catalog.ps1` may be added for Windows
  parity with `build-release.ps1`.
- **Scoped, non-destructive:** obeys AGENTS.md core principle 7 — it only reads/
  writes inside the workspace (`scripts/.cache/completion/` for raw downloads,
  `crates/completion/assets/` for output). It never scans the whole disk.

```bash
# Download raw upstream docs into the git-ignored cache
python scripts/completion-catalog.py download                 # all sources
python scripts/completion-catalog.py download --source cmd
python scripts/completion-catalog.py download --source coreutils

# Parse the cache → generate the committed JSON catalogs
python scripts/completion-catalog.py generate                 # all sources
python scripts/completion-catalog.py generate --source coreutils

# Convenience: download + generate + report a diff summary
python scripts/completion-catalog.py update
```

## 3. Sources and parsing strategy

### 3.1 Windows Commands → `external/cmd/`

- **Raw source:** the `windows-commands` folder of the MicrosoftDocs
  `windowsserverdocs` repository
  (`WindowsServerDocs/administration/windows-commands`), a set of Markdown files,
  one per command (`dir.md`, `date.md`, …).
- **Download:** fetch the folder — either a sparse/shallow `git clone` of the repo
  into the cache, or the GitHub API/tarball for that subtree. A shallow clone is
  simplest and robust to layout changes.
- **Parse (`generate`):** for each `*.md`:
  - Command name = the file stem (`dir.md` → `dir`), validated against the page
    title / H1.
  - Options = flags extracted from the page's **Parameters** table / syntax block.
    Windows command pages list parameters like `/A[[:]attributes]`, `/B`, `/Q`.
    The parser extracts the leading `/X` (and `-X` where present) token, strips the
    argument placeholder, and dedupes. Phase 1 keeps only the flag token, not its
    description.
- **Output:** one file per command under `crates/completion/assets/external/cmd/`
  (`dir.json`, `ipconfig.json`, …). Windows commands the MicrosoftDocs set omits are
  added by hand under `manual/windows/cmd/` (category `windows`) — not by this
  script.

### 3.2 Unix coreutils → `external/coreutils/`

- **Raw source:** the Debian bookworm coreutils manpage index
  (`manpages.debian.org/bookworm/coreutils/index.html`) → the per-utility manpages
  (`ls`, `cp`, `mv`, `cat`, …).
- **Download:** fetch the index, enumerate the coreutils utility pages, and fetch
  each (HTML, or the plain-text manpage where available).
- **Parse (`generate`):** for each utility:
  - Command name = the utility name from the index.
  - Options = flags from the **OPTIONS** section: both short (`-a`) and long
    (`--all`) forms. The parser matches the `-x, --long` option headers, splits on
    comma, strips argument placeholders (`--width=COLS` → `--width`), and dedupes.
- **Output:** one file per utility under
  `crates/completion/assets/external/coreutils/` (`ls.json`, `cp.json`, …).
  Non-coreutils Unix commands (`ifconfig`, `vi`, …) are added by hand under
  `manual/linux/` (category `linux`) — not by this script.

### 3.3 Hand-authored categories (not generated here)

`manual/windows/cmd/` (`windows`), `manual/linux/` (`linux`), and `manual/common/`
(`common`, subcommand-rich tools like `git` — see [10-subcommands.md](10-subcommands.md))
are **hand-authored** and committed directly; the script does not produce them. It
validates them against the schema (§4) as a lint, but never overwrites them.

### 3.4 PowerShell → `external/powershell/` (future)

- `crates/completion/assets/external/powershell/<cmdlet>.json`. **Empty in Phase 1**
  (the cmdlet space is large — see [03](03-shell-detection.md) §4); a generator from
  `Get-Command` metadata is a later phase.

## 4. Output guarantees

The generator produces files that satisfy the schema in
[02](02-data-sources.md) §5:

- Stable ordering (commands sorted by name, options sorted) so regeneration yields
  minimal git diffs.
- `schema` and (for `external`) `generated` (date) fields set. Source + category are
  implied by the output folder — no field to set.
- Deterministic: running `generate` twice on the same cache yields byte-identical
  output.
- Validated against a JSON Schema (checked in as
  `crates/completion/assets/catalog.schema.json`); the script fails if output does
  not validate, so malformed catalogs never get committed.

## 5. How the `completion` crate consumes the output

- A `build.rs` walks `assets/**/*.json` at compile time and generates a static
  index of `include_str!`ed files (source + category derived from the folder):

```rust
// generated by build.rs, e.g. OUT_DIR/catalog_index.rs
pub static CATALOG_FILES: &[(&str /*name*/, &str /*source*/, &str /*category*/, &str /*json*/)] = &[
    ("dir",      "external", "cmd",       include_str!(".../assets/external/cmd/dir.json")),
    ("ls",       "external", "coreutils", include_str!(".../assets/external/coreutils/ls.json")),
    ("ping",     "manual",   "windows",   include_str!(".../assets/manual/windows/cmd/ping.json")),
    ("git",      "manual",   "common",    include_str!(".../assets/manual/common/git.json")),
    // …one entry per file (source + category = its folder path)…
];
```

- The engine builds a `name → json &str` index from `CATALOG_FILES` at startup and
  **lazily parses** each command's node on first reference ([02](02-data-sources.md)
  §5.3). Embedding (not runtime file loading) means the shipped binary needs no
  external asset files — matching how `terminal-view` embeds its
  `assets/highlight/default.json` — while per-file layout keeps startup cost flat
  as the catalog grows.

## 6. Maintenance workflow

1. `python scripts/completion-catalog.py update`.
2. Review the git diff of the generated per-command files (new commands/options,
   removals; added/removed files).
3. `cargo test -p oneterm-completion` (catalog parse + schema validation tests).
4. Commit with a `chore(completion): refresh external catalogs` message.

## 7. Licensing note

The upstream sources carry their own licenses (MicrosoftDocs content and Debian
manpages). Only **command and option name tokens** are extracted — short factual
identifiers, not prose — but the provenance (source URL + fetch date) is recorded
in each JSON's header fields and should be cross-checked against
[`docs/license-analysis.md`](../license-analysis.md) before shipping. If Phase 2
adds descriptions (copyrightable prose), revisit attribution/licensing at that
point.

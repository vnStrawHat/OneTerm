# 05 — UI (overlay)

> Part of [Terminal auto-completion design](../auto-completion.md). The overlay
> list: rendering, cursor-aware positioning, item format, tag badges, and key
> handling. Lives in `crates/terminal-view`.

## 1. Where it lives

The overlay is rendered by `terminal-view` as a floating layer **above the
terminal grid**, inside the same element that draws the terminal (so it tracks the
grid's coordinate space and the cursor). It is not a dock panel and not a separate
OS window.

- **State:** a `CompletionOverlay` struct held by the `TerminalView`/Space, holding
  the current `Vec<Suggestion>`, the selected index, and the anchor cell. A small
  `Entity<T>` per terminal is fine; the heavy data (catalogs, history) lives in the
  engine/global, not here.
- **Rendering:** the list is a `RenderOnce` element re-emitted each frame from the
  current suggestions (stateless view over engine output), consistent with
  [`docs/agents/code-style.md`](../agents/code-style.md) guidance (prefer
  `RenderOnce` for stateless widgets).
- **Theme:** all colors come from `cx.theme()` / `TerminalTheme` — never hardcoded
  (workspace rule). Tag colors are defined as theme-derived values (§5).

## 2. Anchoring to the cursor

The overlay anchors to the **cursor cell** on the input line. OneTerm already
computes cursor pixel bounds (`CursorBounds` in the terminal engine, used for IME
positioning); the overlay reuses that:

- Horizontal: left edge aligns with the **start of the token under the cursor**
  (so the highlighted prefix sits directly under what the user typed), clamped to
  stay within the terminal viewport.
- Vertical: see §3.

## 3. Smart placement (top / bottom)

The list opens where it fits best relative to the cursor row:

1. Compute rows available **below** the cursor (viewport bottom − cursor row) and
   **above** (cursor row − viewport top).
2. Desired height = `min(suggestions.len(), max_visible_items)` rows + border.
3. If it fits **below**, open below (preferred — the natural reading direction and
   it does not cover what the user just typed).
4. Else if it fits **above**, open above (list grows upward; selection still starts
   at the top visually nearest the cursor).
5. Else pick the side with more room and let the list **scroll** internally.

The overlay never covers the cursor's own row. When the terminal is resized or
scrolled, the overlay repositions on the next frame or dismisses if the anchor
scrolls out of view.

## 4. Item format

Each row renders as:

```
<matched-prefix><rest-of-suggestion>      <tag>
└─ highlighted ┘└─ normal weight ─┘  gap   └ badge
```

- The **matched prefix** (`suggestion.match_start .. match_start+match_len`) is
  rendered with a highlight (bold + accent color from the theme). For the `d`
  example, the leading `d` of `dir` is highlighted; `ir` follows in normal weight.
- The **rest** of the suggestion text follows in the normal foreground color.
- A flexible gap pushes the **tag badge** to the right edge of the row, so all
  badges align in a column regardless of suggestion length.
- The selected row has a distinct background (theme selection color) and is the
  accept target.

Worked example — user typed `d` in a `cmd` prompt:

```
┌───────────────────────┐
│ date              C   │
│ dir               C   │
│ del               C   │
│ docker            H   │   ← used this session, ranked by frecency
└───────────────────────┘
```

Worked example — user typed `dir /` (option context):

```
┌───────────────────────┐
│ /A                O   │
│ /B                O   │
│ /Q                O   │
│ /S                O   │
└───────────────────────┘
```

Worked example — user typed `git ` (subcommand context; subcommands use the `C`
tag — a subcommand *is* a command). An optional dim breadcrumb shows the resolved
path so the user sees which level the items belong to:

```
┌───────────────────────┐
│ git ›                 │   ← optional breadcrumb (resolved command path)
│ commit            C   │
│ checkout          C   │
│ remote            C   │
│ status            H   │   ← used this session
└───────────────────────┘
```

Nested example — user typed `git remote add -` (breadcrumb `git › remote › add`)
shows `add`'s options (`-t`, `-f`, `--tags`) with the `O` tag. See
[10-subcommands.md](10-subcommands.md).

## 5. Tag badges and colors

Three tags, each a small rounded badge with its own background color and a
readable foreground:

| Kind | Tag | Suggested semantic color (from theme) |
|---|---|---|
| History | `H` | theme "info"/blue accent |
| Command | `C` | theme "success"/green accent |
| Option | `O` | theme "warning"/amber accent |

- Colors are pulled from the active theme's semantic palette (via
  `cx.theme()` / `TerminalTheme`) so they adapt to light/dark themes and never
  clash. Exact tokens are chosen during implementation; the requirement is only
  that the three tags are visually distinct and theme-driven.
- The badge shows the single uppercase letter (`H`/`C`/`O`). A tooltip can spell
  out the full word (History/Command/Option) — optional, low priority.

## 6. Key handling

While the overlay is visible it intercepts a small set of keys **before** they
reach the PTY; everything else passes through (typing keeps filtering the list):

| Key | Action |
|---|---|
| `Down` / `Ctrl+N` | If a suggestion is selected, move down (clamped); otherwise pass through to the shell |
| `Up` / `Ctrl+P` | If a suggestion is selected, move up (clamped); otherwise pass through to the shell |
| `Enter` | If selected, accept the suggestion and dismiss; otherwise pass through to run the shell command |
| `Tab` | With `accept_tab` enabled: first Tab selects item 0, later Tab accepts it; otherwise pass through to the shell |
| `Esc` | Dismiss the overlay without accepting; `Esc` is swallowed (not sent to shell) so it does not also cancel the shell line |
| Any printable char / `Backspace` | Pass through to the PTY; the overlay recomputes from the new line |
| `PageUp` / `PageDown` | Scroll the visible window (if scrolling) |

Interaction rules:

- **`accept_tab` default:** on. First Tab explicitly engages the list by selecting
  item 0 without applying it; a second Tab applies the current selection. When off,
  Tab is forwarded to the shell and does not select an item.
- **Suggestion casing:** acceptance respects the displayed suggestion. Unix
  requires an exact-case prefix. Cmd/PowerShell accept a case-insensitive prefix
  and correct a case-only mismatch inside the suggestion replacement range before
  appending the remainder (`cd p` + `cd Project` → `cd Project`).
- **Enter with no selection:** Enter is forwarded to the shell to run the command;
  after Tab selects a row, Enter applies it without running the command.
- **Navigation requires selection:** Up/Down and Ctrl+P/Ctrl+N are forwarded to the
  shell while no row is selected. After first Tab, they move the selected row.
- **Mouse:** clicking a row accepts it; hovering selects it. Optional in Phase 1.

## 7. Lifecycle

- **Show:** after each input change, show/refresh when completion is not gated off
  ([06](06-configuration.md) §3) and actionable results remain. Suppress the overlay
  when the sole result already byte-exactly matches its typed replacement range;
  keep multiple results, prefix extensions, and case-correction results visible.
- **Refresh:** on every keystroke that changes the token; recompute and re-anchor.
- **Dismiss:** on `Esc`, on accept, on empty results, on leaving the command-input
  region (OSC 133 `OutputStart`), on entering the alternate screen, on focus loss,
  or on terminal resize that invalidates the anchor.
- **One overlay per terminal:** each Space/terminal owns its own overlay; only the
  focused terminal shows one.

## 8. Accessibility & polish

- Respect the terminal font + size so the list is visually consistent with the
  grid.
- Ensure sufficient contrast for the highlight and badges (theme-driven).
- Keep the list compact (default 8 rows) to avoid dominating the viewport.
- No animation that delays interaction; appearance is immediate.

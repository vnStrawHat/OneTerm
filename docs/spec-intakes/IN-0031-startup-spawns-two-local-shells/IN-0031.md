# Spec Intake: Startup spawns two local shells

ID: IN-0031
Date: 2026-09-14
Type: change_request
Lane: normal

## Source

Owner report (2026-09-14, screenshot `cmd.exe - Application Error: The application was unable to
start correctly (0xc0000142). Click OK to close the application.`): launching
`dist/oneterm-x86_64-pc-windows-msvc/oneterm.exe` (v0.5.2) shows that dialog, and Task Manager
shows **two** `C:\Windows\system32\cmd.exe /K chcp 65001 >nul` processes. Pressing OK closes one
of them. Reported as constant on the 0.5.2 package and intermittent on the latest commit.

Reproduced and measured here on the same package; see Evidence below.

## Requested Outcome

One launch spawns exactly one local shell. Startup builds the persisted center layout before
resetting it, so the saved `terminal` panel spawns a local shell that is discarded milliseconds
later; when that discarded session's `ClosePseudoConsole` lands while its `cmd.exe` is still
initialising, the shell dies with `STATUS_DLL_INIT_FAILED` (0xc0000142) and Windows shows the
error dialog. Nothing about the layout, the right dock, or zoom restoration may change.

## Evidence

Probe: launch the shipped `dist` binary repeatedly, sample new `cmd.exe` / `OpenConsole.exe`
children of the app pid, and enumerate visible dialog windows (`#32770`).

| `docks.json` center | runs | new `cmd.exe` per launch | error dialog |
| --- | --- | --- | --- |
| holds `terminal` (the real user file) | 8 | 1–2, two in 5 runs | 3 runs |
| `children: []` (center emptied by hand) | 4 | **1 in every run** | none |
| file absent (`reset_default_layout` only) | 1 | 1 | none |

Direct observation of one affected launch: `oneterm.exe` pid 13360 owned children `cmd.exe`
11696, `cmd.exe` 12688 and one `OpenConsole.exe` 2692; window enumeration attributed an
invisible window to pid 12688, and the visible `#32770` dialog belonged to `csrss.exe` (pid
1464), which is where Windows raises a client-side start failure. Both `cmd.exe` processes were
still alive seconds later in several runs.

The sampler polls at 20–60 ms, so its counts are a lower bound: a shell that dies between two
samples is missed. This is why the affected column reads 1–2 rather than always 2.

Emptying the persisted center removes the second spawn and the dialog, which locates the extra
spawn in the `load_layout` path rather than anywhere in the PTY transport.

### Why 0.5.2 is constant and `HEAD` is intermittent

The defect is present in both; only the width of the race differs.

| | shipped `dist` 0.5.2 | `HEAD` (`feat/vt-engine`) |
| --- | --- | --- |
| bundled ConPTY pair | 1.23.2512.16003 | 1.24.2607.10001 (`c60545b`, after `v0.5.2`) |
| transport | `alacritty_terminal::tty` | `crates/pty` (`US-0071`), different close ordering |

Neither difference touches the double spawn; both change how long the discarded `cmd.exe` is
vulnerable.

### Not IN-0020

`IN-0020` / `BUG-0053` carry the same error code from a different cause — `build.rs` rewriting
`x64/OpenConsole.exe` in place while a launch raced a rebuild — and that fix holds: the asset
copy is now change-gated and atomic. This intake needs no rebuild running and reproduces from a
packaged binary.

## Project Impact

- Surfaces: every Windows launch that has a saved `docks.json` with a terminal in the center,
  which is every launch after the first. macOS and Linux take the same code path and spawn the
  same wasted shell; only the visible dialog is Windows-specific.
- Contracts: `docs/gui-layout.md` §Persistence already states startup resets the center to one
  terminal tab. The implementation contradicts it — the persisted center is fully built first.
  The contract needs sharpening, not redefinition.
- Users: an error dialog on launch, plus one leaked shell process and one leaked console host
  per launch when the discarded session survives.
- Systems: no schema, no persisted-format, and no external-effect change.

## Architecture and Boundary Questions

- Runtime and owning boundary: `crates/workspace` startup (`OneTermWorkspace::new`,
  `persistence::load_layout`, `layout::reset_center_only`). The panel and session crates are not
  touched by `BUG-0054`; `BUG-0055` sits in `crates/local-shell` / `crates/pty`.
- Data ownership and lifecycle: `docks.json` stays owned by
  `oneterm_state::dock_persistence`. Reading it is unchanged; only what startup does with the
  center subtree changes. Nothing is written differently, so old and new files round-trip as
  they do today.
- Auth, security, privacy, or audit: none.
- External systems and side effects: fewer, not more — one `CreateProcessW` and one
  `CreatePseudoConsole` per launch instead of two.
- Public interfaces and compatibility: `MAIN_DOCK_VERSION` stays `3`; `DockDocument`
  `schema_version` stays `1`. A document written by any earlier build still loads.

## Open Decisions and Questions

- [x] Where to stop the extra build: in `persistence::load_layout` (drop the center subtree
  before handing the state to `DockArea::load`) rather than in `DockArea` or in
  `TerminalPanel`. The dock crate is a dependency, and the panel must keep spawning when it is
  genuinely built. Owner: implementer of `BUG-0054`; not blocking.
- [x] Whether `BUG-0055`'s orphan is a missing kill on the `pty_close` path or the console host
  outliving its client by design. **Neither**: `ClosePseudoConsole` only asks the host to end the
  session, and a `cmd.exe` that has not finished starting never processes that request — it then
  never exits at all (alive at 15 s, against 20 ms for the normal path), and its console host
  stays alive with it because a host exits with its last client. `BUG-0055` adds a bounded wait
  and an escalation (`DEC-0016`); the measurement is in that packet's Context.

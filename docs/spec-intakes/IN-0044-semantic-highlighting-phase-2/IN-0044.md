> (a) `RowRoles` from OSC 133 are never populated, so the §4.2 fast path is dead and every
> line goes through the prompt regex.
> (b) The prompt-line background (§8 item 6, `ClassStyles::prompt_line_bg`) is parsed but
> never painted.
> (c) Drive-anchored output with an unspaced `>` (`C:\src -> C:\dst`, and the MSVC
> diagnostic `x.cpp(5): error C2059: syntax error: '>'`) reads as a prompt.
> (d) There is no highlighter benchmark, and the wrap-run scan bound can equal the
> viewport.
> (e) A wrap run whose head is above the viewport is classified from the first visible row.

(c) is `BUG-0071` gap `N2`, measured there and left as a cosmetic, bounded trade. (d) and
(e) are its "No benchmark harness" and "A logical line whose head has scrolled above the
top of the viewport" gaps. (a) and (b) are the two follow-ups its Handoff says deserve
their own packets.

## Requested Outcome

Phase 2 of `docs/terminal-semantic-highlighting.md` §11: the OSC 133 fast path goes live,
the prompt-line background is painted, the highlighter's cost is measured rather than
argued, and the one remaining Windows false positive is closed.

Concretely, when the shell emits OSC 133:

- every visible row's role is read from the engine instead of guessed by a regex, including
  the continuation rows of a prompt that wraps;
- the prompt sign carries a success or failure tint from the command's exit code;
- the prompt line gets its background, on every row of a wrapped prompt.

When the shell does not emit OSC 133, nothing changes: the prompt regex stays the
fallback, and it stops calling `C:\src -> C:\dst` a prompt.

## Project Impact

- **Surfaces.** The terminal grid only. Colour and one background band inside
  `crates/terminal-view/src/render/`; no panel, menu, dialog or setting gains a control.
  The existing `terminal.semantic_highlighting` setting still gates the whole layer.
- **Contracts.** `docs/terminal-semantic-highlighting.md` is the owning contract. §4.2 and
  §13 Q1 describe `RowRoles` as rebuilt "in the pump ... alongside the grid snapshot" from
  the event stream; the engine `IN-0029` shipped afterwards makes that unnecessary, so the
  clause is restated rather than implemented as written (see the high-level design). §8
  item 6, §10 and §11 gain text.
- **Engine.** None. `oneterm-vt` already carries the OSC 133 region on every cell
  (`crates/vt/src/cell.rs:83`, surfaced as `SnapshotCell::semantic`,
  `crates/vt/src/snapshot/row.rs:52`). No public API change, so
  `scripts/vt-public-api.py` is untouched and the crate's package contract is unaffected.
- **Themes.** `prompt_line_bg` is a colour the terminal paints under text. Today it is one
  fixed value in `crates/terminal-view/assets/highlight/default.json`, theme-independent.
  Making it correct on a light theme is a theme-token question and carries a contrast-gate
  question with it (`scripts/check-theme-contrast.py`); both are settled in the
  high-level design, one of them provisionally (see Open Decisions).
- **Users.** Anyone whose shell emits OSC 133 sees more accurate prompt colouring and a new
  background band. Anyone whose shell does not sees only the `BUG-0073` fix.
- **Performance.** §10's budget is currently an argument from the rescan scope plus one
  ad-hoc debug-build probe. This intake replaces the probe with a committed measurement and
  states the bound honestly.

## Architecture and Boundary Questions

- **Runtime and owning boundary.** All of it is in the render thread, inside the existing
  per-frame plan-cache pass. `crates/highlight` stays pure and gains no row concept it does
  not already have (`RowRoles` is already declared there and inert). The view owns the
  mapping from the snapshot's per-cell region to a per-row role, because the view is what
  knows which rows are on screen.
- **Data ownership and lifecycle.** The OSC 133 region is owned by the engine and stored in
  the cell, so it moves with the content through scroll, scrollback trimming and reflow with
  no bookkeeping on either side. The derived `RowRoles` is frame-scoped view state,
  rebuilt from the snapshot each frame it is needed and never persisted. The exit code is
  the one fact **not** in the cells; where it comes from and what that costs is the
  high-level design's main question.
- **Auth, security, privacy, audit.** None. No new input is trusted, no new process is
  started, nothing is written. The OSC 133 payload is already parsed and bounded by the
  engine (`MARK_MAX`, `crates/vt/src/terminal/mod.rs:62`); this intake only reads a
  two-bit field that is already in the snapshot.
- **External systems and side effects.** None.
- **Public interfaces and compatibility.** No `oneterm-vt` public API change, so the
  package, the public-API snapshot and the semver promise of `IN-0038` are untouched. The
  theme JSON may gain one optional key (`US-0134`); a theme that omits it keeps working,
  which is the same backwards-compatibility rule §7 already states for the whole
  `terminal.semantic` block.

## Open Decisions and Questions

- [ ] **The contrast gate's scope.** `scripts/check-theme-contrast.py` measures kit UI
      tokens read out of `crates/theme/themes/*.json`; the terminal grid's own colours are
      not in `SURFACES` and are not measurable from those files at all, because the semantic
      palette lives in `crates/terminal-view/assets/highlight/default.json`. The
      high-level design proposes deriving `prompt_line_bg` from the theme's own terminal
      background so the band cannot invert a theme, and proving it with a Rust test rather
      than extending the Python gate. Extending `SURFACES` to terminal tokens instead is a
      larger, and separate, change to what that gate is for. **Owner, non-blocking for
      `US-0133`, blocking for `US-0134`'s acceptance wording only.**
- [ ] **How far back the exit-code tint reaches.** The exit code is not stored in a cell, and
      the engine reports it only as an event with no row attached
      (`crates/vt/src/events/vt_event.rs:62`). The cheap answer tints the most recent
      completed command block from the backend's existing `last_exit_code`
      (`crates/terminal/src/backend/state.rs:59`) and leaves older prompts in scrollback
      untinted. The complete answer needs a per-block record, which needs the engine to say
      *where* a block ended. The high-level design recommends the cheap answer with the
      limit written down. **Owner, blocking `US-0133`'s acceptance wording.**
- [ ] **The head-above-viewport rule.** `US-0135` measures before it decides: either scan
      from the run's true head up to a cap, or keep the viewport-only contract and document
      the limit. Not a question anyone can answer without the number. **Settled inside
      `US-0135`.**

# Spec Intake: Terminal printable-output logging

ID: IN-0010
Date: 2026-08-19
Type: new_spec
Lane: high_risk

## Source

User request dated 2026-08-19. Clarifications accepted in-session:

- printable output is recorded as line-oriented messages after ANSI/control sequences are removed;
- carriage return ends the current progress-style message;
- saved SSH sessions use `Use global`, `On`, or `Off` logging behavior;
- Overwrite truncates a colliding file once when logging starts, then writes subsequent records to that open file.

## Requested Outcome

Users can automatically or manually log printable local-shell and SSH terminal output to timestamped files, with persisted global settings, a saved SSH-session override, state-aware controls, and visible recording indicators.

## Project Impact

- Terminal output path: `oneterm-terminal` shared pump and the local/SSH backends.
- Persisted settings: `terminal.json` and `ssh_session.json`.
- UI: General Settings Terminal page, SSH session editor, terminal context menu, tab title, and split-Space overlays.
- Privacy/data: terminal output may contain secrets and is written unencrypted to a user-selected folder; failures must be visible and must not stop terminal rendering.

## Architecture and Boundary Questions

- Runtime and owning boundary: capture occurs once in the shared terminal pump so local and SSH cannot drift and UI repaint coalescing cannot lose messages.
- Data ownership and lifecycle: `terminal.json` owns global logging defaults; `ssh_session.json` owns the saved-session tri-state; each terminal owns one runtime logger and open file.
- Auth, security, privacy, or audit: logs are plaintext user-owned files and can contain sensitive terminal output. No input, OSC payload, password, or authentication secret is intentionally logged.
- External systems and side effects: folder creation and file open/write/flush are fallible filesystem effects; failures are reported to the terminal UI without ending the session.
- Public interfaces and compatibility: `TerminalSession` exposes logging state/control through a capability object; `SessionFactory` receives backend-neutral logging startup configuration.

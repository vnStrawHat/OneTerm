# Spec Intake: Windows self-update rolls back after launch and fails to relaunch

ID: IN-0012
Date: 2026-08-20
Type: maintenance
Lane: normal

## Source

User field report: OneTerm 0.4.0 on Windows cannot update to 0.4.1. Choosing
"Install Update" quits the app, but it never relaunches, and reopening still
shows 0.4.0. The user later found the trigger: a stale `OpenConsole.exe`
(the ConPTY console host) kept running after OneTerm quit; killing it by hand
made the 0.4.0 update succeed.

## Requested Outcome

On Windows, an in-app update from 0.4.x reliably replaces the installed
binaries and relaunches OneTerm on the new version. When it cannot, it leaves a
readable record explaining why, instead of silently reverting to the old build.

## Project Impact

- Affected surface: the auto-update subsystem (`crates/update`), specifically
  the Windows install path in `crates/update/src/install.rs`
  (`schedule_windows_update` and the generated helper `.cmd`).
- Affected users: all Windows users updating in place. macOS/Linux paths are
  untouched.
- Existing behavior: `InstallOutcome::RestartScheduled` → `cx.quit()` → detached
  helper replaces files and relaunches. The helper's file replacement was
  failing and rolling back.
- No change to the check/download/stage flow, the release format, or any
  cross-platform contract.

## Candidate Work Packets

- [x] `BUG-0012` — Windows self-update completes and relaunches: terminate the
  stale `OpenConsole.exe` holding file locks (root cause) and harden the helper
  script (`/R` for read-only files, reset errorlevel before `start`).
- [x] `US-0024` — Write a full Windows update log so failures are debuggable
  from a single file across the Rust pre-quit phase and the detached helper.

## Architecture and Boundary Questions

- Runtime and owning boundary: `oneterm-update`; the Windows helper is a
  detached `cmd.exe` process spawned before the app quits.
- Data ownership and lifecycle: install directory binaries, a backup in the
  update cache, and staged package files. Log lives at
  `<config>/updates/update.log`.
- Auth, security, privacy, or audit: process termination is scoped to images
  inside OneTerm's own install directory (full-path match, never process name).
- External systems and side effects: `TerminateProcess` on OneTerm's own
  console-host children; no network effects.
- Public interfaces and compatibility: none changed. The fix only benefits
  builds that ship it (the on-disk 0.4.0 helper is already baked in).

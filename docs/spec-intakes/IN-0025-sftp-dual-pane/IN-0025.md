# Spec Intake: SFTP dual-pane (Local + Remote)

ID: IN-0025
Date: 2026-09-11
Type: new_spec
Lane: high_risk

## Source

Owner request (2026-09-11, Vietnamese): the SFTP Browser only shows the remote server today.
It should be able to Expand or Collapse. Collapsed keeps the current UI. Expanded splits the
browser into two parts, Local on the left and Remote on the right, and adds the usual
Local ↔ Remote functions found in other SFTP tools.

## Requested Outcome

The SFTP Browser toolbar gains an expand/collapse toggle. Collapsed is today's single remote
pane. Expanded shows a horizontal resizable split: a Local pane (this machine's file system)
on the left and the existing Remote pane on the right, with the transfer queue under both.
The Local pane browses directories (path box, back, refresh, double-click, sortable
Name / Date Modified / Size columns) and offers New Folder, Rename, Delete, Refresh. Between
the panes: Upload (local selection → remote cwd), Download (remote selection → local cwd,
no save dialog while expanded, overwrite confirmed), double-click on a local file uploads it,
and drag & drop of a row from one pane into the other transfers it. The expanded flag and the
local directory persist in `docks.json` under the SFTP-owned `sftp_table_state` field.

## Project Impact

- Surfaces: SFTP Browser panel (right dock, `SshClientPanel` bottom section).
- Contracts: `docks.json` `sftp_table_state` gains `expanded` and `local_dir` (additive,
  serde defaults); `SftpBackend` unchanged; no new actions.
- Users: default behaviour unchanged (collapsed). Download while expanded targets the local
  pane's directory instead of opening a save dialog; the collapsed flow keeps the dialog.
- Safety: the Local pane can delete local files/folders (recursive, confirmed) and a download
  can overwrite a local file (confirmed). Both run on the user's own disk; see the LLD.

## Architecture and Boundary Questions

- Runtime and owning boundary: everything lives in `crates/sftp-ui`. Local listing uses
  `std::fs` on the GPUI background executor (no new crate, no backend trait for the local
  side). Remote operations keep going through `SftpBackend`.
- Data ownership and lifecycle: `LocalPane` (one per `SftpPanel`, independent of the active
  SSH backend) owns the local cwd, entries, sort, and selection. The remote side is unchanged
  and still snapshots per backend in `SftpBrowserStore`.
- Auth, security, privacy, or audit: none new. Local paths are host `PathBuf`s; remote paths
  stay `RemotePath`; the two never mix (`FileEntry` is not reused for local rows).
- External systems and side effects: local disk writes (mkdir, rename, delete, download
  target); each destructive one is confirmed.
- Public interfaces and compatibility: `SftpTableState` gains two defaulted fields; an old
  `docks.json` loads as collapsed with the home directory.

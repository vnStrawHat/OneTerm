# Spec Intake: Embeddable VT core

Date: 2026-09-15
Type: new_initiative

## Source

Owner request, 2026-09-15 (verbatim intent):

> `oneterm-vt` shall have the same mission as `alacritty_terminal` and `rio-vt`
> (<https://github.com/raphamorim/rio/tree/main/rio-vt>): an embeddable terminal core usable by
> other projects, not only OneTerm. It contains no rendering. Whatever belongs in the core should
> move into it. OSC handling should move into it too, but with a convenient mechanism to extend
> and override.

Decisions the owner took with the request; this intake implements them and does not re-open them:

| # | Decision |
| --- | --- |
| a | `crates/terminal/src/search.rs` moves into the engine; regex sits behind an optional cargo feature so the default dependency set stays light. |
| b | `key_encode.rs` and `mouse_encode.rs` move from `crates/terminal` into the engine (`KeyboardFlags` and `MouseProtocol` already live there). |
| c | The `render` module and its types are renamed to a name that says "snapshot, no drawing" -- `snapshot` or `frame`, justified in one paragraph. |
| d | OSC processing moves into the engine, with an extension / override mechanism. |
| e | The crate keeps the name `oneterm-vt`, stays Apache-2.0, and is published from this repository. |
| f | ~~PTY,~~ clipboard backends, security policy, URL policy and GPUI stay **out** of the core. **Amended by the owner ruling of 2026-09-15 below: the PTY comes back in.** |

**Owner ruling, 2026-09-15 (verbatim intent):**

> I still want a PTY in the core: provided by default, and overridable if wanted.

This reverses decision (f) **for the PTY only**. Clipboard backends, `TerminalSecurityPolicy`, URL
policy and GPUI stay out, unchanged. `crates/pty` is deleted and its 2 759 lines move to
`crates/vt/src/pty/` behind a cargo feature `pty` that is on by default -- `rio-vt`'s shape, which
the parity table below previously called "the shape to avoid". `--no-default-features` keeps the
crate at its six leaf dependencies and compiles no platform code, which is what "overridable" is
bought with. `US-0104` implements it; [`low-level-design/pty.md`](low-level-design/pty.md) is the
design, including the decision that the transport traits are gated with the feature rather than
living in a feature-independent module, and why.

Four further owner rulings of the same day stand alongside it, and `US-0097` (merged @ `0558fa2`)
has already implemented all four: **no crates.io publish** -- the crate is consumed as a git
dependency and `crates/vt/Cargo.toml` carries an explicit `publish = false` (Open Decision 2); **no
`serde` feature** (Open Decision 3); **`Config::product_name` default** `oneterm-vt(<engine
version>)` (Open Decision 5); and the crate **stays in this monorepo** (Open Decision 6). `US-0104`
inherits that state rather than re-deciding it: its packaging criterion is the gate `US-0097`
shipped, `cargo package --list | verify-dependency-graph.py --package-list -`, and there is no
`cargo publish` anywhere in it.

## Requested Outcome

`oneterm-vt` becomes a terminal core another project can add to its `Cargo.toml` and use without
OneTerm: it parses bytes, owns the grid and the VT semantics, hands back a pull-side snapshot and a
value-typed event stream, encodes key and mouse input, searches its own scrollback, and handles the
OSC set a terminal is expected to handle -- with a documented way for the embedder to add an OSC
number, override a built-in one, or observe one without changing engine behaviour.

After this intake:

- `crates/vt` is a crate another project can depend on by git (Open Decision 2: **not** published
  to crates.io): it carries a README, one headless example, a CHANGELOG, the licence text and
  `#![warn(missing_docs)]`, and its rustdoc is readable by someone with no access to this
  repository's `docs/` tree.
- Every OSC number OneTerm interprets today is parsed **once**, in the engine, into a typed
  `VtEvent`. `crates/terminal` keeps only the policy layers: sanitising, rate limiting, clipboard
  origin, URL policy, the `PathBuf`, the session event fan-out.
- OneTerm's OSC 20308 agent channel and `TerminalSecurityPolicy` stay outside the core and become
  the crate's worked example of an embedder extension.
- Key and mouse encoding and scrollback search are the engine's, with regex optional and off by
  default.
- The engine's public API says "snapshot", not "render".

**No user-visible OneTerm behaviour changes**, with one exception the owner must rule on (the
deprecated `OSC 9;7` alias -- see Open Decisions). If any packet in this intake changes what a user
sees on screen, that packet is wrong.

Two conclusions this table is the evidence for:

1. **Neither reference core is extensible for OSC.** Both are a compile-time `match` with a silent
   drop. OneTerm's own OSC 20308 proposal is exactly the case that would force a fork of either --
   which is the history `DEC-0014` records. The extension mechanism is therefore not parity work,
   it is the one place `oneterm-vt` can be better than both, and it is what makes the crate worth
   publishing at all.
2. **`oneterm-vt`'s dependency budget is already the smallest of the three by a factor of two.**
   *(Superseded in part by the owner ruling of 2026-09-15.)* This row originally read that
   decision (f) is what keeps the budget there and that `rio-vt` shipping a PTY by default is the
   shape to avoid. The ruling copies `rio-vt`'s feature shape deliberately, and the claim is
   narrowed rather than dropped: the budget that matters is the one a VT-only embedder pays, and
   `cargo build -p oneterm-vt --no-default-features` keeps that at six leaf dependencies with no
   platform code. Neither reference core can offer that number at any feature setting. The cost of
   the ruling -- `polling` becomes a public dependency, and the default `cargo tree` no longer
   reads as platform-free -- is recorded in

### The DCS routing bug

`dcs_hook` (`crates/vt/src/terminal/dispatch.rs:1311-1319`) ignores its `_intermediates` argument
and matches only the final byte:

```rust
fn dcs_hook(&mut self, _params: &Params, _intermediates: &[u8], byte: u8) {
    self.state.dispatched = true;
    if byte == b'q' {
        self.state.graphics.parser = Some(SixelParser::new());
```

`DECRQSS` is `DCS $ q <sequence> ST` and `XTGETTCAP` is `DCS + q <caps> ST`. Both have final byte
`q`. Both therefore open the Sixel decoder and feed it their payload. This is a live engine defect
independent of everything else in this intake and is fixed first, in `BUG-0058`.

## Project Impact

- **Surfaces.** No OneTerm screen, key binding, setting, persisted file or CLI changes. The one
  candidate behaviour change is Open Decision 1 (`OSC 9;7`).
- **Contracts.** `oneterm-vt`'s Rust public API becomes an **external** contract: today it is
  workspace-internal with two consumers and can be changed freely; after `US-0097` anything outside
  this repository can pin a commit or a tag, and semver applies to what they pin. That single fact is what puts this intake in the high-risk
  lane. `oneterm-terminal`'s `TerminalSession`, `SessionFactory`, `SftpBackend`, `AppServices`,
  `WorkspaceCommands` and the dock panel names are untouched.
- **Crate graph.** R1-R5 and R9-R12 keep holding. R6, R7 and R8 are **rewritten by `US-0104`**: the
  workspace loses a crate (`oneterm-pty`), `local-shell` and `tools` re-point at `oneterm_vt::pty`,
  and R7 stops claiming the engine is unconditionally platform-free -- the replacement text is in
  [`low-level-design/pty.md`](low-level-design/pty.md), "Rule changes". What survives intact is the
  part that matters: `vt` depends on no OneTerm crate under any feature set, and
  `--no-default-features` is still six leaf dependencies. `crates/terminal` sheds about 1 500 lines
  of parsing to become what its own name says -- an adapter with policy.
- **Users.** None directly. Indirectly, external embedders become possible, and every OSC number is
  parsed once instead of twice.
- **Systems.** No schema, no migration, no secret. Packaging gains a consumable crate
  (`US-0097`), fetched by git rather than from a registry; `THIRD-PARTY-NOTICES.md` is unaffected while the `regex` feature is off, and
  unaffected even when on, because `regex 1.12.4` is already in the app graph via
  `oneterm-highlight`.
- **Tests.** Every existing test keeps passing untouched except where a packet names the file it
  moves. Tests move with their code: the adapter's `osc.rs`, `key_encode.rs`, `mouse_encode.rs` and
  `search.rs` test modules go to `crates/vt` with the functions they cover.

## Architecture and Boundary Questions

- **Runtime and owning boundary.** The engine stays synchronous, lock-free, callback-free and
  allocation-bounded. The embedder owns the lock, the event loop, the transport and every policy.
  `crates/terminal` remains the OneTerm-shaped adapter and keeps `TerminalHandle`, the pump, the
  security policy, the URL policy and the agent channel.
- **Data ownership and lifecycle.** Unchanged: `EventBatch` owns every payload span for the life of
  one `feed`; `VtEvent` is deliberately not `Clone` so an event cannot outlive its batch. The new
  typed OSC variants follow the same rule.
- **Auth, security, privacy, audit.** The core gains no policy. It parses OSC 7 into `host` and
  `path` byte spans and stops; it does not touch the filesystem, the clipboard, the network or any
  environment variable. `TerminalSecurityPolicy` (title, notification, clipboard and cwd caps, the
  ten-per-second notification limiter, the remote clipboard gates) stays in `crates/terminal` and is
  the reason the engine must keep reporting rather than acting. The `OSC_INLINE = 2048` and
  `OSC_LARGE = 8 MiB` ceilings and the `large` opt-in survive the rewrite unchanged.
- **External systems and side effects.** **None new** (Open Decision 2). The crate is not
  published; another project consumes it by git from this repository, which adds no service this

## Open Decisions and Questions

- [x] **1. The deprecated `OSC 9;7` alias.** `crates/terminal/src/backend/osc_router.rs:264` says it
  "is dropped in the next release", and `docs/osc-agent-status.md` section 3.1 carries the same
  clause. Under `OscRoutes` the engine's built-in `OSC 9` arm would parse `9;7;<base64>` as a
  desktop notification. **Owner ruling (2026-09-15): `OSC 9;7` is OneTerm's custom spelling and is
  handled outside the engine; `oneterm-vt` only provides the mechanism.** So `US-0098` keeps the
  alias: the adapter routes `9` as `BuiltinAndForward` with `large(9, true)`, discards the
  `VtEvent::Notification` whose forwarded first parameter is `7`, and feeds the forwarded payload to
  `osc_agent`. The engine's `OSC 9` arm stays a clean built-in with no knowledge of `7`. The alias
  is the live demonstration of the wrap route; its eventual removal is a separate adapter-only
  change and not part of this intake.
- [x] **2. First publish.** Does the owner want `cargo publish` to happen inside this intake, or does
  `US-0097` stop at `--dry-run` plus a release-workflow step? **Owner ruling 2026-09-15:
  `oneterm-vt` is not published to crates.io. Other projects consume it as a git dependency on
  the OneTerm repository for now.** `crates/vt/Cargo.toml` therefore carries an explicit
  `publish = false`, there is no docs.rs page and no crates.io link anywhere, and the packaging
  gate is `cargo package` rather than `cargo publish --dry-run`. The manifest keeps its
  `description`, `keywords`, `categories`, `readme`, `license` and `rust-version`, so the day the
  owner decides otherwise the flip is one line.
- [x] **3. `serde` feature.** Worth adding at all? `alacritty_terminal` has it on by default and
  `rio-vt` depends on serde unconditionally, so an embedder will expect it, but nothing in OneTerm
  serialises an engine type. `api-surface.md` proposed it as default-off over `Config`, `Rgb`,
  `Color`, `Style`, `Attrs`, `Pos`, `Size`, `RowId` and `SelectionRange` only. **Owner ruling
  2026-09-15: no `serde` feature.** Adding one later is a patch bump; removing one is not.
- [ ] **4. MSRV policy.** `rust-toolchain.toml` pins 1.96.0 and `[workspace.package] rust-version`
  follows it. A published crate's MSRV is a compatibility promise, and OneTerm bumps its toolchain
  freely today. Proposal in `packaging.md`: an MSRV bump is a minor version bump and a CHANGELOG
  line, never a patch. Owner; blocks nothing.
- [x] **5. `Config::product_name` default.** `XTVERSION` replied `OneTerm(<version>)` before
  `US-0097` and `DA2` replied `CSI > 0 ; <version> ; 1 c`. Both embedded the crate's own
  `CARGO_PKG_VERSION`, which for an embedder is the *engine's* version, not theirs. **Owner ruling
  2026-09-15: the default is `oneterm-vt(<crate version>)` when `product_name` is `None`.** `Config::product_name: Option<Cow<'static, str>>`, `None`
  meaning that string; OneTerm's adapter sets `OneTerm(<app version>)`, so its own bytes did not
  change.
- [x] **6. Repository layout.** A published crate whose source lives at `crates/vt` inside an
  application repository is unusual but legal, and `rio-vt` does exactly this. **Owner ruling
  2026-09-15: the crate stays in the OneTerm monorepo.** Every repository link `US-0097` writes is
  an absolute `https://github.com/vnStrawHat/OneTerm/...` URL for that reason, and the git
  dependency form in the README names the same repository.

# Spec Intake: Sixel graphics

ID: IN-0028
Date: 2026-09-11
Type: new_spec
Lane: normal

## Source

Owner request (2026-09-11): "Sixel or Kitty graphics: the render engine is ours now, drawing
images as textured quads is feasible and a highlight." Ranked third after font fallbacks and
ligatures (IN-0027). Sixel first (DCS only, the vendored `vte` already delivers DCS
hook/put/unhook); the Kitty graphics protocol needs APC dispatch and a much larger command
set and is a later intake.

## Requested Outcome

A program that emits a Sixel image (`DCS P1;P2;P3 q ... ST`, e.g. `img2sixel`, `chafa -f sixel`,
`lsix`, `timg`) sees it drawn in the terminal grid at the cursor position, the cursor moves
below the image, the image scrolls with the text and disappears when its cells are erased or
the screen is cleared, and the terminal advertises Sixel support in its primary device
attributes so those programs pick Sixel automatically.

## Project Impact

- Surfaces: terminal grid (image quads); no settings, no menu.
- Contracts: vendored `vte` gains `Handler::dcs_hook/dcs_put/dcs_unhook`; vendored
  `alacritty_terminal` gains a `graphics` module (`Cell::graphic()`, `Term::take_graphics`,
  `Term::set_cell_size`), and DA1 changes from `CSI ? 6 c` to `CSI ? 62 ; 4 c`;
  `TerminalContent` gains `graphics`; `TerminalInput` gains `set_cell_size` (additive,
  default no-op).
- Users: no behavior change until a program emits Sixel; DA1 now claims VT220 + Sixel, which
  `tmux`, `lsix`, `chafa`, `timg` read.
- Dependencies: `image` (already in `Cargo.lock` through GPUI) becomes a direct dependency of
  `oneterm-terminal-view` for `image::Frame`, the only way to build a `gpui::RenderImage`.
- Memory: decoded images are RGBA in the `Term` only until the next snapshot moves them out;
  the view keeps a bounded store (64 images / 64 MB, oldest evicted, GPU tile dropped).

## Architecture and Boundary Questions

- Runtime and owning boundary: decoding and placement happen inside the vendored `Term`
  (under the `FairMutex`, in the pump thread) because cursor movement and scrolling must be
  consistent with the byte stream; the view only uploads and paints.
- Data ownership and lifecycle: pixels are owned by `Arc<GraphicData>`; the `Term` holds only
  the not-yet-snapshotted ones; the view store owns the GPU tiles; cells hold a `(id, col,
  row)` reference and travel with the grid (scrollback, alternate screen, resize).
- Auth, security, privacy, or audit: Sixel data comes from the PTY (untrusted). The decoder
  clamps dimensions (4096 x 4096), ignores malformed bytes, and allocates only after the
  raster size is known or as bands arrive; a stream that never sends `ST` is bounded by
  the same clamp. No file or network access.
- External systems and side effects: none.
- Public interfaces and compatibility: `TerminalInput::set_cell_size` is additive with a
  default; `Event` enum unchanged; DA1 response changes (documented in the LLD).

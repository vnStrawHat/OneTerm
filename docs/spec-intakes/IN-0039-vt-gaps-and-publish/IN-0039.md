## Why this is a `change_request`

`docs/HARNESS.md` offers six input types. The reasoning, since the choice is not obvious:

- **not `new_initiative`.** IN-0038 is the initiative. This intake adds no crate, no product
  surface and no mission; it finishes the one already accepted.
- **not `spec_slice`.** A slice implements part of a spec that already covers it. IN-0038 ruled
  three of these four items explicitly **out of its own scope**: `DECRQCRA` (the `US-0102`
  evidence: "none of it belongs in a print-path packet"), the kitty encoder
  (`encoding-and-search.md`: "wiring the two together is a future packet"), and benchmarks (never
  scoped at all). They are not slices of an accepted spec; they are additions to it.
- **not `maintenance`.** Three of the four change the crate's outward contract -- its public
  surface, the bytes `encode_key` returns, and the replies it sends.
- **`change_request`.** An accepted public contract is being extended in three places and a defect
  in it is being fixed in a fourth. That is a request to change what was agreed.

`BUG-0059` on its own would be `maintenance`; it is inside this intake rather than standing alone
because it is the first rung of the same request and because the gate it adds is what keeps the
other three honest.

## Why the lane is `high_risk`

Two independent triggers from `docs/HARNESS.md`, either one sufficient:

- **Public contracts.** `oneterm-vt`'s Rust API and its documented reply bytes are already an
  external contract -- other projects pin a commit on this repository and semver applies to what
  they pin (IN-0038 sat in the same lane for the same reason). `BUG-0059` adds four names to it,
  `US-0105` changes the bytes `encode_key` returns for an input, and `US-0106` adds three new reply
  forms and one `Config` field.
- **A new capability at a trust boundary.** `DECRQCRA` is a screen-readback primitive: it lets a
  program running inside the terminal read the characters on the screen back out. xterm gates it
  behind `allowWindowOps`, WezTerm behind an off-by-default configuration flag, and this engine
  must make the same kind of deliberate choice rather than shipping it open. See
  [`low-level-design/conformance-queries.md`](low-level-design/conformance-queries.md).

Detail (low-level) design is therefore mandatory before any `story create`, and all four concern
files exist below.

## Architecture and Boundary Questions

- **Runtime and owning boundary.** Unchanged and load-bearing: the engine stays synchronous,
  lock-free, callback-free and allocation-bounded, and every new reply is a value in the
  `EventBatch` exactly as `DA1`'s already is. `US-0105`'s encoder is a pure function of
  (key event, mode snapshot) and has no side effect, which is what keeps it testable as a table.
- **Data ownership and lifecycle.** `US-0106` introduces the first DCS payload the engine buffers
  for a reason other than an image. It reuses the existing `DCS_MAX_BYTES` ceiling and the existing
  abort path, so a hostile stream cannot make it allocate without bound; the buffer is one
  `Vec<u8>` on the terminal, cleared at `dcs_unhook`, at `RIS` and at `DECSTR`.
- **Auth, security, privacy, audit.** One genuinely new surface: `DECRQCRA` reads the screen back.
  The engine gains `Config::allow_screen_readback`, default **false**, and with it false the
  sequence is counted unhandled and answers nothing -- which is what the engine already does for
  it today, so the default is the status quo. Everything else stays policy-free. `XTGETTCAP`
  answers from a fixed table compiled into the crate and never reads a terminfo database, an
  environment variable or a file.
- **External systems and side effects.** **None, new or otherwise.** The crate is not published,
  no workflow gains a credential, and no packet here contacts a network at build or test time. The
  `esctest` job runs a checked-in Python harness against a locally built binary.
- **Public interfaces and compatibility.** The nine-clause promise in
  [`IN-0038/low-level-design/api-surface.md`](../IN-0038-embeddable-vt-core/low-level-design/api-surface.md)
  governs every change here, and it binds tags exactly as it would bind releases -- a consumer
  pinning a tag is as broken by a rename as one pinning a version. `US-0105` is the one packet that
  changes what an existing function returns for an existing input. The before-and-after list, the
  bump arithmetic, and the one clause this intake amends are in
  [`low-level-design/api-surface.md`](low-level-design/api-surface.md).

## Open Decisions and Questions

- [x] **1. Publish to crates.io?** **No.** IN-0038 Open Decision 2 stands, restated by the owner on
  2026-09-15. No packet in this intake touches `publish`, and no decision record is opened for it.
  The cost is accepted and recorded in "Gap 3 is accepted, not scheduled" above.
- [ ] **2. Is `DECRQCRA` default-on or default-off?** The design proposes
  `Config::allow_screen_readback` defaulting to **false**, matching xterm's `allowWindowOps` and
  WezTerm's `enable_checksum_rectangular_area`. The cost is that an `esctest` run has to turn it
  on, which is one line in the harness. The alternative -- default **true**, so that "the terminal
  conforms" is true out of the box -- hands every program inside every OneTerm terminal a way to
  read the screen back. Owner; does not block `US-0106` starting, does block its acceptance.
- [x] **3. Which `DECRQCRA` checksum variant?** Decided inside
  [`low-level-design/conformance-queries.md`](low-level-design/conformance-queries.md): the variant
  xterm reaches with `checksumExtension: 7` -- positive, attributes excluded, blanks counted rather
  than trimmed -- which is the one variant `esctest` can compare against without a per-cell
  correction, pinned by a doctest. Not owner-blocking; recorded because a checksum variant cannot
  be changed later without breaking every harness that stored a number.
- [ ] **4. Should the tier-3 regression guard run in CI?** `IN-0029`'s rule R-29 says no numeric
  target appears in a packet's exit criteria, and a shared GitHub runner is too noisy for a tight
  threshold. The design puts the guard in `vt-bench --check` with a deliberately wide band and runs
  it by hand on the baseline machine rather than in the quality gate. If the owner wants it in CI
  as well, it goes in report-only, like `esctest`. Owner; blocks nothing.
- [ ] **5. Should `Config` gain `#[non_exhaustive]` here?** The accepted IN-0038 design says
  `Config` is marked; the shipped code says it is not. `US-0106` is the packet that adds a `Config`
  field and therefore the packet that notices. The design applies the mark in the same commit,
  which is compatible with every construction site in this repository (all use
  `Config { ..Config::default() }`). Recorded as a drift finding rather than new scope; the owner
  can decline and pay a minor bump per future field instead.
- [ ] **6. MSRV policy** -- inherited unresolved from IN-0038 Open Decision 4, and untouched here.
  It is less urgent while the crate is consumed by git (a consumer pins a commit and chooses when
  to move) but it is not free: a tag that raises the MSRV still breaks a consumer who moves to it.
  The standing proposal is unchanged: an MSRV bump is a minor version bump and a CHANGELOG line,
  never a patch. Owner; blocks nothing in this intake.

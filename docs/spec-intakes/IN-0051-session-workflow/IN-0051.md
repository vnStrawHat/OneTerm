# Spec Intake: Connect all in group and per-session startup command

ID: IN-0051
Date: 2026-10-09
Type: new_spec
Lane: normal for feature 1 (Connect All in Group); **high-risk recommended** for feature 2
(per-session startup command), see [Lane](#lane) below. Owner to confirm (Q11).

Document number: 51.

## Source

A GitHub issue (paraphrased) asks for two enhancements to the SSH Sessions workflow:

1. **"Connect All in Group"** (or "Open All") in the context menu of a group folder in the SSH
   Sessions panel. Today that menu has only "Rename Group..." and "New Session". Proposed:
   filter `SshSessionStore` sessions by `group` and open a tab for each.
2. **An optional "Startup Command" per saved SSH session**: a text field in the session
   properties dialog; when set, OneTerm sends `<cmd>\r` to the shell channel once the
   interactive session is up, after `request_shell` and after the shell-integration bootstrap
   (`send_shell_integration_bootstrap`, `crates/ssh/src/session.rs` ~381 / ~753). Data:
   `pub startup_command: Option<String>` on `SshSession` with
   `#[serde(default, skip_serializing_if = "Option::is_none")]`, no schema bump.

**This is a records-only intake.** It checks the issue's claims against the code, records a
recommended design ([`high-level-design.md`](high-level-design.md) and, for the high-risk
half, [`low-level-design/startup-command.md`](low-level-design/startup-command.md)) and
candidate packets. No packet file is created and no code is written until the owner rules on
the open questions below.

### Facts this intake rests on (verified 2026-10-09 against main @dfcf6149)

**Feature 1**

- The group menu is as the issue says: `crates/session-ui/src/tree_render.rs:337-351` builds
  `Rename Group…`, a separator and `New Session` for a folder; `docs/ssh-client-connect.md`
  § 6.5 documents the same three rows.
- **Opening a saved session never opens a tab directly.** Double-click and the leaf's "Open"
  row call `open_connect_dialog` (`connect_dialog.rs:62`), which collects credentials; a tab
  appears only after authentication, in `connect_ssh_session`'s success branch
  (`common.rs:412`, `add_ssh_terminal_to_dock` puts a new tab in the centre dock). There is
  **no dialog-free connect path** today. `IN-0050` Q4 deliberately kept the connect dialog
  even when every password is saved ("one-click connect is a follow-up"). So "open a tab for
  each" needs a new path, not a loop over an existing one.
- **`connect_ssh_session` closes the topmost dialog blindly.** On success (`common.rs:478`)
  and before a host-key alert (`common.rs:517`) it calls `window.close_dialog(cx)`, which in
  GPUI Kit pops the *top* of the window's dialog stack, whatever it is
  (`gpui-component` 0.7 `Root::close_dialog` -> `active_dialogs.pop()`). That is correct while
  the connect dialog is on top, and wrong for a request that owns no dialog: the retry after
  "Trust and Connect" (`common.rs:603`) runs with no dialog of its own, so a dialog the user
  opens while it runs is closed when it completes. N concurrent dialog-free attempts would
  close each other's prompts routinely. This is an existing latent defect (reading only; not
  reproduced) and a precondition for feature 1: candidate `BUG-0084`.
- Each attempt holds one background-executor thread for its whole duration (up to the 60 s
  `CONNECT_DEADLINE`): `connect_ssh_session` spawns `factory.connect_ssh(..)` on
  `background_executor()` (`common.rs:450`) and `oneterm_ssh::connect` blocks on the shared
  runtime (`session.rs:202`, `runtime.block_on`). A group of 20 started at once would hold 20
  threads; Connect All must bound its parallelism.
- Unknown host keys open an alert per attempt (`open_host_key_confirmation`, `common.rs:547`);
  concurrent attempts would stack alerts and, through the blind close above, close each other.
  A changed key is rejected outright (`DEC-0010`), never prompted.
- `oneterm_state::vault_dialogs::ensure_unlocked(window, cx, on_ready)` runs `on_ready` after
  Unlock (or Set up) and **reports no cancel** (`US-0158` as built). One unlock covers every
  saved password until the vault locks again.
- There is **no mapping from an open tab to the saved session it came from**: a tab keeps only
  `SshDuplicateConfig` (host, port, user, hops). "Skip sessions already open" would need new
  tracking.
- Groups are flat (no nesting). The tree trims group names and sorts sessions by label within
  a folder (`tree_builder.rs` `build_tree_items`), and a search query filters what a folder
  shows. The folder `TreeItem` handed to the context menu carries its visible children
  (`TreeItem::children` is public), so the list Connect All acts on is already there, in tree
  order and with the filter applied; filtering the store by `group` would have to repeat the
  trim and would ignore the filter.
- Broadcast (`IN-0022`, `DEC-0009`): membership belongs to a Space; a new tab is a non-member;
  "Join All Spaces In Tab To X" is the one-click join, and it works within one tab only. One tab
  per session therefore means one join per tab. A split-placement seam exists for Duplicate
  Session (`SshDuplicateCompletion`, `crates/terminal-view/src/panel/duplicate.rs`).
- The session panel is hidden in the elevated instance (`IN-0043` M1), so Connect All never
  runs there.

**Feature 2**

- `send_shell_integration_bootstrap` (`session.rs:753`, called at `:381`) writes the bootstrap
  line **blind**, as type-ahead, right after `request_shell(true)` returns. That reply means
  sshd accepted the request, not that a shell is reading. The PTY is requested with
  `ECHO 0` while the bootstrap runs (`SHELL_INTEGRATION_PTY_MODES`), and the bootstrap's last
  command is `stty echo`. So the issue's send point is an *ordering* in the byte stream, not a
  readiness signal: a command written there is typed into whatever reads the PTY first (an
  expired-password `passwd` prompt, an rc-file menu, an auto-attached `tmux`) and, in a shell
  without a line editor (`dash`, `sh`), is **not echoed**, because ECHO is still off when the
  bytes arrive. It would also run inside `connect`'s future, so a failure there fails the whole
  connection.
- **A readiness signal already exists.** The bootstrap's closing `__oneterm_precmd` call
  emits OSC 133 `A`, for every POSIX shell (bash, zsh, sh, dash; `terminal-backend.md`
  § 6.1.2); the router counts it in `SharedSessionState::prompt_count`
  (`crates/terminal/src/backend/osc_router.rs:239`, `state.rs:57`), and `ssh_main_task`
  (`crates/ssh/src/task.rs:37`) holds that state and the channel. For bash and zsh the bootstrap
  also appends OSC 133 `B` to `PS1`, so `B` arrives when the first real prompt is drawn, just
  before the line editor reads; the router passes `B` on as an event but does not count it
  (`osc_router.rs`, the `_ => {}` arm). `sh` and `dash` get the one `A` and no `B`. fish, csh
  and tcsh cannot parse the bootstrap and emit nothing from it.
- **SSH-level 2FA prompts cannot happen**: keyboard-interactive is supported only as a
  one-prompt password fallback, and any other prompt fails authentication
  (`session.rs:596-663`). The "never type into a password prompt" risk is at the PTY level,
  after login, not in SSH authentication.
- **There are no SFTP-only sessions.** The SFTP channel rides the terminal connection
  (`session.rs` opens it after the shell); every saved-session connect opens a shell. The
  "never for SFTP-only sessions" rule is moot today.
- A precedent sends text right after connect: Duplicate-at-cwd writes `cd '<dir>'` with
  `ssh_session.send_text` on success (`common.rs:482`). It is blind type-ahead too; it is
  acceptable for a `cd` into a directory the source tab was in, and not the bar for an
  arbitrary user command (HLD § Alternatives).
- `shell_integration` is `true` for every saved-session connect (`connect_dialog.rs:582`);
  a duplicate copies the source's value.
- Persistence: `SshSession` has no `deny_unknown_fields`; an optional field with
  `skip_serializing_if` needs no schema bump, and an older binary ignores it and **drops it on
  its next write** (sessions kept), the same documented loss as `sealed_password`
  (`docs/agents/persistence.md`, `ssh_session.json` row). The issue's data shape is right with
  that caveat.
- `DEC-0021` and `docs/PROJECT.md`: secrets are persisted only sealed; no document holds a
  plain-text password. `SecretPurpose` has one variant, `SshPassword`
  (`crates/vault/src/vault.rs:31`).
- Debug logs: `ssh_main_task` logs written byte counts, never bytes (`task.rs`, "write {}
  bytes").
- Local shells have no profile store: `terminal.json` holds one `shell: LocalShellConfig`
  (`crates/core/src/config/shell.rs:68`). "Local-shell profile parity" needs a profiles
  capability first.

## Requested Outcome

1. From a group's context menu the user connects every session the folder shows, with at most
   one master-password unlock, no dialog per session, a bounded number of attempts at a time,
   and one summary that names every session that did not connect and why. One failure never
   stops the rest.
2. A saved session can carry a one-line command that OneTerm types into the remote shell once
   that shell has shown its first prompt, visibly, as if the user had typed it; never into
   anything that is not a ready shell, never twice, never logged.

## Security Analysis (feature 2)

1. **Who authors the bytes.** The command is written by the user in their own session record;
   OneTerm types it into a shell the user is logging into with their own credentials. It is not
   a remote-injection vector: nothing the server sends can set or change it. A hostile *file*
   is the remaining source: someone who can write `ssh_session.json` can make OneTerm type a
   command on the user's next connect. That attacker can already re-point `host`, add a
   `jump_host` or a port forward, or replace `oneterm.exe`; the field adds no new capability,
   but it does make the effect immediate and remote. Mitigations: the validator refuses control
   characters and newlines at send time too (a hand-edited value cannot smuggle key sequences
   or a second line), the command is shown where the user sees it (typed at the prompt), and
   the session dialog shows the stored value.
2. **Secrets at rest.** `ssh_session.json` would hold the command in plain text. Users will put
   `export TOKEN=...` there. Sealing it would not keep the secret: the command is echoed on
   screen, kept in scrollback, written to the terminal log when logging is on, saved in the
   remote shell history, and visible in the remote process list while it runs. Sealing would
   give a false assurance and cost an unlock for every connect of a key-only session, a second
   reseal-on-address-edit flow in the session dialog, and loss on vault reset. **Recommended:
   plain text, stated in the dialog ("Stored in plain text. Do not put passwords or tokens
   here."), and a decision (`DEC-0022` candidate) that a startup command is configuration,
   not a secret.** The alternative is analysed in the LLD § 6.
3. **Never into the wrong program.** Sent only after the shell reports a prompt (OSC 133 `B`,
   or `A` plus a 250 ms grace for shells that emit no `B`), so an expired-password prompt, an
   rc-file menu or an auto-attached multiplexer (which emit no mark) never receive it; after a
   deadline (15 s recommended) it is dropped with a toast, never sent blind (Q9).
4. **Never mixed with the user's typing.** If the user has typed into the tab before the
   prompt arrived, the command is not sent (LLD § 3). A new SSH tab becomes the active tab
   (`DockArea::add_panel_view` inserts with `activate: true`), so under Connect All a user
   typing elsewhere can land keys in a tab whose prompt has not appeared yet: the case is real.
5. **Not fanned out.** The backend writes it on the channel directly; broadcast fans out only
   input that a member view's handlers send (`IN-0022`), so a startup command never reaches
   another Space.
6. **Logging.** The text is never written to the application log, at any level (byte count
   and outcome only). The terminal log captures it as echoed output, like anything typed.
7. **Jump hosts.** Only the target's command runs; a hop session's own command is ignored when
   it serves as a hop (only the target has a shell channel).

### Lane

**Feature 2 is recommended high-risk.** HARNESS lists external effects, secrets/privacy,
public contracts and persisted data as triggers; feature 2 makes OneTerm execute a command on
a remote host without a keystroke (external effect whose failure mode is typing into the
wrong program), settles a secrets-at-rest question that needs a decision next to `DEC-0021`,
adds a field to `SshConfig` (a core contract every connect path builds) and makes the
shell-integration marks a safety gate rather than a display hint. The schema change itself is low risk
(additive, no bump). High risk here means an explicit readiness contract, explicit proof for
each "never", and the LLD, not a large packet. **Feature 1 stays normal**: it composes
existing connect, vault and host-key paths without weakening any of them; its one
security-relevant choice (dialog-free connect with saved passwords, Q1) is an owner ruling on
an existing `IN-0050` follow-up, not a new mechanism.

## Architecture and Boundary Questions

- Runtime and owning boundary: Connect All lives entirely in `oneterm-session-ui` (it already
  owns the store, the connect flow and tab placement); no new crate edge. The startup command
  is carried by `oneterm-core::SshConfig` and sent by `oneterm-ssh`, the only crate that holds
  both the channel and the prompt-mark state (R3, R8 kept).
- Data ownership and lifecycle: `startup_command` is owned by `ssh_session.json`
  (`oneterm-session-ui`); a batch is in memory, one per group, gone on restart.
- Auth, security, privacy, or audit: § Security Analysis; Connect All reuses saved passwords
  under the existing vault rules and never weakens host-key checking.
- External systems and side effects: SSH connections and, for feature 2, one typed command per
  connection on the remote host.
- Public interfaces and compatibility: `SshConfig` gains a field (every struct literal
  changes); `ssh_session.json` gains an optional field (older binaries drop it on write); no
  `oneterm-vt` change.

## Open Decisions and Questions

- [ ] **Q1 (owner): dialog-free connects inside Connect All.** `IN-0050` Q4 kept the connect
  dialog for saved passwords and deferred one-click connect. Connect All needs it for the
  sessions whose credentials are all known (agent, unencrypted key, saved password after one
  unlock). Recommended **yes, only inside Connect All**; the single-session double-click keeps
  its dialog.
- [ ] **Q2 (owner): sessions that need typing** (no username, password not saved, an encrypted
  key, a hop without a saved password). Recommended for `US-0160`: **not attempted, named in the
  summary** ("needs a password: open it to connect"). Alternative: open their connect dialogs
  one at a time after the batch (follow-up).
- [ ] **Q3 (owner): unknown host keys during Connect All.** Recommended: **reported, not
  prompted** ("host key not trusted yet: open it once to verify"); twenty fingerprint alerts in
  a row invite clicking through without checking. Alternative: one alert at a time after the
  batch. Changed keys are rejected either way (`DEC-0010`).
- [ ] **Q4 (owner): confirmation.** Recommended: confirm when the folder shows **more than 5**
  sessions (count and how many will be skipped in the question). Alternatives: always, never.
- [ ] **Q5 (owner): sessions already open.** Recommended: **open another tab**, as a double-click
  does today; skipping needs a tab-to-saved-session mapping that does not exist.
- [ ] **Q6 (owner): placement and broadcast.** Recommended for `US-0160`: one **new tab per
  session**, in completion order, like a single connect. Tiled-in-one-tab and "join channel X"
  are follow-ups. Alternative: include "join channel" in `US-0160`.
- [ ] **Q7 (owner): which sessions.** Recommended: **those the folder shows** (the search
  filter applies, tree order). Alternative: every session whose group matches, filter ignored.
- [ ] **Q8 (owner): storage of the startup command.** Recommended: **plain text with the
  note**, recorded as `DEC-0022`. Alternative: sealed under the vault (LLD § 6 lists the cost).
- [ ] **Q9 (owner): no prompt mark within the deadline** (fish, csh, tcsh, an rc-file that
  starts a program, an expired password). Recommended: **not sent**, one toast naming the
  reason, deadline 15 s. Alternative: send anyway after the deadline (blind type-ahead).
- [ ] **Q10 (owner): Duplicate of a live tab.** Recommended: **does not run** the startup
  command (it duplicates a connection and already sends `cd`); Duplicate Saved Session copies
  the field. Alternative: run it on every connection of the session.
- [ ] **Q11 (owner): lanes.** Recommended: feature 2 high-risk, feature 1 normal (§ Lane).

## Decision Candidates (proposed, not created)

> **DEC-0022 A startup command is plain-text configuration, typed only into a ready shell**
>
> 1. A per-session startup command is configuration, not a secret. It is stored in plain text
>    in the document of the session it belongs to, never sealed, never written to the
>    application log (byte count and outcome only), and the UI that edits it says it is plain
>    text. Secrets belong in the vault (a saved password) or on the remote host.
> 2. OneTerm types a command into a remote shell on its own initiative only after that shell
>    has reported a prompt on this connection (OSC 133 `B`, or `A` followed by a short grace
>    for shells that emit no `B`), only once, and only when the user
>    has not typed into the session first. It never sends blind type-ahead for a user command;
>    the shell-integration bootstrap (OneTerm's own line, echo off) is the one exception.
>    Without a prompt mark before the deadline the command is dropped and the user is told.
> 3. The command is one line of printable text (no control characters, no line breaks, at most
>    1024 bytes), validated where it is edited and again where it is sent; it is sent as typed
>    text followed by one carriage return, never inside a bracketed paste.

Alternatives to record: sealed under the vault (false assurance: echoed, logged, in remote
history; costs an unlock per connect and a second reseal flow); send right after
`request_shell` like the bootstrap (types into whatever reads first, invisible on `dash`);
send at connect return like Duplicate's `cd` (same problems); `\n` instead of `\r` (not what
Enter sends; some line editors bind `C-j` differently).

> **DEC-0023 (optional) A batch connect never prompts per session**
>
> An operation that connects several saved sessions at once asks for the master password at
> most once, before any attempt starts, and opens no per-session dialog: a session that needs
> typed credentials or an untrusted host key is reported in one summary, never prompted
> during the batch.

Record it only if the owner accepts Q2 and Q3 as recommended; it binds future batch features
(for example restoring sessions at startup).

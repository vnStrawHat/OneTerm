# Spec Intake: New Terminal button lists SSH sessions

ID: IN-0033
Date: 2026-09-14
Type: new_spec
Lane: normal

Document number: 33.

## Source

Owner request, 2026-09-14, written in Vietnamese and recorded here in English (this
repository's contributor text is English-only; see `scripts/check-english.py`): the "+"
(New Terminal) button should additionally show the items saved under "SSH Sessions".

Read out: the dropdown behind the "+" button in the center tab bar must also list the
sessions saved in `ssh_session.json`, so a saved SSH session can be opened from the same
place a local shell is opened.

## Requested Outcome

The "+" menu keeps its local-shell entries and gains a section listing every saved SSH
session by name, in storage order. Clicking one opens that session exactly as clicking it
in the SSH Sessions panel does — the connect dialog, then a new center terminal tab. With
nothing saved, the section shows a disabled hint and every other entry behaves as it does
today.

## Project Impact

- Surfaces: the `TerminalPanel` title suffix ("+" button) in the center tab bar, on every
  platform. No other view changes.
- Contracts: `docs/gui-layout.md` §Panel registration and presentation describes the "+"
  creation entry point; `docs/ssh-client-connect.md` §1 describes the SessionPanel as the
  single entry to the connect dialog. Both need one sentence added, not redefined.
- Users: one less trip to the right dock to reach a saved host. No behaviour is removed.
- Systems: no schema change, no new persistence, no new external effect. The saved list is
  read from the existing `SshSessionStore` global.

## Architecture and Boundary Questions

- Runtime and owning boundary: the menu is built in `crates/terminal-view`
  (`TerminalPanel::title_suffix`); the saved list and the connect dialog are owned by
  `crates/session-ui`. `oneterm-session-ui` already depends on `oneterm-terminal-view`
  (the single same-layer edge R5 allows), so the reverse edge is forbidden and would also
  be a cycle (R1). The two crates meet at `oneterm_state::commands::WorkspaceCommands`,
  the existing L2 fn-pointer registry that `crates/terminal-view/src/panel/duplicate.rs`
  already uses.
- Data ownership and lifecycle: `ssh_session.json` stays owned by `SshSessionStore`. The
  menu only reads it, and reads it at the moment the menu opens, so an added or deleted
  session is reflected on the next open without any observer wiring.
- Auth, security, privacy, or audit: no credential is read, stored, or displayed. Only the
  session label (and, for a label-less hand-edited entry, `host:port`) reaches the menu.
  Connecting goes through the unchanged connect dialog, so host-key policy, jump chains and
  logging overrides are untouched.
- External systems and side effects: none beyond the SSH connection the existing dialog
  already makes.
- Public interfaces and compatibility: two fields added to `WorkspaceCommands`, a struct
  built only at the composition root (`crates/app/src/init.rs`) and in test doubles. No
  persisted format and no action name changes.

## Open Decisions and Questions

- [x] Split button or plain button? **Plain button, unchanged.** The "+" is already a
  `Button` with `dropdown_menu(...)`: one click opens the popup. A split button would add a
  second hit target for a default action the menu's first entries already provide, so it is
  not worth a new control. Recorded in the HLD.
- [x] Group the sessions by their `group` field? **No.** The store exposes the group only as
  a `String` field per entry; grouping it is the tree panel's job and would need submenus
  for a list that is normally short. Flat, storage order, matching the request. Revisit
  only if the owner asks.
- [x] Does the session open into the current Space? **No — a new center tab**, which is what
  the SSH Sessions panel does today (`add_ssh_terminal_to_dock`). Matching that path
  verbatim is the point of the packet; changing placement would be a separate outcome.

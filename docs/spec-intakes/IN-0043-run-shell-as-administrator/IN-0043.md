# Spec Intake: Run a Windows shell as administrator

ID: IN-0043
Date: 2026-09-21
Type: new_spec
Lane: high_risk

Document number: 43.

## Source

Owner request, 2026-09-21, written in Vietnamese and recorded here in English (this
repository's contributor text is English-only; see `scripts/check-english.py`):

> In the "+" (New Terminal) button, I want the Windows shells to be able to run as
> administrator.

Read out: the dropdown behind the "+" button in the centre tab bar lists the platform's
local shells (`Command Prompt`, `PowerShell`, `PowerShell 7` on Windows —
`crates/terminal-view/src/panel/terminal_panel.rs:697-703`). The owner wants a way, from
that same menu, to start one of them elevated.

The request does not say *where* the elevated shell should appear, and Windows does not
allow the obvious answer. That gap is what this intake resolves before any code.

## Requested Outcome

A user can start an elevated Windows shell from the "+" menu, and can always tell whether
what they are typing into is elevated.

**Lane: high_risk.** Starting an elevated process is an external effect and a security
boundary: it crosses an integrity level, it goes through the UAC consent service, and
whatever the elevated process then reads or executes runs with an administrator token.
Under `docs/HARNESS.md` this means the owning decision and at least one detail design must
exist before any work packet.

**This intake is blocked on one owner decision.** Four shapes are possible and they differ
in cost by an order of magnitude; the research below recommends one. No work packet is
created until the owner picks. See `docs/decisions/DEC-0019-elevated-shells-open-in-an-elevated-window.md`
(status: Proposed).

## Project Impact

- **Surfaces.** The "+" menu (`crates/terminal-view/src/panel/terminal_panel.rs:681-767`).
  Under the recommended option also the window's identity: the OS title
  (`crates/app/src/window.rs:66`), the in-app title bar
  (`crates/workspace/src/layout/workspace/mod.rs:262`) and a per-window marker.
- **Process model.** OneTerm gains a second kind of process. It has **no command line**
  today (`crates/app/src/lib.rs:32-125` never reads `std::env::args`) and **no
  single-instance guard** (no `CreateMutex`, no named pipe, nothing) — both would be new,
  and the second is a security-relevant rule, not a convenience.
- **Contracts.** `docs/gui-layout.md:104` describes the "+" menu top to bottom;
  `docs/terminal-backend.md` sections 6.1 and 6.2 describe local shell resolution and the
  ConPTY spawn. Both gain paragraphs; neither is redefined. `docs/auto-update.md` and
  `docs/crash-reporting.md` each describe behaviour that changes meaning under elevation
  and need a sentence.
- **Users.** Windows users only. Nothing existing changes for anyone who does not use the
  new rows; the non-Windows menu is untouched.
- **Systems.** One new external effect (`ShellExecuteExW` with the `runas` verb), one new
  `windows-sys` feature (`Win32_UI_Shell`; `Cargo.toml:125-135` does not have it). No new
  dependency, no new persisted document, no schema change.

## Candidate Work Packets

**None created yet — the owner decides the option first**, and the high-risk lane also
requires a detail design under `low-level-design/` before `harness story create` is
allowed. What follows is the shape each option would take, so the decision can be made
against real packet counts.

### If the owner picks option A (recommended): the elevated shell opens in a new elevated OneTerm window

- [ ] `US-0130` — **OneTerm accepts an "open this shell" command line, and an elevation
      request is always served by the process that received it.** `run()`
      (`crates/app/src/lib.rs:32`) reads `argv` for the first time: an argument naming a
      `ShellKind` replaces the default startup shell (`IN-0031`, `DEC-0016`: exactly one
      initial shell). An unknown argument starts normally and logs. Records the rule that
      a future single-instance guard must never route an elevation request into another
      process. No dependencies. Verifiable on its own by launching `oneterm.exe` with and
      without the argument.
- [ ] `US-0131` — **The "+" menu's "Run as administrator" submenu launches an elevated
      OneTerm on the chosen shell.** The `#[cfg(windows)]` submenu, one new
      `WorkspaceCommands` fn pointer (`crates/state/src/commands.rs`), the
      `ShellExecuteExW` `runas` call with an explicit `lpDirectory` and
      `current_exe()` as `lpFile`, and the error map (declined = silent no-op, everything
      else = one message). Depends on `US-0130`.
- [ ] `US-0132` — **An elevated window says so, and the docs say what elevation costs.**
      The marker derived from the process token (never from the launch argument) in the OS
      title, the in-app title bar and inside the window; the submenu absent in an already
      elevated window; and the paragraphs in `docs/gui-layout.md`,
      `docs/terminal-backend.md`, `docs/auto-update.md` and `docs/crash-reporting.md`.
      Depends on `US-0131`. Independently acceptable: the marker is what makes the feature
      safe to use, and it is verified by looking at the window.

### If the owner picks option B (the cheap fallback)

- [ ] `US-0130` — **The "+" menu can start a Windows shell elevated in its own console
      window.** One `ShellExecuteExW("runas", <resolved shell program>, ...)` and one
      submenu. No command line, no marker, no process model: the shell runs outside
      OneTerm, in a plain `conhost` window, without OneTerm's theme, keybindings,
      scrollback, search or shell integration (the `runas` verb carries no environment
      block, so OSC 7 and OSC 133 are lost — `crates/core/src/config/shell.rs:338-365`).
      One packet, and the whole option.

Options C and D are not packeted: C ("Restart as administrator") destroys every open tab
and live connection for less benefit than A, and D (an elevated helper feeding a ConPTY
into this window) creates a standing elevation service this project would own. Both are
argued in full in `research/windows-elevation-and-conpty.md` section 3.

## Architecture and Boundary Questions

- **Runtime and owning boundary.** The menu is built in `crates/terminal-view`; launching
  a process is an external effect a feature crate must not perform directly. The two meet
  at `oneterm_state::commands::WorkspaceCommands`
  (`crates/state/src/commands.rs:38-70`), the fn-pointer registry `IN-0033` established
  and the composition root installs (`crates/app/src/init.rs:62-80`). **Open:** which
  crate owns the `ShellExecuteExW` call and the `is_elevated()` token query —
  `crates/core` (gpui-free, already carries Windows FFI) or `crates/app` (already owns the
  process-level concerns: crash handling, the Ctrl handler at
  `crates/app/src/lib.rs:78-93`, the allocator). R1-R12 permit either; the detail design
  decides.
- **Data ownership and lifecycle.** No new persisted document. Under option A the two
  processes share the config directory **only when the elevated token belongs to the same
  account**: `config_dir()` derives from `USERPROFILE`
  (`crates/core/src/config/shell.rs:91-96`, `:109-124`). Over-the-shoulder elevation (a
  standard user typing an administrator's credentials) gives the elevated instance a
  *different* `~/.OneTerm` — no saved sessions, no theme, no dock layout, its own crash
  store.
- **Auth, security, privacy, or audit.** The whole point of the lane.
  1. The UAC prompt is a real consent step, and declining is the normal case.
  2. An elevated OneTerm runs *everything* elevated: `russh` network code, SFTP transfers,
     key and `known_hosts` handling, config writes.
  3. `terminal.json` holds `LocalShellConfig::program` and `args`
     (`crates/core/src/config/shell.rs:68-81`) — a file the **unelevated** process can
     write that names an executable the **elevated** process would run. The rule "nothing
     the unelevated process writes may direct what the elevated process executes" must be
     defended in the detail design, not assumed.
  4. No channel is opened from the medium-integrity process into the elevated one. That is
     option D's attack surface and it stays out.
- **External systems and side effects.** One: `ShellExecuteExW` with `runas`, which hands
  the request to the AppInfo service and shows the consent UI on the secure desktop. The
  elevated process's own effects (PTY spawn, SSH, updater, crash store) are the existing
  ones under a different token.
- **Public interfaces and compatibility.** One field added to `WorkspaceCommands`, a
  struct built only at the composition root and in test doubles. A command line where
  there was none — new public surface for the binary, and the first thing a future
  single-instance feature will collide with. No persisted format and no action-name
  changes.
- **UIPI regressions inside an elevated window.** `crates/sftp-ui/src/render.rs:436-451`
  accepts `ExternalPaths` drops to upload files. Explorer runs at medium integrity, and
  UIPI forbids a drop onto a high-integrity window, so drag-and-drop upload does not work
  in the elevated window. Inherent to elevation, must be documented, cannot be fixed.

| --- | --- |
| Focused | Pure-data unit tests: the argument parser (`ShellKind` round trip, unknown argument falls back to the default shell and logs), and the `ShellExecuteExW` error map (`ERROR_CANCELLED` is a no-op, every other code produces a message). Both are testable without launching anything. |
| Unit | `cargo test -p oneterm-app`, `cargo test -p oneterm-state`, `cargo test -p oneterm-terminal-view`. |

| E2E | **Windows interactive desktop, and it needs a real UAC prompt, so it cannot be driven by the posted-message GUI walks this project uses.** Manual, with screenshots: (1) the submenu is present on Windows and absent on an elevated instance; (2) picking a shell shows a UAC prompt; (3) declining leaves the original window untouched and opens nothing; (4) accepting opens a second window that carries all three markers and has that shell open; (5) `whoami /groups` in the new tab shows the high mandatory level; (6) the original window's tabs and connections are still alive. |
| Platform / Release | `pwsh scripts/ci-local.ps1`. Linux and macOS must still compile: every new surface is `#[cfg(windows)]`. |

## Open Decisions and Questions

- [ ] **Which option?** A (a new elevated OneTerm window, recommended), B (an external
      console window, cheap fallback), C (restart the whole app elevated) or D (an
      elevated helper feeding this window). Owner. **Blocking everything else.** Argued in
      `research/windows-elevation-and-conpty.md` section 3 and proposed in `DEC-0019`.
- [ ] **How the rows are presented**, if A or B: a "Run as administrator" submenu (the
      design's proposal), three extra top-level rows, or a modifier click. Owner. The
      design argues for the submenu; a modifier click is invisible, undiscoverable and
      cannot be exercised by the project's GUI walks.
- [ ] **What the elevated window does when it lands in a different profile** (the
      over-the-shoulder case: no saved sessions, no theme, no layout). Explain it in place
      once, or document it only? Owner. Not blocking the option choice.
- [ ] **Which crate owns the Win32 elevation code** — `crates/core` or `crates/app`.
      Detail design, not the owner.
- [ ] **Should `docs/auto-update.md` forbid updating from an elevated window?** An
      elevated updater can write `C:\Program Files` and can leave files the ordinary
      instance cannot replace. Owner, once A is accepted.

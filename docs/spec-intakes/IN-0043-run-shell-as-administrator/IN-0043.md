# Spec Intake: Run a Windows shell as administrator

ID: IN-0043
Date: 2026-09-21
Type: new_spec
Lane: high_risk

Document number: 43.

## Source

Owner request, 2026-09-21, written in Vietnamese and recorded here in English (this
repository's contributor text is English-only; see `scripts/check-english.py`):

> In the "+" (New Terminal) button, I want the Windows shells to be able to run as
> administrator.

Read out: the dropdown behind the "+" button in the centre tab bar lists the platform's
local shells (`Command Prompt`, `PowerShell`, `PowerShell 7` on Windows —
`crates/terminal-view/src/panel/terminal_panel.rs:697-703`). The owner wants a way, from
that same menu, to start one of them elevated.

The request does not say *where* the elevated shell should appear, and Windows does not
allow the obvious answer. That gap is what this intake resolves before any code.

## Requested Outcome

A user can start an elevated Windows shell from the "+" menu, and can always tell whether
what they are typing into is elevated.

**Lane: high_risk.** Starting an elevated process is an external effect and a security
boundary: it crosses an integrity level, it goes through the UAC consent service, and
whatever the elevated process then reads or executes runs with an administrator token.
Under `docs/HARNESS.md` this means the owning decision and at least one detail design must
exist before any work packet.

**Unblocked 2026-09-21.** Four shapes were possible and they differ in cost by an order of
magnitude; the owner picked **option A with mitigations M1-M7**. See
`docs/decisions/DEC-0019-elevated-shells-open-in-an-elevated-window.md` (status: Accepted)
and the high-risk lane's detail design,
`low-level-design/elevated-instance.md`.

## Project Impact

- **Surfaces.** The "+" menu (`crates/terminal-view/src/panel/terminal_panel.rs:681-767`).
  Under the recommended option also the window's identity: the OS title
  (`crates/app/src/window.rs:66`), the in-app title bar
  (`crates/workspace/src/layout/workspace/mod.rs:262`) and a per-window marker.
- **Process model.** OneTerm gains a second kind of process. It has **no command line**
  today (`crates/app/src/lib.rs:32-125` never reads `std::env::args`) and **no
  single-instance guard** (no `CreateMutex`, no named pipe, nothing) — both would be new,
  and the second is a security-relevant rule, not a convenience.
- **Contracts.** `docs/gui-layout.md:104` describes the "+" menu top to bottom;
  `docs/terminal-backend.md` sections 6.1 and 6.2 describe local shell resolution and the
  ConPTY spawn. Both gain paragraphs; neither is redefined. `docs/auto-update.md` and
  `docs/crash-reporting.md` each describe behaviour that changes meaning under elevation
  and need a sentence.
- **Users.** Windows users only. Nothing existing changes for anyone who does not use the
  new rows; the non-Windows menu is untouched.
- **Systems.** One new external effect (`ShellExecuteExW` with the `runas` verb), one new
  `windows-sys` feature (`Win32_UI_Shell`; `Cargo.toml:125-135` does not have it). No new
  dependency, no new persisted document, no schema change.

## Candidate Work Packets

The owner accepted **option A with mitigations M1-M7** on 2026-09-21
(`docs/decisions/DEC-0019-elevated-shells-open-in-an-elevated-window.md`), and the
high-risk lane's detail design is written
(`low-level-design/elevated-instance.md`). Three packets, in dependency order.

- [x] `US-0130` — **The elevated launch and the command line.** The `ShellExecuteExW`
      `runas` call on `current_exe()` with an explicit `lpDirectory`, the new
      `WorkspaceCommands` fn pointer that carries a `ShellKind` value and never a path, the
      error map (UAC declined = silent no-op, everything else = one notification), the
      `--elevated-shell cmd|powershell|pwsh` parser with its "anything else = one message
      and exit" rule, and the trusted shell-path resolution that never consults `PATH`,
      `COMSPEC` or user configuration (M3). Records M6, the rule that an elevation request
      is never forwarded to another instance. **No dependencies.** Independently
      acceptable: launching `oneterm.exe` by hand with and without the argument, and
      clicking a temporary debug entry point, exercises all of it.
- [x] `US-0131` — **The elevated instance mode.** The `GetTokenInformation(TokenElevation)`
      query and the M5 marker it feeds (OS title, in-app title bar, title-bar border), the
      M1 local-shells-only UI (no SSH Sessions panel, no SFTP, no Quick Connect / New Saved
      Session rows, no Agent panel, right dock absent with its toggles), the M2 updater
      shutdown and its one-line About text, the M4 read-only configuration matrix, and the
      M7 `crashes/elevated/` store with the crash dialog suppressed. **Depends on
      `US-0130`** for the flag that says which shell to open and for the launch that
      produces an elevated process to look at. Independently acceptable: it is verified by
      looking at the window and by hashing five configuration files before and after.
- [x] `US-0132` — **The "+" menu rows and the documentation.** One "Run as administrator"
      entry per Windows shell, placed **without reordering the owner-fixed rows below
      them** (`docs/gui-layout.md:104`, settled during `US-0094` acceptance) — either rows
      under a labelled separator or a `Run as administrator >` submenu, whichever reads
      better once the rows exist; the `FIXED_ROWS` bump (`terminal_panel.rs:763`) so the
      scroll estimate stays honest; and the paragraphs in `docs/gui-layout.md`,
      `docs/terminal-backend.md`, `docs/auto-update.md` and `docs/crash-reporting.md` plus
      the user-facing note that says what the elevated window does and does not have.
      **Depends on `US-0131`**, because the rows must already be suppressible in an
      elevated window before they are shown in a normal one.

Options B, C and D are not packeted. B stays named in `DEC-0019` as the fallback if A's
cost is ever judged too high; C ("Restart as administrator") destroys every open tab and
live connection for less benefit than A; D (an elevated helper feeding a ConPTY into this
window) creates a standing elevation service this project would own. All three are argued
in full in `research/windows-elevation-and-conpty.md` section 3.

## Architecture and Boundary Questions

- **Runtime and owning boundary.** The menu is built in `crates/terminal-view`; launching
  a process is an external effect a feature crate must not perform directly. The two meet
  at `oneterm_state::commands::WorkspaceCommands`
  (`crates/state/src/commands.rs:38-70`), the fn-pointer registry `IN-0033` established
  and the composition root installs (`crates/app/src/init.rs:62-80`). **Open:** which
  crate owns the `ShellExecuteExW` call and the `is_elevated()` token query —
  `crates/core` (gpui-free, already carries Windows FFI) or `crates/app` (already owns the
  process-level concerns: crash handling, the Ctrl handler at
  `crates/app/src/lib.rs:78-93`, the allocator). R1-R12 permit either; the detail design
  decides.
- **Data ownership and lifecycle.** No new persisted document. Under option A the two
  processes share the config directory **only when the elevated token belongs to the same
  account**: `config_dir()` derives from `USERPROFILE`
  (`crates/core/src/config/shell.rs:91-96`, `:109-124`). Over-the-shoulder elevation (a
  standard user typing an administrator's credentials) gives the elevated instance a
  *different* `~/.OneTerm` — no saved sessions, no theme, no dock layout, its own crash
  store.
- **Auth, security, privacy, or audit.** The whole point of the lane.
  1. The UAC prompt is a real consent step, and declining is the normal case.
  2. An elevated OneTerm runs *everything* elevated: `russh` network code, SFTP transfers,
     key and `known_hosts` handling, config writes.
  3. `terminal.json` holds `LocalShellConfig::program` and `args`
     (`crates/core/src/config/shell.rs:68-81`) — a file the **unelevated** process can
     write that names an executable the **elevated** process would run. The rule "nothing
     the unelevated process writes may direct what the elevated process executes" must be
     defended in the detail design, not assumed.
  4. No channel is opened from the medium-integrity process into the elevated one. That is
     option D's attack surface and it stays out.
- **External systems and side effects.** One: `ShellExecuteExW` with `runas`, which hands
  the request to the AppInfo service and shows the consent UI on the secure desktop. The
  elevated process's own effects (PTY spawn, SSH, updater, crash store) are the existing
  ones under a different token.
- **Public interfaces and compatibility.** One field added to `WorkspaceCommands`, a
  struct built only at the composition root and in test doubles. A command line where
  there was none — new public surface for the binary, and the first thing a future
  single-instance feature will collide with. No persisted format and no action-name
  changes.
- **UIPI regressions inside an elevated window.** `crates/sftp-ui/src/render.rs:436-451`
  accepts `ExternalPaths` drops to upload files. Explorer runs at medium integrity, and
  UIPI forbids a drop onto a high-integrity window, so drag-and-drop upload does not work
  in the elevated window. Inherent to elevation, must be documented, cannot be fixed.

## Open Decisions and Questions

- [x] **Which option?** **A**, with mitigations M1-M7, owner, 2026-09-21. Argued in
      `research/windows-elevation-and-conpty.md` section 3, recorded in `DEC-0019`.
- [x] **Should the updater refuse to run from an elevated window?** Yes — M2: the elevated
      instance never checks, downloads or installs updates, and its About/Updates surface
      says so.
- [x] **What the elevated window does when it lands in a different profile** (the
      over-the-shoulder case). It starts on the defaults and **says so once**; under M4 it
      writes nothing into that other profile.
- [x] **Which crate owns the Win32 elevation code.** Split, by what each half needs: the
      enum, the parser, the trusted-path resolution and the process globals in
      `crates/core` (pure `std`, the one crate everyone can name); the token query, the
      `ShellExecuteExW` call and the fatal message box in `crates/app` (the composition
      root, and already the only non-VT crate with a `windows-sys` dependency). Detail
      design, `low-level-design/elevated-instance.md` section 2.
- [x] **How the rows are presented.** Settled in `US-0132`, owner ruling 2026-09-21: **one
      `Run as administrator ›` submenu row**, placed directly after the Windows shell rows
      and before the "SSH Sessions" separator, listing the three shells. Windows only
      (`#[cfg(windows)]`). Three top-level rows were the alternative and were rejected for
      doubling the menu's shell block for a case that is not the everyday one; one row also
      keeps the owner-fixed order below the shells untouched by construction rather than by
      care. A modifier click stays rejected: invisible, undiscoverable, it would make "open
      a shell" and "open an elevated shell" the same hit target, and it cannot be exercised
      by this project's GUI walks. Built menu:
      `evidence/US-0132-plus-menu-run-as-admin.png`.
- [ ] **Must a pwsh installed outside `%ProgramFiles%\PowerShell` be elevatable?** The
      detail design resolves pwsh under `%ProgramFiles%` only and does not read
      `HKLM\...\PowerShellCore\InstalledVersions\<GUID>\InstallLocation`, because that
      value can point at a user-writable directory — the exact hole M3 closes. Cost: such
      an install shows one message and exits after the consent prompt. Owner, not blocking:
      it changes a failure message, not the design.

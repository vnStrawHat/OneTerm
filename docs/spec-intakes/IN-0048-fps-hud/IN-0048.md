# Spec Intake: FPS HUD

Type: new_spec
Lane: normal

Document number: 48.

## Source

Owner request, 2026-09-29: "I also want a function to show FPS when needed. Default off.
Displayed information: max fps, frame, p95, drop, GPU name, GPU % usage", pointing at GPUI
Kit's `crates/fps` (published as `gpui-fps` 0.7.0; the pinned copy under
`reference/gpui-kit/crates/fps/` is byte-identical to the crates.io package once line endings
are normalised, checked 2026-09-29). Owner addition the same day: the HUD also shows the
**graphics API** in use, read at runtime where it can be, otherwise the compile-time backend
name, said so.

## Requested Outcome

A performance overlay, off by default, that the user switches on when needed (settings switch,
app-menu entry, rebindable action). While on it shows, in a window corner: the maximum frame
rate the window could sustain, the frame cost (mean and p95), the share of dropped frames,
this process' GPU usage, the GPU's name and the graphics API. While off it costs nothing at
run time: no timer, no frame trace, no sampler.

## Project Impact

- Surface: a new overlay on the main window (`OneTermWorkspace` root), a switch on the
  Settings **General** page (Interface group), an item in the app menu, a row in
  Settings > Key Bindings (App Menu group, unbound).
- Persisted data: one new optional field `show_fps` in `ui_config.json` (absent = `false`;
  no schema-version bump, old files load unchanged).
- New dependency: `gpui-fps` 0.7 (Apache-2.0), the GPUI Kit 0.7 family's HUD crate. It turns on
  `gpui-pre`'s `profiler` feature for the whole graph (Cargo feature unification), which adds
  gpui's always-on foreground journal; its cost is measured in `US-0151`.
- Owning docs: `docs/gui-layout.md` (overlay + settings page), `docs/agents/persistence.md`
  (`ui_config.json` row), `docs/agents/dependencies.md` (§1 family table).

Follow-up candidates (not created):

- Direct3D feature level at run time. gpui-pre-windows 0.3.7 creates the device with
  `D3D11CreateDevice` asking for 11.1, 11.0, 10.1 and only **logs** which one it got
  (`directx_devices.rs`, `Created device with Direct3D 11.x feature level.`); the device is
  `pub(crate)`, so OneTerm can read neither. Showing it needs a gpui accessor upstream, or a
  second probe device, which would be a guess about gpui's adapter choice.
- Frame count. The kit HUD has no running frame counter; its `FPS` headline (right-click)
  and `INTERVAL` row cover "how often it drew".

## Architecture and Boundary Questions

- Runtime and owning boundary: `oneterm-workspace` (shell) renders the overlay at its root;
  the flag lives in `oneterm-settings`' `UiConfig`; the action in `oneterm-actions`.
- Data ownership and lifecycle: the flag is persisted in `ui_config.json`. The kit monitor
  entity is created on the first frame the HUD is shown and dropped on the first frame it is
  hidden.
- Auth, security, privacy, or audit: none; only this process is measured.
- External systems and side effects: PDH counter query (Windows), `/proc/self/fdinfo`
  (Linux), IO registry (macOS), all inside `gpui-fps`, all only while the HUD is shown.
- Public interfaces and compatibility: a new optional JSON field; old files load.

# Spec Intake: Master password vault and idle lock

ID: IN-0050
Date: 2026-10-09
Type: new_spec
Lane: high-risk (secrets, encryption at rest, persisted schema, a rule that reverses `DEC-0001`)

Document number: 50.

## Source

Owner request, 2026-10-09 (translated from Vietnamese):

1. Introduce a **master password**. It is never stored anywhere; only the user knows it. It
   encrypts sensitive data before that data is written to a persistence file, for example the
   login password of an SSH session.
2. When the user creates an SSH session and wants to save its password too, the master password
   must be initialised first; only then may the save happen. If it is already initialised, it is
   used to encrypt the data.
3. Once a master password is initialised, **screen protection** is on: after a period with no
   user interaction, an overlay covers the whole UI and asks for the master password to unlock.

This intake records the facts, the threat model, a recommended design and candidate packets.
**No packet file is created and no code is written until the owner rules on the open questions
below.** The design is in [`high-level-design.md`](high-level-design.md) and four detail designs
under [`low-level-design/`](low-level-design/), which the high-risk lane requires.

### Facts this intake rests on (verified 2026-10-09 against main @b1be967b)

- **No secret is persisted today, by rule.** `docs/decisions/0001-ssh-key-secret-persistence.md`
  (accepted 2026-08-11) forbids writing passwords and passphrases to any OneTerm document, and
  says a credential vault "must be designed as a new capability rather than silently changing
  this persistence rule". `docs/PROJECT.md` repeats it as an invariant ("No secrets are
  persisted"), and `docs/ssh-authentication.md` lists "integrating a credential vault" as a
  non-goal. This intake is that new capability; it amends all three (see Decision candidates).
- `SshAuthPreference::Password` means "ask for an optional password when connecting"
  (`crates/session-ui/src/session_state.rs:59`). The session dialog renders the auth form
  without any secret field (`auth_form.render(false, cx)`, `session_dialog.rs:588`); only the
  connect dialog collects a password (`auth_form.rs:224` `take_auth`), wraps it in
  `oneterm_core::SecretString` (zeroizing, `Debug` prints `***`) and drops it with the dialog.
- Sessions persist to `ssh_session.json` (`config_dir()`: `target/` in debug, `~/.OneTerm/` in
  release), schema v2. `SshSession` has no `deny_unknown_fields`, so unknown fields are ignored
  on load. `migrate_json_value` rejects a document whose `schema_version` is newer than the
  binary's (`crates/core/src/schema.rs`), and `SshSessionStore::load_from` then **quarantines the
  file and starts empty**. So a schema bump would make an older OneTerm hide every saved session;
  an additive optional field does not.
- `atomic_write` copies the previous content to `<name>.bak` (`path.with_extension("bak")`, so
  `ssh_session.bak`) before replacing the file (`crates/core/src/persistence.rs:73-103`);
  `update_json_file` treats a missing file as `{}` under the same inter-process lock.
- No keyring, DPAPI, Keychain or Secret Service is used by OneTerm. (`oo7`, a Secret Service
  client, is in `Cargo.lock` only through `gpui-pre-linux`.)
- **The crypto crates are already in the graph** (read from `Cargo.lock` `dependencies` blocks):
  `argon2 0.6.0` via `russh 0.63.3 -> ssh-key 0.7.0-rc.11 -> argon2`; `aes-gcm 0.11.1` via
  `ssh-key -> ssh-cipher 0.3.0 -> aes-gcm` (with `aes 0.9.1`, `ghash`, `aead 0.6.1` and the
  `zeroize` feature already on); `getrandom 0.4.3` via `crypto-common 0.2.2`; `zeroize 1.9` and
  `base64 0.22` are workspace dependencies already (`oneterm-core`, `oneterm-terminal`);
  `rand 0.10` is the workspace `rand` (not 0.9). `hkdf` (0.12.4 via `elliptic-curve`, 0.13.0 via
  `oo7` on Linux), `scrypt 0.12`, `pbkdf2` and `ring` are present too. `chacha20poly1305` is
  **not**.
- Windows: two kinds of window, the main window (`crates/app/src/window.rs`, `Root` over
  `OneTermWorkspace`) and the single Settings window (`crates/settings-ui/src/window.rs`, `Root`
  over `SettingsPanel`). Both are `gpui_component::Root`, which since GPUI Kit 0.7 is
  `gpui_base::Root` plus registered `RootPlugin`s. The elevated instance (`IN-0043`, `DEC-0019`)
  is a separate process with one main window; it is local-shells-only (M1) and writes no
  configuration (M4); the switch is `oneterm_core::elevation::is_restricted()`
  (`crates/core/src/config/elevation.rs:435`).
- Input hooks: gpui's `App::intercept_keystrokes` sees every keystroke in every window before
  any action or key handler; `App::observe_keystrokes` does **not** see keystrokes consumed by a
  raw key handler, which is how the terminal takes typed text, so it cannot be the activity
  signal (`gpui-pre 0.3.7` `src/app.rs:2295-2345`). Nothing in OneTerm tracks user activity
  today; `oneterm_state::until_next_tick` is a repaint grid and not relevant here.

## Requested Outcome

A user can set a master password, save SSH passwords encrypted under it, connect with them
after typing the master password once per unlock, and leave OneTerm unattended knowing that,
after the idle timeout, every OneTerm window shows only a lock screen until the master password
is typed again. Nothing that would let someone recover a saved password without the master
password is ever written.

## Threat Model

**Protects against (data at rest):**

- A copy of `~/.OneTerm` taken by someone else: a stolen laptop disk, a backup, a sync folder
  (OneDrive, Dropbox, a dotfiles repository), a support bundle, an image of a VM. Without the
  master password an attacker has only an offline guessing attack against Argon2id with
  per-vault salt (cost per guess about 64 MiB and a few hundred milliseconds).
- Another local user, or an administrator browsing files, who can read the folder but does not
  know the master password. (On Windows the profile ACL already stops ordinary users; on Unix the
  files are created with the umask, see the persistence LLD.)
- A file edited by someone who can write the folder but not read OneTerm's memory: a tampered
  envelope fails authentication, and a sealed password is bound to the host, port and user it
  was saved for, so re-pointing a session's `host` at another server does not make OneTerm send
  the password there.

**Protects against (unattended running app):**

- A passer-by at an unlocked desktop while OneTerm sits idle: after the timeout no terminal
  content, host name, notification or dialog is drawn, input does not reach any session, and the
  in-memory key is dropped.

**Does NOT protect against, and the UI must not claim to:**

- Anyone using OneTerm while it is unlocked: they can connect with saved passwords (they cannot
  read them in plain text from the UI, but they can use them).
- Malware running as the user: a keylogger captures the master password, a debugger or memory
  dump reads the unlocked key or a decrypted password, and a process with the user's rights can
  inject input or replace `oneterm.exe`.
- Shell processes keep running behind the lock; their own effects (writing files, OSC 52
  clipboard writes from a remote program) continue.
- The process being killed and restarted: the lock protects a running UI and the stored secrets,
  it is **not** an application-launch gate (owner question Q1). A restarted OneTerm has no
  sessions and no key in memory.
- Swap or hibernation files holding key material (no `VirtualLock` / `mlock` in scope).
- A weak master password. The KDF slows guessing; it does not make `password1` safe.
- Forgetting the master password. There is no recovery: reset deletes every saved password.

## Security Analysis (summary; details in the LLDs)

1. **Crypto suite:** Argon2id (v1.3, 64 MiB, 3 passes, 1 lane, 16-byte salt, parameters stored
   and raisable) derives a key-encryption key; a random 256-bit data key is wrapped with
   AES-256-GCM; every item is AES-256-GCM under the data key with a random 96-bit nonce and
   associated data binding the vault id, the purpose and the item's context. The GCM tag of the
   wrapped key is the password verifier: no known plaintext, no hash of the password, nothing
   else is stored. `crypto-and-format.md`.
2. **No new crypto dependency.** XChaCha20-Poly1305 would need the `chacha20poly1305` crate; the
   nonce budget of random-nonce GCM (2^32 messages per key) is many orders above what a session
   list will ever use.
3. **Versioned envelope** `otv1:<base64>`; an unknown version is kept untouched and never
   treated as plaintext. A plaintext value in `sealed_password` is rejected, never used.
4. **Memory:** the master password is copied into `SecretString`; keys live in zeroizing types;
   no `Debug`, no `Display`, no logging of any secret or envelope. The gpui `InputState` text is
   not zeroizable; the input is cleared and dropped after use (documented limit).
5. **Brute force at the UI:** each attempt costs one Argon2id run; after 5 consecutive failures
   an in-memory back-off (2, 4, 8 ... capped at 30 s) applies. Never a permanent lockout, never
   an automatic wipe.
6. **Data loss:** forgetting the master password loses every saved password, by design; reset
   is explicit, confirmed, and destroys only sealed values, never sessions.
7. **`.bak` copies:** changing the master password, removing a saved password and reset scrub
   the one-generation backups so an old wrapped key or ciphertext does not linger.
8. **Elevated instance:** never writes `vault.json` (M4); reads it to apply the idle lock with
   the same master password (recommended, Q5); has no SSH surface (M1), so it never decrypts.
9. **Lock bypass by file:** a passer-by can start a second OneTerm, reset from its Settings page
   and set up a password of their own. The lock screen therefore verifies only against the
   vault header held in memory, never a fresh read of `vault.json` (`idle-lock-overlay.md`).
10. **Screen leak:** while locked, the lock plugin replaces the window's whole element tree, so the
   workspace is not laid out or painted at all (no pixels, no accessibility nodes), not merely
   hidden behind an opaque layer. The OS window title is already static (`OneTerm` or
   `OneTerm (Administrator)`).

## Architecture and Boundary Questions

- Runtime and owning boundary: crypto and the header file in `oneterm-vault` (L1); the runtime
  phase and the dialogs in `oneterm-state` (L2); the lock screen and idle clock in
  `oneterm-workspace`; the session field in `oneterm-session-ui`.
- Data ownership and lifecycle: `vault.json` is owned by `oneterm-vault`; each sealed value is
  owned by the document that holds it (`ssh_session.json` by `oneterm-session-ui`). The data key
  lives in memory only while unlocked.
- Auth, security, privacy, or audit: see Threat Model and Security Analysis. No audit log.
- External systems and side effects: none beyond files in `config_dir()`. No network, no OS
  keychain.
- Public interfaces and compatibility: two persisted formats become contracts (`vault.json`
  schema 1 and the `otv1:` envelope). Older binaries ignore both and drop `sealed_password` on
  their next write (documented loss, sessions kept). No `oneterm-vt` API change.

## Open Decisions and Questions

- [x] **Q1 (owner): lock at startup?** Recommended **no**: OneTerm starts with its UI open and
  the vault locked (key not in memory); the first use of a saved password asks for the master
  password; the idle timeout covers the screen. A launch gate adds a prompt to every start and
  buys nothing, because a forgotten password must still be resettable from somewhere. **Ruled 2026-10-09: as recommended.**
- [x] **Q2 (owner): timeout default and range.** Recommended 15 minutes, 1-480, no "Never" (the
  request says protection is on once a master password exists). Alternative: allow Off. **Ruled 2026-10-09: as recommended.**
- [x] **Q3 (owner): bind a saved password to host, port and user?** Recommended **yes** (a
  tampered `host` cannot redirect the password). Cost: editing those fields while locked asks
  to unlock or remove the saved password. **Ruled 2026-10-09: as recommended.**
- [x] **Q4 (owner): connect UX.** Recommended for `US-0158`: the connect dialog still opens,
  shows "Using saved password", and Enter connects. One-click connect without the dialog is a
  follow-up. **Ruled 2026-10-09: as recommended.**
- [x] **Q5 (owner): the elevated window.** Recommended: it reads `vault.json` and applies the idle
  lock with the same master password, cannot set up, change or reset (M4). Under over-the-shoulder
  elevation the administrator's profile has no vault, so no lock. Alternative: no lock there. **Ruled 2026-10-09: as recommended.**
- [x] **Q6 (owner): quit while locked.** Recommended **allowed** (window close, Alt+F4, the
  lock screen's Quit button). Ending the processes reveals nothing. **Ruled 2026-10-09: as recommended.**
- [x] **Q7 (owner): where reset lives.** Recommended: Settings > Security only, with typed
  confirmation, available while locked (a forgotten password cannot be proved). **Not** on the

- [x] **Q8 (owner): master password policy.** Recommended: minimum 8 characters, entered twice,

- [x] **Q9 (owner): new crate or a module in `oneterm-core`.** Recommended new crate
  `oneterm-vault` (HLD); the module is a viable fallback that saves the crate plumbing. **Ruled 2026-10-09: as recommended.**
- [x] **Q10 (owner): OS keychain / DPAPI as an extra layer.** Recommended not now (the request is
  a password only the user knows); could wrap the data key a second time later. **Ruled 2026-10-09: as recommended.**
- [ ] **Q11 (verification, not owner):** Argon2id default cost on the owner's machine; whether
  replacing the surface in `RootPlugin::decorate` keeps gpui focus, IME and TitleBar drag

## Decision Candidates (DEC-0021 created 2026-10-09)

Proposed as one record, `DEC-0021`, with three rules; the owner may split it into three
records. Text for the record's Decision section:

> **DEC-0021 Secrets at rest are sealed by a master-password vault**
>
> 1. **Crypto suite and format.** A secret OneTerm persists is sealed, never stored in plain
>    text. The master password derives a key-encryption key with Argon2id (version 0x13;
>    parameters and a 16-byte random salt stored in `vault.json`; defaults 64 MiB, 3 passes,
>    1 lane; parameters may be raised, never lowered below 19 MiB / 2 passes). The key-encryption
>    key wraps a random 256-bit data key with AES-256-GCM; items are AES-256-GCM under the data
>    key with a fresh random 96-bit nonce and associated data binding the vault id, the purpose
>    and the item's context. Every persisted ciphertext is an envelope string beginning with a
>    version tag (`otv1:`); a reader that does not know the version keeps the value untouched
>    and never treats it as plain text. A new suite or layout is a new version tag, migrated
>    item by item while unlocked. The master password, a hash of it, the key-encryption key and
>    the data key are never written anywhere.
> 2. **Forgot means wipe.** There is no recovery path, escrow, hint or backdoor. Reset removes
>    `vault.json` and every sealed value, and nothing else; it is explicit, confirmed, and never
>    automatic (no wipe after failed attempts).
> 3. **Location and ownership.** The vault header lives in its own document,
>    `config_dir()/vault.json`, owned by `oneterm-vault`, never quarantined automatically, and
>    written only by a non-elevated process. Each sealed value lives in the document of the
>    data it belongs to (today `ssh_session.json`'s `sealed_password`), owned by that
>    document's owner. Only `oneterm-vault` depends on the crypto crates.
>
> Supersedes `DEC-0001` in part: passwords may be persisted when sealed under rule 1;
> passphrases and key contents stay forbidden until a packet adds a purpose for them.

Alternatives to record: OS keychain / DPAPI (not a password only the user knows; platform
divergence); XChaCha20-Poly1305 (new dependency, no need at this volume); PBKDF2 (not memory
hard); scrypt (acceptable, but Argon2id is the current recommendation and already in the lock);
one key directly from the password with no data key (change password would rewrite every
document and two files could disagree after a crash); a separate known-plaintext verifier
(redundant with the wrap's tag).

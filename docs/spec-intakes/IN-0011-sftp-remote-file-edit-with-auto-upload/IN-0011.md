# Spec Intake: SFTP remote file edit with auto-upload

ID: IN-0011
Date: 2026-08-19
Type: new_spec
Lane: high_risk

## Source

User request (Vietnamese): add an "edit file" capability to the SFTP browser.

1. A setting configures the default file editor; the default follows the OS
   default application.
2. When the user saves the file locally, it is automatically uploaded back to
   the remote host over SFTP.

Clarifications captured in this intake (answered by the user):

- Save detection uses a local file watcher (`notify` crate). On a detected
  change, a dialog asks whether to upload (Yes / No). The dialog offers an
  "always upload without asking again" option scoped to **the file currently
  being edited**, not the whole session.
- If the remote file's modified time changed after the download but before the
  local save is uploaded, warn before overwriting (do not silently overwrite).
- Editing is triggered from the **context menu ("Edit") only**; double-click a
  file stays unchanged.
- The editor setting lives under a **new SFTP settings section**.

## Requested Outcome

From the SFTP browser, the user can open a remote file in an editor, edit it
locally, and have their saves flow back to the remote host — with an explicit,
safe upload confirmation and protection against clobbering concurrent remote
changes. The editor used is configurable (OS default by default, or a custom
command) from a dedicated SFTP settings section.

## Project Impact

Affected surfaces, contracts, and behavior:

- **`crates/settings`** — new `sftp` config group in `terminal.json`
  (`SftpConfig { editor: EditorConfig }`). New serde schema; old files load the
  group from `Default` (OS-default editor), same pattern as `completion` /
  `logging`.
- **`crates/settings-ui`** — new "SFTP" settings page exposing the editor mode
  (OS default vs custom command + arguments).
- **`crates/sftp-ui`** — new edit workflow: a context-menu "Edit" item, a
  download-to-temp step, editor launch, a temp-file watcher, save-driven upload
  prompts, a remote-mtime conflict warning, and edit-session lifecycle/cleanup.
- **`crates/actions`** — one new `SftpEdit` action id for the menu item.
- **`crates/core`** — no `SftpBackend` trait change is required; `stat()` already
  returns `FileEntry.modified` for the conflict check, and `upload()` /
  `download()` reuse the existing `TransferHandle` path. A small local-editor
  launcher helper (OS default + custom command) is the only new logic; its home
  crate is decided in the HLD.
- **New dependencies** — `notify` (temp-file watching) and the **`open` crate**
  (OS-default launcher); both pinned in the root `[workspace.dependencies]`
  (DEC-0004).
- **Docs** — `docs/sftp-browser-design.md` gains an "Edit" row in the file-op
  table (§4.6) and a short edit-workflow section; `docs/PROJECT.md` persistence
  list gains the `sftp` group and the edit-cache temp location.

No change to authentication, host-key policy, the transfer pipeline, the
`RemotePath` contract, or the dock/persistence schema beyond the new config
group.

## Architecture and Boundary Questions

- **Runtime and owning boundary:** the edit workflow is UI-owned
  (`crates/sftp-ui`) because it drives dialogs, the transfer queue, and the
  panel lifecycle. The watcher runs on a background thread/task owned by an
  edit-session registry inside the panel; SFTP I/O stays behind `SftpBackend`.
- **Data ownership and lifecycle:** editing writes remote file **content to
  local disk** (a temp copy). The temp copy lives under a dedicated edit-cache
  directory, is keyed by session + remote path, and is removed when the edit
  session ends (panel/session close, app exit). This is the main new data-at-rest
  concern.
- **Auth, security, privacy, or audit:** launching a **custom editor command**
  is an external process effect. The command is invoked with an explicit argv
  vector (no shell string interpolation) and the temp path passed as an
  argument, to avoid command injection from file names or config. Temp content
  may be sensitive; it is confined and cleaned up.
- **External systems and side effects:** OS default-app launch (`start` /
  `open` / `xdg-open` equivalent), a spawned editor process, and a filesystem
  watcher — all local. Re-upload uses the existing SFTP channel.
- **Public interfaces and compatibility:** additive only. New config group
  (back-compatible via serde defaults), one new action id, one new settings page,
  one new context-menu item.

## Open Decisions and Questions

Resolved during review (2026-08-19), recorded in DEC-0004:

- [x] OS-default launcher uses the **`open` crate** (pinned in the root
  `Cargo.toml`). Custom commands still spawn via `std::process::Command` argv.
- [x] Editor-launcher helper lives in **`crates/core`**
  (`oneterm_core::editor_launcher`), taking an owned `EditorChoice` (no
  `core → settings` dependency).
- [x] The "Edit" action has a **configurable maximum file size, default 1 MB**.
  Files larger than the limit prompt a confirmation before downloading (not a
  hard block); `0` = no limit. The limit lives in the `sftp` config group and is
  editable on the SFTP settings page.

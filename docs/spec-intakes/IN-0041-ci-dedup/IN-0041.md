# Spec Intake: CI runs each check once per platform it needs

ID: IN-0041
Date: 2026-09-16
Type: maintenance
Lane: normal

## Source

Owner review of `.github/workflows/ci.yml` on `main` @ `f315bf5e` (2026-09-16), right after
`BUG-0063` and `BUG-0064` had been merged to unbreak the Linux job. Three findings, all decided
by the owner the same day:

1. Three checks are duplicated across the Linux and the Windows quality job although what they
   exercise is platform-free:
   - `cargo clippy --features oneterm-app/terminal-diagnostics` — its `#[cfg(feature = ...)]`
     sites live in `crates/local-shell/src/event_loop.rs`, `crates/ssh/src/transport.rs` and
     `crates/terminal-view/src/render/`, none of them under a `cfg(windows)` / `cfg(unix)`;
   - `cargo test -p oneterm-vt --features vt-paranoid` — the integrity walk is grid logic, and
     the only platform-conditional code in `oneterm-vt` is `src/pty/`, which
     `cargo test --workspace` already compiles and runs on each platform anyway.
2. The reverse gap: `BUG-0063` showed that `crates/vt/src/pty/unix.rs` is not one platform but
   two. `libc::sigset_t` is a `u32` on macOS and a struct on glibc, so `cfg(unix)` code that
   compiles on macOS can still fail to compile on Linux, and the other way round. The macOS job
   does *compile* that file — `oneterm-local-shell`, which the job tests, depends on
   `oneterm-vt` with `features = ["pty"]` — but it has never **run** `oneterm-vt`'s own test
   targets, because compiling a crate as a dependency does not build its `#[cfg(test)]` modules.
   `pty/unix.rs`'s test module and the `#[cfg(unix)]` arm of `pty/loopback_tests.rs` therefore
   execute on Linux only.
3. Every Rust job repeats the same three setup steps verbatim — read the channel out of
   `rust-toolchain.toml`, `dtolnay/rust-toolchain`, `Swatinem/rust-cache` — six times over. Six
   copies of a pinned-SHA block are six places to forget when a SHA moves.

## Requested Outcome

Every check in `.github/workflows/ci.yml` runs in exactly one job per platform that check
actually needs, and the per-job Rust setup exists once. No check leaves the gate, and
`scripts/ci-local.*` keeps running all of them locally.

## Project Impact

- Surfaces: CI configuration only. No crate, no test, no script, no runtime behaviour.
- Contracts: `AGENTS.md` § 4 promises the local script runs "the same set of checks CI runs" —
  that stays true as a *set*, but CI now spreads the set across jobs and platforms instead of
  repeating parts of it, and § 4 says so.
- Coverage moves, and each move is stated deliberately:
  - `terminal-diagnostics` clippy: Linux + Windows -> Windows (the primary platform).
  - `vt-paranoid`: Linux + Windows -> the `vt-package` job (Linux), the crate-centric job that
    already builds `oneterm-vt` in three feature configurations.
  - `regex`: the Linux quality job -> that same `vt-package` job. Same runner OS, better home.
  - macOS: `cargo test` gains `-p oneterm-vt`, so the engine's own test targets run there for
    the first time. That is new coverage, not moved coverage.
- Generated artifacts: none.

## Candidate Work Packets

- [x] `US-0109` — deduplicate the platform-free checks, close the macOS `cfg(unix)` gap, and

  acceptable — taking a step out of one job without putting it into another *is* a coverage
  regression — so they are one packet, not four.

## Architecture and Boundary Questions

- Runtime and owning boundary: GitHub Actions. Nothing in the workspace reads these files.
- Data ownership and lifecycle: none.
- Auth, security, privacy, or audit: the composite action re-uses the pinned action SHAs
  unchanged. Pinning is the security property and it is preserved verbatim; no new third-party
  action is introduced and no secret is read.
- External systems and side effects: none beyond the runners themselves.
- Public interfaces and compatibility: none. The published-crate gates in `vt-package` keep
  running where they are.

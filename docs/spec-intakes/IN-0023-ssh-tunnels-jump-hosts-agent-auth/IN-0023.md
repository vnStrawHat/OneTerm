# Spec Intake: SSH tunnels, jump hosts, and agent auth

ID: IN-0023
Date: 2026-09-10
Type: new_spec
Lane: high_risk

## Source

Owner request (2026-09-10) after a survey of the SSH connection features that established
SSH clients offer and OneTerm lacks: bring the three features every SSH client is expected
to have to OneTerm.

1. ProxyJump / bastion host.
2. Port forwarding: local, remote, and dynamic (SOCKS).
3. SSH agent authentication, plus agent forwarding.

Not requested and out of scope: `ProxyCommand` (spawning an arbitrary local process),
HTTP/SOCKS proxies on the client side, X11 forwarding, GSSAPI, ControlMaster.

## Requested Outcome

A saved SSH session can name another saved session as its jump host. Connect opens the jump
host first, authenticates there with that session's own method, opens a direct-tcpip channel
through it, and runs the target SSH handshake over that channel. A chain of jump hosts works
the same way, hop by hop. The host-key prompt and every error name the hop they belong to.

A saved SSH session can list port forwards. While the session is connected, every `Local`
forward listens on the local machine and relays each accepted connection to `target:port` on
the remote side; every `Remote` forward asks the server to listen and relays each incoming
connection to a local `target:port`; every `Dynamic` forward is a local SOCKS5 proxy whose
CONNECT requests are relayed through the session. Closing the session closes every listener.

An SSH session can authenticate with the identities held by the local SSH agent (Windows
OpenSSH agent, Pageant, or `$SSH_AUTH_SOCK`), with no key path and no passphrase typed in
OneTerm. A session can additionally forward that agent to the remote host so `ssh` and
`git` there can use the local keys. Agent forwarding is off unless the user turns it on for
that session.

Existing sessions keep their behaviour: every new field defaults to "off" or "none".

## Project Impact

- Surfaces: session dialog and Quick Connect (SSH agent radio, jump host picker, agent
  forwarding switch, port forward list); connect dialog (one credential block per hop);
  host-key confirmation (names the hop); notifications (forward bind failures, refused agent
  forwarding).
- Contracts: `SshConfig` / `SshAuthMethod` in `oneterm-core` (new `Agent` variant, `jump_hops`,
  `port_forwards`, `agent_forwarding`); `ssh_session.json` gains optional fields (schema stays
  v2, additive with serde defaults, same precedent as `auth_method`); `docs/ssh-authentication.md`
  (agent auth leaves "Out of Scope"); `docs/ssh-client-connect.md` (connection route);
  `docs/agents/persistence.md` (new fields); `docs/agents/structure.md` (new files).
- Users: no change until a session opts in.
- Safety (high-risk lane): agent forwarding lets the remote host sign with local keys while
  the session is open; forwards open listening sockets on the local machine and on the remote
  host; jump hosts add a second set of in-memory secrets and a second host key to verify.

## Architecture and Boundary Questions

- Runtime and owning boundary: everything protocol-level stays in `crates/ssh` on the hidden
  tokio runtime (R3/R8); UI crates only build `SshConfig` and call `SessionFactory::connect_ssh`.
  `russh` 0.61 already provides `connect_stream`, `channel_open_direct_tcpip`, `tcpip_forward`,
  `Channel::agent_forward`, the agent client (named pipe, Pageant, `SSH_AUTH_SOCK`), and
  `Signer` for `AgentClient`; no new dependency is needed.
- Data ownership and lifecycle: `russh::client::Handle` is moved into `ssh_main_task` and is
  not `Clone`, so dynamic channel opens (one per accepted local connection) go through a new
  request channel serviced by that task; jump-hop handles move into the same task and are
  dropped after the target in teardown; every listener and relay task shares the session's
  `CancellationToken` (today's `sftp_shutdown`).
- Auth, security, privacy, or audit: no secret is persisted (jump host credentials are typed
  per connect, DEC 0002 applies to every hop); agent forwarding is refused by the handler
  unless enabled for that session; forward listeners bind `127.0.0.1` unless the user types
  another bind address; SOCKS5 is no-auth and loopback-only by default (DEC-0011).
- External systems and side effects: listening sockets on the local machine and on the
  remote host; connections to a local SSH agent.
- Public interfaces and compatibility: `SshConfig` / `SshAuthMethod` (core) change shape —
  internal to the workspace; `ssh_session.json` stays readable by older builds (unknown
  fields are dropped on their next save, acceptable and documented).

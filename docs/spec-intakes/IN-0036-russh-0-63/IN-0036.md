# Spec Intake: Bump the russh family off the release-candidate crypto stack

ID: IN-0036
Date: 2026-09-15
Type: maintenance
Lane: high-risk

## Source

Owner order (2026-09-15), on `main` @ `621e4c9` ("Merge BUG-0057"). `BUG-0057` (IN-0035) fixed
the two yanked crates at lock level and recorded the remaining debt: the whole SSH crypto stack
still sits on RustCrypto **release candidates**, because `russh 0.61.2` pins them.

The rejected alternative #1 in
[`IN-0035/high-level-design.md`](../IN-0035-yanked-russh-crypto-crates/high-level-design.md)
predicted this change's scope: `russh 0.61 -> 0.63.3`, `russh-sftp 2.3 -> 3.0.0`,
`russh-cryptovec 0.61 -> 0.62`, described there as "two semver-major bumps across the SSH auth,
host-key, channel and SFTP APIs that `crates/ssh` and `crates/sftp-ui` call directly". That
prediction is now the requested work.

The `-rc` pins named by the owner:

```text
ssh-key        0.7.0-rc.10
ssh-cipher     0.3.0-rc.9
ecdsa          0.17.0-rc.18
rsa            0.10.0-rc.18
ed25519-dalek  3.0.0-rc.0
pkcs1          0.8.0-rc.4
```

`Cargo.lock` at `621e4c9` carries **16** `-rc` crates in total; the six above are the ones the
owner named.

## Requested Outcome

The SSH stack leaves the release-candidate crypto pins: bump `russh` to `0.63.x` and
`russh-sftp` to `3.0.x` (with `russh-cryptovec` / `russh-util` following transitively), adapt
every OneTerm call site, and keep every existing auth, host-key and forwarding guarantee intact.

**Achievable outcome, measured (see the HLD):** 16 `-rc` crates -> **3**. `ssh-key 0.7.0-rc.11`,
`rsa 0.10.0-rc.18` and `pkcs1 0.8.0-rc.4` stay because **russh 0.63.3 pins all three with an `=`
requirement** (`russh-0.63.3/Cargo.toml:351, 309, 281`), so cargo gives OneTerm no choice: they
move only when russh does. They also happen to be the newest published version of each crate,
their current major line having no stable release yet — but the `=` pin is what settles it.
Neither an upstream gap OneTerm could work around nor a OneTerm choice.

**The stronger reason to take the bump** (added after independent verification): 0.63.3 fixes
**three panics a hostile server could reach** in 0.61.2 — an all-zero-mpint index in the key
exchange, a packet-length underflow in the cipher layer, and an IV-length `clone_from_slice` in
the PKCS#8 parser — and replaces a non-constant-time agent-unlock password comparison with
`subtle::ct_eq`. The first two sit on the inbound path of every connection, before
authentication, on values the remote end chooses. See the HLD's "Remote-crash fixes" table for
each `file:line`.

## Architecture and Boundary Questions

- Runtime and owning boundary: `oneterm-ssh` owns every `russh` / `russh_sftp` call. Its public
  API (`SshSession`, `SftpTask`, `AppError`) is what `oneterm-sftp-ui` and `oneterm-terminal`
  see, and none of it changes. `oneterm-tools`' `sftp-dev-server` is a second, independent
  `russh::server::Handler` implementation and must move with the same API.
- Data ownership and lifecycle: `~/.ssh/known_hosts` is read and appended through
  `russh::keys::known_hosts::*`. That module is **byte-identical** between 0.61.2 and 0.63.3, so
  the on-disk format and the round trip are untouched.
- Auth, security, privacy, or audit: **this is the high-risk core.** `check_server_key` changes
  shape — russh 0.63 gained OpenSSH host-certificate support, so the callback now receives
  `PublicKeyOrCertificate` instead of `PublicKey`. OneTerm has no certificate-authority trust
  store, so the certificate arm must **fail closed**. Separately, server-initiated channel opens
  (agent forwarding, forwarded-tcpip) are no longer auto-confirmed by russh before the handler
  runs: the handler now owns accept/reject.
- External systems and side effects: SSH servers, the local SSH agent, and forwarded TCP
  endpoints. Wire negotiation itself is unchanged — the kex, cipher, MAC and compression
  preference lists are byte-identical between the two releases (proven by diff in the HLD).
- Public interfaces and compatibility: no OneTerm public API changes. Two workspace
  requirements move (`russh`, `russh-sftp`); neither is re-exported.

## Open Decisions and Questions

- [x] **Host certificates: fail closed.** russh 0.63's `Preferred::host_key_certificates` is
  `Cow::Borrowed(&[])` by default, so OneTerm never advertises a `*-cert-v01@openssh.com` host-key
  algorithm and a conforming server therefore never presents a certificate. The
  `PublicKeyOrCertificate::Certificate` arm is unreachable in practice, but it is implemented as
  an explicit refusal rather than a `_ => Ok(true)`. Not a decision record: it is the only
  behaviour consistent with the accepted contract in `docs/ssh-client-connect.md`
  ("an unrecognised host key is refused"), not a new choice future work must inherit.
- [x] **Three `-rc` crates remain.** No alternative exists: `russh 0.63.3` pins `ssh-key`, `rsa`
  and `pkcs1` with `=` requirements, so cargo cannot choose anything else. Reported to the owner,
  not worked around.
- [x] **russh-sftp 3.0's transfer pacing is pinned back to 2.3.0's, not inherited.** Its new
  defaults cut the in-flight write budget 4x and make OneTerm's striped download pull 9.3x the
  file size. Both measured; both overridden in `session::sftp_config()`. Adopting 3.0's pacing
  would be a throughput change to argue on its own evidence, which a dependency bump is not the
  place for.

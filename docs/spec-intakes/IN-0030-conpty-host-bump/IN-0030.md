# Spec Intake: ConPTY host bump mechanism

ID: IN-0030
Date: 2026-09-12
Type: maintenance
Lane: normal

## Source

Owner decision (2026-09-12), after trying the "ship no console host" experiment: *"keep both
files; add a mechanism or script so the version of those two files can be bumped easily."*

The experiment that removed `crates/app/assets/conpty.dll` + `x64/OpenConsole.exe` lives on the
unmerged branch `fix/conpty-inbox` (commit `4c8d510`). It was rejected because the inbox
`conhost.exe` on this machine (10.0.26100.1) swallows the Sixel DCS, so local Windows shells
rendered no images (evidence in that branch's `US-0069` packet). `US-0069` is therefore
**retired**; its Markdown packet exists only on that branch and is not carried onto `main`.

## Requested Outcome

OneTerm keeps bundling the Windows Terminal console host pair, and bumping it becomes a
one-command, verifiable operation instead of a manual copy: a script downloads a chosen
version from an authoritative source, checks it, installs it into `crates/app/assets/`, and
records what it installed in a manifest that the licence notice and CI read back.

## Project Impact

- Surfaces: none. No UI, no runtime code change — `crates/app/build.rs` keeps copying the pair.
- Users: local Windows shells keep Windows Terminal's console host (Sixel passthrough, Ctrl+C
  delivery, `SetConsoleWindowInfo`-style host control) instead of the user's inbox `conhost.exe`.
- Contracts: `THIRD-PARTY-NOTICES.md` §1 becomes generated from the manifest, so the notice
  follows a bump automatically; `scripts/third-party-notices.py --check` (already in CI) now
  also fails when the tracked binaries and the manifest disagree.
- Release: `scripts/build-release.ps1` is unchanged — it stages whatever `build.rs` copied.

## Architecture and Boundary Questions

- Runtime and owning boundary: build-time only. `crates/app/build.rs` already copies the pair
  next to `oneterm.exe` (x86_64 targets only; an aarch64 build falls back to the OS ConPTY),
  and the vendored `alacritty_terminal` `tty/windows/conpty.rs` loads `conpty.dll` from the exe
  directory if present, else `kernel32`. Neither changes.
- Data ownership and lifecycle: the manifest (`crates/app/assets/conpty-manifest.json`) is the
  single record of what is bundled; the binaries themselves stay tracked in git, so any previous
  pair is recoverable with `git checkout <rev> -- crates/app/assets`.
- Auth, security, privacy, or audit: the binaries are redistributed third-party executables. The
  bump script refuses anything whose Authenticode signature is not `Valid` and signed by
  `O=Microsoft Corporation`, and records a SHA-256 per file that CI re-checks on every run.
- External systems and side effects: one HTTPS download from `api.nuget.org`, run by a developer
  on demand. CI never downloads — its check is offline hashing.
- Public interfaces and compatibility: none.

## Open Decisions and Questions

- [x] Source of truth for the pair: the `Microsoft.Windows.Console.ConPTY` NuGet package
      (rationale in the high-level design).
- [x] x64 only: `build.rs` ships the pair for `x86_64` targets only, so the package's `win-x86`
      and `win-arm64` copies are not tracked.
- [x] Rollback path: `git`, not the script. The previously bundled 1.23.251216003 is **not** on
      the NuGet flat container (it was published only as a GitHub release asset of
      microsoft/terminal `v1.23.13503.0`), so `-Version 1.23.251216003` cannot restore it.

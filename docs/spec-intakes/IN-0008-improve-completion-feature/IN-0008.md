# Spec Intake: Improve completion feature

ID: IN-0008
Date: 2026-08-13
Type: change_request
Lane: tiny

## Source

Consolidated user feedback for terminal completion:

1. A displayed whole-line history suggestion must apply correctly after a partially typed later token, including exact displayed casing on Cmd/PowerShell.
2. First Tab selects the first result; second Tab or Enter accepts it. Up/Down and Ctrl+N/Ctrl+P navigate only after explicit selection and otherwise continue to the shell.
3. When the sole result already byte-exactly matches the typed replacement range, the overlay should not appear.

This intake consolidates the former IN-0008, IN-0009, and IN-0010 records into one completion-improvement feature.

## Requested Outcome

Improve completion acceptance and interaction as one coherent feature: suggestions apply from their declared replacement boundary and preserve displayed casing, selection is explicit before completion captures navigation or acceptance, and the overlay is hidden when a sole result has no actionable edit.

## Project Impact

The work is localized to the `oneterm-terminal-view` completion controller and key handling around the existing completion engine. Matching, ranking, catalog/history ownership, redaction, persistence, and settings schema remain unchanged.

- `Suggestion::replace_from` determines the typed range used by suppression and acceptance.
- Unix acceptance remains exact-case and append-only.
- Cmd/PowerShell may emit bounded terminal Backspace bytes from the first case mismatch before writing the displayed suggestion suffix.
- Selection remains per terminal and resets on recompute or dismiss.
- Sole-result suppression is byte-exact so a case-only Windows correction remains visible and actionable.

## Architecture and Boundary Questions

- Runtime and owning boundary: `CompletionController` owns visible results, selection, replacement-range interpretation, and acceptance payloads; `LocalTerminalView::completion_handle_key` decides whether keys mutate completion state or continue to the shell.
- Data ownership and lifecycle: selection remains per-terminal; `GlobalCompletionHistory` remains in-session and process-global.
- Auth, security, privacy, or audit: no change; existing history redaction remains authoritative.
- External systems and side effects: acceptance writes the bounded terminal-edit payload to the existing PTY; forwarded keys use the normal terminal encoder.
- Public interfaces and compatibility: no public API or persisted schema change; user-visible completion behavior changes intentionally.

# Spec Intake: retire OneTerm's striped SFTP download

ID: IN-0037
Date: 2026-09-15
Type: change_request
Lane: normal

## Source

Owner instruction, 2026-09-15: retire OneTerm's own striped SFTP download path in favour of
russh-sftp 3.0's pipelined read-ahead — "option B" as measured during `US-0095`
([`../IN-0036-russh-0-63/low-level-design/upgrade.md`](../IN-0036-russh-0-63/low-level-design/upgrade.md),
Change G). `US-0095` chose option A (keep the striping, set `max_concurrent_reads: 1`) because a
dependency-bump packet had no mandate to rewrite the download path, and left the note *"If
`copy_striped` is ever retired, raise `max_concurrent_reads` in the same change"*. This intake is
that change.

## Requested Outcome

Downloads read the remote file sequentially through one handle and let russh-sftp keep
`max_concurrent_reads` `SSH_FXP_READ` packets on the wire, instead of OneTerm opening up to four
handles and seeking before every chunk. `copy_striped`, `read_handles_for` and `REORDER_WINDOW`
are deleted; `sftp_config()` restores `max_concurrent_reads` to russh-sftp 3.0's default of 16.

Measured on the same 5 MiB loopback download that `US-0095` used, both options serve the file
exactly once (1.00x) in 21 READs; option B keeps ~4.2 MB in flight against striping's ~1.04 MB,
so it wins by roughly the in-flight ratio on any link with real RTT and is marginally faster on
loopback. The deletion is the second half of the win: ~150 lines of hand-rolled re-order buffer,
`JoinSet` lifecycle and multi-handle bookkeeping go away.

## Candidate Work Packets

- [x] `US-0096` — downloads read sequentially through the library's pipelined reader; striping

## Architecture and Boundary Questions

- **Runtime and owning boundary:** unchanged. `sftp_task` owns the transfer; `transfer::pipeline`
  owns the byte loop; `sftp-ui` owns the queue item.
- **Data ownership and lifecycle:** unchanged. Bytes land in a `.part` local sibling and replace
  the target only once complete (`staging::finalize_local_file`).
- **Auth, security, privacy, or audit:** none. No new syscall, no new path, no new credential.
- **External systems and side effects:** the SFTP wire pattern changes — 1 `SSH_FXP_OPEN` instead
  of up to 4, and reads are sequential rather than seek-per-chunk. Both are ordinary SFTP.
- **Public interfaces and compatibility:** none. `pipeline` is `pub(super)`.

## Lane

**Normal, not high-risk.** The data-loss trigger was checked explicitly and does not fire:

- **There is no resume feature to break.** `grep -rni "resume" crates/sftp-ui/src crates/ssh/src`
  returns nothing; a download writes to a fresh `.part` sibling, and a cancelled or failed one
  deletes that sibling (`download::download_file_contents`). Cancellation loses the partial bytes
  today and still loses them after this change. Nothing is appended to and nothing is resumed, so
  no offset arithmetic can corrupt a user's file.
- The destination file is only ever replaced by `finalize_local_file` on success, and that
  function is untouched.
- Upload is untouched.

The risk that does exist is throughput and correctness of the byte loop, both of which are
mechanically testable against the in-process counting server that `US-0095` built.

# Spec Intake: Rebuild terminal-view from scratch on GPUI

ID: IN-0018
Date: 2026-09-08
Type: change_request
Lane: normal

## Source

Owner request (2026-09-08): the `crates/terminal-view` crate is patchy and borrowed from
several sources. Rebuild it from scratch with these goals:

- render with GPUI;
- the terminal render engine is written from scratch, without consulting Zed's terminal view,
  wezterm, or any other terminal renderer;
- box-drawing / block / powerline glyphs are drawn with quads, not font glyphs, and every
  shape is constructed symmetrically about the cell's x and y axes (never accumulated
  left-to-right / top-to-bottom);
- keep every current feature of the crate;
- documentation that only describes the old `terminal-view` internals is not a constraint;
- high performance is a first-class goal.

A first attempt (US-0044 / US-0045, 2026-09-08) was discarded before merge; those packets are
retired and this intake restarts from `main` @ 12b3c11.

## Requested Outcome

A new `oneterm-terminal-view` crate that replaces the old one file-for-file: same public
API for `crates/app` and `crates/session-ui`, same user-visible behavior (tracked by the
parity checklist in the HLD), a new render engine (frame snapshot -> row plans -> GPUI
primitives) with quad-drawn symmetric shapes, and measurable per-frame cost that is not
worse than the old crate on the DOOM-fire full-screen benchmark.

## Project Impact

- Surfaces: terminal panel, tabs, split Spaces, terminal rendering, keyboard/mouse/IME input,
  search, completion overlay, semantic highlight overlay, gutter timestamps, scrollbar,
  context menu, status-bar metrics, agent focus.
- Contracts kept: `TerminalSession` and friends in `crates/terminal` (engine stays
  alacritty-based and is not part of this rewrite), `AppServices` hooks in `crates/state`,
  registered panel name `panel_names::TERMINAL`, `docks.json` layout schema, the `PanelSpec`
  API used by `crates/app` and `crates/session-ui`.
- Docs that describe the old view internals (`docs/terminal-rendering-optimization.md`,
  `docs/terminal-gap-analysis.md`, `docs/terminal-split/`) become historical; the HLD of this
  intake is the new owning contract for the view.

## Architecture and Boundary Questions

- Runtime and owning boundary: view crate only; `crates/terminal` engine API is consumed, not changed (small additive changes allowed if a packet records them).
- Data ownership and lifecycle: the view owns per-terminal UI state; the session entity owns the grid; caches are per view and dropped with it.
- Auth, security, privacy, or audit: paste/OSC/URL policies stay in `crates/terminal`; the view must keep calling them.
- External systems and side effects: none new.
- Public interfaces and compatibility: `lib.rs` exports and `PanelSpec` stay source-compatible for `app` and `session-ui`.

# IN-0046 research: hotpath evaluation

Date: 2026-09-25. Machine: Windows 11 Enterprise 10.0.26200 (the IN-0045 machine). Toolchain
1.96.0. Branch `feat/in-0046-hotpath-profiling` off main `d27f06ca`. Every number below comes
from runs made for this record unless it says "estimate" or "read from code".

Raw reports: [`raw/`](raw/) (hotpath JSON, one file per run). All tables:
[`tables.md`](tables.md), generated by [`hotpath-tables.py`](hotpath-tables.py). Protocol:
[`hotpath-measure.ps1`](hotpath-measure.ps1). Frame-time overhead runs:
[`raw/frame-time.txt`](raw/frame-time.txt).

## 1. The crate

`hotpath` 0.26.1, MIT, <https://github.com/pawurb/hotpath-rs>. Read from its source in the
cargo registry (the README on crates.io is three lines).

| Question | Answer |
| --- | --- |
| Site API | `#[hotpath::measure]` on a fn (sync or async; `impl_type = "T"` names the type, `label = ".."` renames); `hotpath::measure_block!(label, expr)`; `#[hotpath::main(..)]` or `HotpathGuardBuilder` for the guard |
| Zero cost when off | Its own `hotpath` feature switches between `lib_on` and `lib_off`; with it off `measure` expands to the fn unchanged. OneTerm goes further: `cfg_attr`, so without `hotpath-profiling` the dependency is not even in the graph |
| Timing cost per call | Two `quanta` clock reads and a push into a thread-local queue drained by a background thread (`hp-functions`). No channel send per call, no lock |
| Allocation mode | `hotpath-alloc`: a `CountingAllocator<A>` global allocator adds each allocation's size to thread-local counters of the innermost measured frame. **Exclusive** by default (a site's figure excludes nested measured sites; `HOTPATH_ALLOC_CUMULATIVE=1` makes it inclusive). One metric per run: bytes, or count with `HOTPATH_ALLOC_METRIC=count`. Async fns report `N/A` in alloc mode |
| Global allocator | Required for `hotpath-alloc`. `#[hotpath::main(allocator = X)]` emits `#[global_allocator] static: CountingAllocator<X> = CountingAllocator::with(X)`. OneTerm passes `oom::OomResilientAlloc` and compiles its own `GLOBAL_ALLOC` static out under `hotpath-profiling-alloc`, so the OOM ballast and retry loop stay the inner allocator. They coexist; no wrapper code was needed |
| Report | On guard drop: table, `json` or `json-pretty`; stdout or `HOTPATH_OUTPUT_PATH`. `HOTPATH_SHUTDOWN_MS` writes it after a timeout and calls `process::exit(0)`. A killed process writes nothing. Closing OneTerm's window returns from `run()`, which is what the protocol does |
| Extras on by default | A thread sampler (`hp-threads`, per-thread CPU %, every 250 ms) and a live HTTP metrics server on port 6770 (`HOTPATH_METRICS_SERVER_OFF=1`) |
| Not available here | `hotpath-cpu` (sampling CPU profiles) is macOS/Linux only: `compile_error!` on Windows |

## 3. Overhead

**Per site.** `frame_time_under_output` (1 MiB of scrolling output in 4 KiB chunks, one drawn
frame per chunk, `fast-dev` profile, 3 runs each; the test starts a guard when the feature
is on):

| | flood avg | flood p50 | flood p95 | idle avg |
| --- | ---: | ---: | ---: | ---: |
| off (3 runs) | 1576 / 1565 / 1565 us | 1537 / 1536 / 1531 us | 1734 / 1709 / 1782 us | 236 / 257 / 237 us |
| on (3 runs) | 1747 / 1724 / 1775 us | 1673 / 1661 / 1685 us | 2172 / 2092 / 2166 us | 240 / 235 / 242 us |

+11.5 % on the flood frame (+180 us per frame), nothing measurable on an idle frame. The
flood frame runs about 575 measured calls, 520 of them `GlyphCache::shape` hits whose body
takes 82 ns, so the cost is about 0.3 us per measured call. `hotpath` itself is compiled at
opt-level 0 in `fast-dev` (only the listed OneTerm and regex crates are optimized), so this
is an upper bound; the release figure was not measured (§ 7).

**In the release app.** The 300k-line flood took 13 s with main and with the timing build,
twice each (the protocol polls every 2 s, so this only bounds the effect below 15 %).

**Its own threads.** The thread sampler `hp-threads` averaged 9 to 11 % of one core in every
run, on its own thread. It does not inflate the per-function durations, but it must be
subtracted from any process-level CPU figure taken from a profiling build.

**Reading the numbers.** Timing is inclusive: `TerminalElement::prepaint` contains
`PlanCache::update`, which contains `class_rows_into` and `build_row_plan`, which contains
`GlyphCache::shape`; `Pump::advance` contains `Terminal::feed` contains `Parser::advance`
contains `Screen::scroll_up`. Allocation figures are exclusive. Percentages are of the whole
run's wall time, not of CPU time.

Not proposed:

- **`class_rows_into`'s first call** builds the highlight rule set: 23,916 allocations and
  about 2.6 ms, once per process. Moving it off the UI thread saves one frame's worth once.
- **`snapshot_update` / `refill`** (14-26 us per frame), **`Screen::scroll_up`** (109-164 ns,
  no allocation), **`Terminal::feed`'s** fixed per-call part (0.13 us), **`paint`**
  (58-139 us per frame, one allocation per frame): already small.
- Retained memory: none of the above changes what IN-0045 budgets. Rows 1 and 2 cut
  allocation traffic, not the working set.

## 6. What hotpath is good for here

- Good: per-site call counts and averages that explain a load (one feed per line, one row
  allocation per line, two shapes per row), exclusive allocation counts per site, and a
  per-thread CPU table that shows how much of a thread the sites explain. Adding a site is
  one line and costs nothing in a normal build.
- Limits: no sampling CPU profile on Windows, so nothing below or outside a site is visible
  (gpui, DirectWrite, the scheduler); async sites have no allocation figures; one allocation
  metric per run; percentages are of wall time; the report is lost if the process is killed.
  Candidates 3 and 5 need a site added before they can be sized.

## 7. Gaps

- **SFTP load (d) not run.** Driving an SFTP download of 300 files through the GUI is not
  cheap with posted messages (connect dialog, host-key prompt, multi-select, destination),
  and `copy_sequential` is async: allocation mode reports `N/A` for it and its timing is
  mostly I/O wait. The site is in place for a later run.
- **Release-build per-site overhead not measured.** The frame test ran in `fast-dev`, where
  `hotpath` itself is unoptimized; the release app showed no difference at the flood
  protocol's 2 s resolution.
- **Frame counts vary run to run** (window not foreground); totals are not comparable across
  runs, per-call figures are.
- **Candidate gains are estimates** until each packet measures them.
- One run per load for the allocation builds (two for the flood timing); the two timing
  flood runs agree within 3 to 7 % per site (`time-flood-2` is the faster one throughout).

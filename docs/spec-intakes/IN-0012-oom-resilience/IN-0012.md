# Spec Intake: OOM resilience

ID: IN-0012
Date: 2026-08-19
Type: bug
Lane: high_risk

## Source

User report (Vietnamese): running a coding agent inside a OneTerm tab, the
agent's `cargo` build exhausted system RAM and OneTerm exited together with it.
Windows Event Log: exception `0xc0000409` in `oneterm.exe` 0.4.0, no crash
report captured (`~/.OneTerm/crashes/` holds only an empty `.native.tmp`).
The user accepts that 100% survival is impossible and asks for maximum
practical mitigation, plus a reduction of continuous allocation.

## Requested Outcome

When system memory is exhausted by a sibling process (e.g. `rustc` spawned by
a coding agent in a tab), OneTerm survives the spike instead of aborting with
no crash report, and the render hot path stops allocating every frame.

## Project Impact

- Root cause: Windows has no OOM killer — on commit-charge exhaustion every
  allocating process sees NULL, and Rust's infallible-allocation path aborts
  via `__fastfail` (0xc0000409), skipping both the panic hook and the
  `crash-handler` callback (`docs/crash-reporting.md` capture boundary).
- Affected surfaces: process-wide allocation (`crates/app` composition root),
  render snapshot path (`crates/terminal` + `crates/terminal-view`).
- No UI change; no persisted-schema change; no protocol change.

## Architecture and Boundary Questions

- Runtime and owning boundary: global allocator lives in `crates/app`
  (composition root, R-rules keep it out of library crates); snapshot reuse
  lives in `oneterm-terminal` / `oneterm-terminal-view`.
- Data ownership and lifecycle: reusable snapshot buffer is owned by
  `RenderCache` (per-view, lives with the view).
- Auth, security, privacy, or audit: none.
- External systems and side effects: none.
- Public interfaces and compatibility: `TerminalRender` gains a defaulted
  `snapshot_into` method — existing implementors keep compiling.

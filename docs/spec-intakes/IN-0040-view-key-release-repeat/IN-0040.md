# Spec Intake: OneTerm delivers key release and repeat to the engine

ID: IN-0040
Date: 2026-09-16
Type: change_request
Lane: high_risk

Document number: 40

## Source

Owner request, 2026-09-16, on reading `US-0105`'s closing gap:

> File a packet for kitty release/repeat in the view.

The gap it names was recorded by the packet that created it. `US-0105`
([`IN-0039`](../IN-0039-vt-gaps-and-publish/US-0105-kitty-keyboard-encoder.md), "Evidence and
Gaps") states it as a measured fact rather than an assumption:

> **`crates/terminal-view` does not yet deliver release or repeat events**, which was out of scope
> and is confirmed rather than assumed: GPUI *can* supply both -- `gpui::KeyDownEvent` carries
> `is_held` (the repeat) and `gpui::KeyUpEvent` exists -- but `TerminalView` registers only
> `on_key_down`, and `crates/terminal-view/src/input/keys.rs` maps a `Keystroke` to
> `(KeySpec, KeyMods)` with no event kind. So today every event the application delivers is a
> press, `REPORT_EVENT_TYPES` never produces a repeat or release byte in OneTerm itself, and
> `REPORT_ALTERNATE_KEYS` and `REPORT_ASSOCIATED_TEXT` get no platform values either.

and names the follow-up in its own Handoff, item 2:

> `crates/terminal-view` delivering release and repeat events, so OneTerm itself can use
> `REPORT_EVENT_TYPES` -- the engine is ready and the platform has the data.

## Requested Outcome

A program running in an OneTerm terminal that has negotiated the kitty keyboard protocol's
`REPORT_EVENT_TYPES` flag receives the repeat and release events it asked for, because the view
tells the engine which kind of event each key was.

The engine half shipped in `US-0105` and is complete: `oneterm_vt::input::KeyEvent` carries `kind`
(`Press` / `Repeat` / `Release`) and `text`, `encode_key_event` honours them, and a release with no
flag asking for it already returns `None`. The application half is the one line of the chain still
missing. Concretely, after this intake:

| | Today | After |
| --- | --- | --- |
| A key-down | `KeyEvent::new(..)`, kind `Press` by default | kind `Press`, or `Repeat` when GPUI says `is_held` |
| A key-up | not observed at all -- `on_key_up` is never registered | kind `Release`, delivered to the encoder |
| The text a key produced | dropped; `KeyEvent::text` is always `None` | the `Keystroke`'s own `key_char`, on press and repeat |
| `REPORT_EVENT_TYPES` inside OneTerm | negotiated, answered, and never honoured | honoured |
| Everything with no flag pushed | the legacy bytes | **byte-identical**, and that is an acceptance criterion rather than a hope |

## Project Impact

- **Surfaces.** The terminal view's keyboard path, and only it. No screen, setting, persisted file,
  menu or CLI changes. The IME path, the completion overlay, the search bar, zoom, copy/paste and
  scroll chords are untouched, and a release must not re-trigger any of them -- that is the
  packet's first correctness rule, not an afterthought.
- **Contracts.** `oneterm-terminal`'s re-export shim in `crates/terminal/src/lib.rs` gains three
  names (`KeyEvent`, `KeyEventKind`, `encode_key_event`). `oneterm-vt` is **not** touched: no file
  under `crates/vt` changes, which is why this is a separate intake from `IN-0039` rather than a
  fifth packet inside it.
- **Crate graph.** R1-R12 hold unchanged. No crate is added, removed or re-pointed, and no
  dependency is added anywhere: `crates/terminal-view` keeps reaching the encoder through
  `oneterm-terminal`'s existing shim rather than taking a direct `oneterm-vt` edge.
- **Users.** Every OneTerm terminal, because this changes what the input path does with every key.
  The change is designed to be invisible to every program that has not asked for event types, and
  the proof that it is invisible is the packet's central acceptance criterion.
- **Systems.** None. Nothing leaves the process that did not leave it before.
- **Tests.** `crates/terminal-view`'s view tests gain the kind-mapping and byte-identity cases.
  Everything existing keeps passing, including
  `member_input_reaches_the_channel_peers_only`, which is the broadcast test this design has to
  stay compatible with.

## Why this is a `change_request`

`docs/HARNESS.md` offers six input types.

- **not `new_spec`.** The protocol, the encoder, the flag stack and the byte formats are all
  specified and shipped. Nothing here defines new behaviour for a program to rely on that
  `US-0105` did not already define.
- **not `spec_slice`.** `US-0105` ruled the view explicitly **out of its own scope** ("the view is
  untouched by this packet"). An item a spec named as out of scope is not a slice of it.
- **not `maintenance`.** It changes what the application sends on the user's behalf.
- **not `new_initiative`.** No new crate, surface or mission.
- **`change_request`.** An accepted behaviour -- OneTerm sends one byte sequence per key-down and
  nothing on key-up -- is being extended, at the owner's request.

## Why the lane is `high_risk`

The owner asked for a judgement rather than a default. It is `high_risk`, on the
`docs/HARNESS.md` trigger "public APIs, client-visible contracts, or **broad established
behavior**", for three reasons that compound:

1. **It is the input path, and it is the whole application.** Every key in every terminal in every
   Space -- local shell, SSH, every split, every broadcast channel member -- goes through the one
   function this packet changes. The blast radius is not a feature; it is typing. A wrong byte on
   an output path paints a wrong glyph; a wrong byte on the input path runs a command the user did
   not type. There is no smaller failure mode available here.
2. **It changes what every program receives, once a flag is negotiated.** `IN-0039`'s own risk
   note says the same thing about `US-0105` from the engine side; this packet is what makes that
   change actually reach a program running inside OneTerm. Until now the engine's new bytes were
   reachable only by an embedder calling `encode_key_event` directly, and no such embedder exists
   in this repository. After this packet they are what the application sends.
3. **The contract is explicit, and it is the one `IN-0039` amended.** Clause 6 of `oneterm-vt`'s
   semver promise now reads "**the bytes the `input` encoders produce for a given (event, mode
   snapshot) pair** are a contract". This packet does not change the encoder -- it changes which
   `(event, mode snapshot)` pairs the application produces, which is the other half of the same
   sentence and is equally observable to the program on the far end.

Three further reasons it is not `normal`, each an ordinary bug in a lower lane and a stuck keyboard
here: a release delivered for a key whose press the view swallowed, a release never delivered
because the window lost focus mid-chord, and a release delivered for a dead key that the IME
consumed. Each leaves a program believing a key is held that is not, and the recovery is to quit
the program.

Detail (low-level) design is therefore mandatory before `story create`, and the one concern file is
[`low-level-design/input-events.md`](low-level-design/input-events.md).

The counter-argument, recorded because it is not weak: with no kitty flag pushed the bytes are
byte-identical, which is the overwhelmingly common case, and the engine's own frozen-copy harness
already proves the encoder side of that over three million comparisons. If the byte-identity
criterion holds, the realistic blast radius is only programs that opted in. That argument is about
the *expected* outcome; the lane is about the *failure* outcome, and the failure outcome is typing.

Three follow-ups this intake deliberately does not schedule, each recorded in the packet's gaps:

- **`REPORT_ALTERNATE_KEYS` stays unsupplied.** GPUI's `Keystroke` has no shifted or base-layout
  code point, so `KeyEvent::shifted` and `base_layout` stay `None` and the encoder omits their
  sub-fields, which the protocol allows. Closing this means reading the keyboard layout per
  platform, which is its own intake.
- **The modifier keys themselves are unreportable.** Windows turns `VK_SHIFT` and friends into
  `ModifiersChanged`, never a key event, so `REPORT_ALL_KEYS_AS_ESC` cannot deliver a `Super`
  press. The engine states the same ceiling from its side (`NamedKey` cannot name them).
- **Broadcast fan-out re-encodes nothing.** A Space broadcasts the *bytes* the originating pane
  encoded, so a pane whose program negotiated different flags receives the originator's encoding.
  That divergence is pre-existing -- `US-0105` created it for `app_cursor` and the kitty rung
  alike -- and this packet must not widen it, which is why a release is never fanned out. Fixing
  it properly means broadcasting the event and re-encoding per target.

## Architecture and Boundary Questions

- **Runtime and owning boundary.** Unchanged. The encoder stays pure and side-effect-free; the
  view stays the only place that knows about focus, overlays and the IME. The one piece of new
  state is a set of key names whose press was actually sent, owned by `TerminalView` beside the
  focus flag it already keeps, and it exists to make two impossible things impossible rather than
  to model anything.
- **Data ownership and lifecycle.** The held-key set lives for the life of the view, is bounded by
  the number of physically held keys, and is drained on blur. (Not on session close: a dead session has no program left to strand, and draining would mean writing from a `Drop` that has no `App`. `US-0108`'s verification found the original wording claimed a drain that does not exist.) It is never
  persisted, never observed by another crate, and never read by the engine.
- **Auth, security, privacy, audit.** Nothing new. The bytes are the same class of data the input
  path already writes; `report_generated_input` already accounts for every write, and a release
  write goes through the same call.
- **External systems and side effects.** None.
- **Public interfaces and compatibility.** `crates/terminal`'s shim gains three re-exports, which
  is additive. `crates/terminal-view`'s items are all `pub(crate)`, so nothing outside the crate
  can see the `KeyAction` shape change. The observable contract that moves is the byte stream, and
  it moves only when a flag asked.

## Open Decisions and Questions

- [x] **1. Does `Ctrl+C` stay `SIGINT` when a program has pushed `REPORT_ALL_KEYS_AS_ESC`?**
  **Settled by the coordinator at `US-0108`: no**, and widened during its verification.
  `Ctrl+C` is delivered as the encoded key whenever the program negotiated a kitty flag that
  puts a ctrl chord on the `CSI u` rung -- `DISAMBIGUATE_ESC_CODES` as well as
  `REPORT_ALL_KEYS_AS_ESC`. The specification is explicit for the first: "Turning on this flag
  will cause the terminal to report the Esc, alt+key, ctrl+key, ctrl+alt+key, shift+alt+key keys
  using `CSI u` sequences instead of legacy ones", with Enter, Tab and Backspace the only
  exceptions. Gating only on `REPORT_ALL_KEYS_AS_ESC` (finding `F4`) left the view's gate
  narrower than `encode_key_event`'s own rung, which is the one answer that makes the two
  halves disagree about a single key. With no such flag pushed the `KeyAction::Interrupt`
  behaviour is unchanged, and **the broadcast channel always receives
  `BroadcastInput::Interrupt`** whatever the origin negotiated (finding `F2`). `KeyContext`
  gained one `ctrl_c_is_a_key` field for it. The original text is kept below.
 Today
  `KeyAction::Interrupt` calls `send_ctrl_c()` and never reaches the encoder, so a program that
  asked for every key as an escape code still gets a signal. That divergence is **pre-existing**
  and this packet does not create it; the design keeps it and therefore emits no release for
  `Ctrl+C` either, which is at least self-consistent. Changing it is a behaviour change with its
  own risk (`Ctrl+C` is how a user stops a runaway program) and belongs to the owner. Owner; blocks
  nothing.
- [x] **2. Should the IME-versus-`REPORT_ALL_KEYS_AS_ESC` conflict be resolved here?**
  **Settled by the coordinator at `US-0108`: no.** IME ownership of printable keys stays gated on
  `alt_screen` exactly as today; the flags-gated alternative is recorded as a gap in `US-0108`
  and owes its own packet. The original text is kept below.
 On the
  primary screen the view deliberately drops printable keys (`KeyAction::Ignore`) so the IME path
  is the only writer of typed text. A program that pushed `REPORT_ALL_KEYS_AS_ESC` on the primary
  screen therefore gets the IME's text and not the escape codes it asked for. The correct fix is
  to gate that rule on "no flag wants this key" rather than on `alt_screen`, which is a change to
  the classification table and a second outcome. Recorded, not scoped. Owner; blocks nothing --
  every program that negotiates these flags in practice is on the alternate screen.
- [x] **3. Is the held-key set the right instrument, or should the release path re-classify?**
  **Settled by the coordinator at `US-0108`: the set, as the detail design specifies.** Built as
  `Vec<KeySpec>` rather than `HashSet<SharedString>`. `Keystroke::key` is the wrong identity
  altogether (finding `F1`): the Windows backend renames a digit or an OEM punctuation key to
  its shifted glyph while Shift is down, so `Shift+1` presses as `"!"` and releases as `"1"`
  and the raw name strands the key. The set is keyed on the unshifted `KeySpec` that
  `canonical_key` produces, which is also what a blur needs to build the release it owes; a
  `Vec` because `KeySpec` is not `Hash` and a handful of held keys does not need more. The
  original text is kept below.

  The design uses a set of key names whose press was sent, because re-running `classify_key` on
  the key-up cannot see a view state that changed between the press and the release, and cannot
  release anything on blur. The cost is one `HashSet` field. Recorded as a design choice rather
  than a question for the owner; raised here because it is the one place this packet adds state to
  a view whose input path is otherwise pure.

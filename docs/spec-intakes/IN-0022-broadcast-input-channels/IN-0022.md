# Spec Intake: Broadcast input channels

ID: IN-0022
Date: 2026-09-09
Type: new_spec
Lane: normal

## Source

Owner request (2026-09-09), design the "Broadcast input" feature:

- terminal tabs can be grouped into input channels;
- channels have the fixed names A, B, C, D, E;
- channels are independent of each other;
- every member of one channel receives the same input when the user types;
- members of one channel share the same highlight so membership is visible;
- a member can leave its channel, and a channel can be closed.

Owner follow-up (2026-09-09): a tab can hold several Spaces, so "tab" alone does not name
the unit of membership; think it through.

## Requested Outcome

A user with several terminals joins them to channel A. Typing, pasting, and Ctrl+C in any
member reach every member of A. Each member shows the channel letter and colour. "Leave"
removes one member, "Close channel" removes all of them at once. Channels B..E behave the
same way and never interact with A.

The unit of membership is a **Space** (one terminal session), not the tab:

- a tab with one Space is a member exactly as the owner described a tab;
- a split tab can hold members of the same channel (the side-by-side "type once into all
  panes" layout), members of different channels, and non-members (a `htop` or `vim` pane
  that must not receive broadcast input) at the same time;
- tab-wide commands ("join every Space in this tab", "leave with every Space in this tab")
  exist as conveniences over the tab's Spaces, and the tab chip lists every channel present
  in the tab.

See DEC-0009 for the rationale.

## Project Impact

- Surfaces: terminal context menu (new "Input Channel" submenu), tab strip (channel chips),
  Space frame (channel colour), Key Bindings settings page (new bindable actions, unbound by
  default).
- Contracts: no persisted document changes; membership is in-memory like the manual tab title.
- Users: no behaviour change until a Space joins a channel.
- Safety: broadcast sends the same bytes to every member, including passwords typed at a
  prompt; the chip and frame are the only guard, so they must be visible on every member at
  all times, including a tab whose only Space is a member (today such a Space draws no frame).

## Architecture and Boundary Questions

- Runtime and owning boundary: the registry lives in `crates/state` beside `AgentRegistry`;
  `crates/terminal-view` decides *what* to broadcast, the registry only knows *who* is a
  member. `InputChannel` lives in `oneterm-core` because `oneterm-actions` (L1) can only see
  `oneterm-core`.
- Data ownership and lifecycle: `HashMap<EntityId, Member>` keyed by the `TerminalView`
  entity; inserted on join, removed on leave, close, and `TerminalView::shutdown`. A dragged
  tab moves the same `TerminalView` entity into the target Space, so membership follows it
  without extra bookkeeping. A split or duplicated Space starts as a non-member.
- Auth, security, privacy, or audit: typed secrets fan out to every member; the registry logs
  nothing. Terminal logging (`docs/terminal-logging.md`) already redacts per session.
- External systems and side effects: none beyond extra PTY writes.
- Public interfaces and compatibility: new actions in `crates/actions`; no schema change.

## Open Decisions and Questions

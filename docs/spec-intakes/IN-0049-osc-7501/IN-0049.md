### What OSC 7501 is

**The Program Status Protocol.** It was written by Mitchell Hashimoto (Ghostty, Superlogical)
and announced on 2026-10-06. A program reports what it is doing — `idle`, `working`, `done`,
`blocked` on the user, or `error` — so that the terminal can show a current picture of
every program running in it. The name is not ambiguous: every search hit for "OSC 7501"
points to this proposal, and no xterm, vendor or registry use of the number was found. The
OSC 20308 numbering survey (`docs/osc-agent-status.md` § 2.2) also lists no 7501 claim; the
nearest band is mintty's 7700-7799.

Spec revision **0.3, 2026-10-07** (0.1 2026-09-28 initial draft; 0.2 2026-10-06 keyword
clarifications; 0.3 "absent `progress` means indeterminate; programs may send reports
without feature detection"). There is no version number on the wire. Extension is by new
keys, which receivers must ignore when unknown.

### Wire grammar (rev 0.3)

```text
report  = ESC ] 7501 ; body ST          ST = ESC \  or  BEL
body    = pair *( ":" pair )
pair    = key "=" value                 key   = [a-z]+            (<= 16 bytes)
                                        value = [A-Za-z0-9_.,+/=-]*
query   = ESC ] 7501 ; ? ST   ->  reply ESC ] 7501 ; ? ST   (the only bytes a terminal sends)
```

- The value character set excludes `:` and `;`, so nothing is escaped. A conforming body is
  therefore **one** OSC parameter after the number. Malformed pairs are skipped, unknown
  keys are ignored, and when a key repeats the last value wins.
- Keys:

| Key | Value | Notes |
| --- | --- | --- |
| `state` | `idle` `working` `done` `blocked` `error` `clear` | Required. An unknown value drops the whole report. |
| `id` | `/`-separated path, segment `[A-Za-z0-9_.+-]{1,32}`, at most 8 levels and 128 bytes | Absent means the root record. A malformed id drops the report; it does not fall back to the root. A parent need not exist. |
| `kind` | `permission` `question` `auth` | Only meaningful with `blocked`. |
| `progress` | integer 0-100 | Only with `working` or `blocked`. Absent means indeterminate. |
| `app` | `[A-Za-z0-9_.+-]{1,32}` | A stable program name, inherited from the nearest ancestor record. |
| `title` | standard base64 of UTF-8, padding optional, <= 192 bytes decoded (256 encoded) | A short label. |
| `msg` | standard base64 of UTF-8, padding optional, <= 2048 bytes decoded (2732 encoded) | One line of current status. |

- Records: one per id per terminal. Each report **replaces** its record entirely (omitted
  keys are dropped). `clear` removes the addressed record and its subtree; a bare `clear`
  removes every record. Records belong to the terminal, not the screen (the alternate screen
  does not touch them). `RIS` removes all records and `DECSTR` does not.
- Lifetime: no heartbeat, and terminals **MUST NOT** require reports to be re-sent to keep a
  record alive. When the attached process exits, or a new shell prompt begins (OSC 133 `A`),
  the terminal **MUST** drop `working` and `blocked` records and **MAY** drop `idle` ones;
  `done` and `error` persist.
- Limits: the whole sequence is at most 4096 bytes; at most 256 records per terminal (at least
  64 must be supported), with the least recently updated record evicted. A report that breaks
  a limit, carries invalid base64, or decodes to text with a control character is discarded
  whole.
- Detection: `OSC 7501 ; ? ST`, optionally followed by `CSI c`. If the DA1 reply arrives
  first, the protocol is unsupported. This is the same idiom as OSC 20308 § 3.2. A `Pst`
  terminfo capability (`Pst=\E]7501;%p1%s\E\\`) advertises support but is not authoritative.
  Revision 0.3 lets programs send reports without detecting support, but at least Claude
  Code still probes and stays silent when nothing answers (see Emitters).
- Security (normative): refuse a report whose decoded `msg` or `title` contains a control
  character; never treat them as markup; disarm direction overrides and invisible formatting
  characters; say which terminal a displayed record came from; rate-limit anything a record
  causes outside the terminal (notifications, sounds). Records cannot be read back.
- Relationship to other sequences, per the spec: OSC 9;4 cannot express `blocked` or a
  message. A terminal **MAY** map 9;4 onto the root record and **SHOULD** stop doing so once
  a 7501 report arrives. OSC 9 / 99 / 777 are one-shot notifications, and a terminal MAY
  notify when a record changes. OSC 133 marks command boundaries, not program state. OSC 0/2
  titles are unstructured. Earlier attempts (iTerm2's OSC 21337 session status, and an
  OSC 9999 JSON proposal) are cited as presentation-first or JSON-first, which the spec
  rejects.

## Requested Outcome

Decide whether OneTerm supports OSC 7501 and, if so, how. Recommended: OneTerm answers the
support query and shows 7501 records in the Agent Panel next to OSC 20308 cards. The effect:
Claude Code 2.1.295+, pi 1.1.0+ and any other 7501 emitter (local or over SSH) show up as
working / blocked / done **with no agent-side setup**. Today Claude Code sends OneTerm a
probe that goes unanswered, so it reports nothing.

## Project Impact

- **Engine (`oneterm-vt`): no change for the recommended slice.** OSC 7501 is unknown to the
  engine, so its route is `Drop` today: parsed, counted in `FeedStats::unhandled_sequences`,
  discarded. The `OscRoutes` extension point is how OSC 20308 is consumed:
  `route(7501, OscRoute::Forward).large(7501, true)` in `adapter_config`
  (`crates/terminal/src/handle.rs`). This needs no engine change and leaves the public-API
  snapshots untouched. `large` is required because the spec allows 4096-byte sequences and
  the inline OSC bound is 2 KiB. 7501 is above the 2048-entry route bitmap, so it lands in
  the spill list, exactly as 20308 does.
- **One engine gap:** `VtEvent::ScreenCleared` is emitted for `ED 2`, `ED 3` **and** `RIS`
  (`crates/vt/src/terminal/dispatch.rs`), and the spec's "`RIS` clears all records" needs
  `RIS` alone. Closing it is an additive variant (candidate `US-0153`): a public API change,
  so it needs both snapshots, the CHANGELOG, and rustdoc with no work-item citations.
- **Adapter (`oneterm-terminal`):** a new parser and per-session record table beside
  `osc_agent`. `OscRouter` answers the query in byte order (the seam `US-0088` fixed for
  20308) and drops records on OSC 133 `A` and on exit. One new `SessionEvent` variant.
- **Agent Panel (`oneterm-state` `AgentRegistry`, `crates/agent-ui`,
  `crates/terminal-view` `agent_status.rs`):** 7501 records fold into cards. The five
  states map one to one onto the existing `AgentState`. The stale timer must not apply to
  7501 cards.
- **Docs:** `docs/osc-sequences-checklist.md` (Group G rows), `docs/osc-agent-status.md` (a
  "Relationship to OSC 7501" section), `docs/agent-panel-display.md` (7501 cards),
  `docs/terminal-backend.md` (the `OscRouter` row).
- No persistence, no new dependency (`base64` is already used by the 20308 decoder), no
  settings change in the smallest slice.

### Comparison with OSC 20308 (OneTerm's agent channel)

| | OSC 20308 (`docs/osc-agent-status.md`) | OSC 7501 |
| --- | --- | --- |
| Author / status | OneTerm's own proposal; the repository holds demo emitters only (`scripts/agent-status-demo.sh`, `.ps1`) and records no third-party emitter | Cross-vendor proposal by the Ghostty author; shipped by Claude Code and pi; parsed by libghostty-vt |
| Payload | base64 JSON, typed events (`state`, `session`, `heartbeat`, `model`, `tool_call`, `file`, `approval`) | `key=value` pairs; status records only |
| States | working / blocked / idle / done / error | the same five, plus `clear` |
| Identity | `agent` + `seq` dedup per (terminal, agent) | hierarchical `id` records + inherited `app`; replace-on-report, no sequence numbers |
| Liveness | heartbeat + 5 min stale threshold | none; lifetime tied to process exit and OSC 133 `A` |
| Blocked detail | `approval` with prompt, options, risk | `kind` (permission / question / auth) + `msg` |
| Progress | `tool_call.progress` text | `progress` 0-100 on working / blocked |
| Size cap | 8 KiB base64 payload | 4096-byte sequence |
| Detection | `20308;0` -> `20308;0;1;OneTerm;<ver>`, DA1 sentinel | `7501;?` -> `7501;?`, DA1 sentinel |
| Reply surface | version + terminal name | fixed echo, nothing else |

**Verdict: 7501 complements 20308.** It covers 20308's `state` event and nothing else (no
model, context, tools, files, session or approval detail). Within that overlap it has what
20308 lacks: real emitters. It does not supersede 20308's telemetry, but it makes 20308's
`state` event redundant for any agent that speaks 7501. Recommended positioning (owner
question Q3): OneTerm reads both; 20308 is documented as the optional rich extension, and
agents are told to report state over 7501.

### What OneTerm already parses (checklist Group G)

OSC 9 (toast), `9;4` (progress bar, states 0-4), `20308;1` / `20308;0` (agent channel and
query), and `9;7` (deprecated alias) are supported; `99`, `777` and `9;1-3` are not. OSC 133
`A`-`D` is supported, and that is what makes 7501's prompt-start lifetime rule implementable
without a new signal. OSC 7501 is absent and its route is the default `Drop`.

### Security analysis (untrusted bytes, possibly from a remote SSH host)

1. **Bounded parse.** Take the payload only when the engine reports `truncated: false`, the
   sequence is at most 4096 bytes and has exactly one parameter after the number (a second
   `;` is outside the value charset, so drop the report). Keys, values and ids are checked
   against the spec's character classes *before* any decode. The record table is capped
   (proposed: 64 per session, the spec's minimum, least recently updated evicted), so a
   flood costs at most about 64 x 2.5 KiB per session.
2. **Text.** `msg` and `title`: strict standard base64 (padding optional), then UTF-8, then
   **reject the whole report** on any C0, DEL or C1 character. The spec says refuse, so the
   existing `strip_unsafe_chars` (which strips and keeps tab and newline) is not enough on its
   own. Then strip bidi controls (`url_policy::is_bidi_control`) and invisible formatting
   characters (U+200B-U+200D, U+2060, U+FEFF, which that helper does not cover today), and
   render as plain text, never markup or links.
3. **Never acted on.** No record opens a URL, runs a command, writes a file, changes config,
   sends input to the PTY, or prompts for credentials. `kind=auth` is a label and must
   **not** turn into a OneTerm password field: a remote program could otherwise print
   "authentication required" in trusted chrome (phishing). Each card names its source tab and
   Space (the spec's "say which terminal").
4. **Reply.** The only bytes sent back are the fixed `ESC ] 7501 ; ? ST`, with the
   terminator the query used. They carry no state, and records cannot be read back. It
   reveals "this terminal speaks 7501", no more than `XTVERSION` already does.
5. **UI churn.** A report storm must not become a render storm. Coalesce to at most one
   `SessionEvent` per parse batch, carrying the table snapshot when it changed.
6. **External effects.** Any notification or sound on a record change (candidate `US-0155`)
   is off by default and goes through the existing `NotificationRateLimiter`.
7. **Elevated instance (`IN-0043`).** Nothing is persisted and no config is written, so the
   read-only elevated instance needs no special case.

## Candidate Work Packets

None created. Ids are proposals, smallest viable first.

- [ ] `US-0152` — **OSC 7501 receiver + Agent Panel cards.** Route 7501 `Forward` + `large`;
  parse and validate per rev 0.3; per-session record table (cap 64, LRU, id subtree `clear`,
  replace-on-report, `app` inheritance); lifetime (OSC 133 `A` and process exit drop
  `working` / `blocked` / `idle`, keep `done` / `error`); answer `7501;?` in byte order; fold
  into `AgentRegistry` with stale detection disabled for 7501 cards; docs (checklist rows,
  `osc-agent-status.md` relationship section, `agent-panel-display.md`). **Acceptance:**
  Claude Code >= 2.1.295 in a local tab and in an SSH tab gives a card going working ->
  blocked (`kind` shown) -> idle / done, with no agent setup. The `?` reply precedes DA1 in
  one batch (unit test) and end to end (Claude Code emits). Malformed, oversized, truncated,
  control-character and bad-id reports are dropped (unit tests from the spec's limits).
  `clear` subtree semantics work. A `working` record disappears at the next OSC 133 `A`. No
  vt public-API diff. No dependencies.
- [ ] `US-0153` — **`RIS` clears program records** (optional; high-risk lane, because it is
  `oneterm-vt` public API). An additive `VtEvent` variant emitted by `RIS` alongside
  `ScreenCleared`, both public-API snapshots regenerated, a CHANGELOG entry, rustdoc with no
  work-item citations or repository paths. The router clears the table on it.
  **Acceptance:** `printf '\033c'` after a `done` report empties that terminal's 7501 cards;
  `ED 2` does not; `vt-public-api.py --check` and `--diff-platforms` pass. Depends on
  `US-0152`. Alternative: record the deviation and skip.
- [ ] `US-0154` — **Tab status glyph.** Unfocused tab headers show a spinner for working, a
  glyph for blocked, and a dot for done / error, from 7501 and 20308 alike (the Rex and
  Ghostty-direction affordance). **Acceptance:** a background tab running Claude Code shows
  the glyph and clears it on focus or prompt. Theme tokens only. Depends on `US-0152`.
- [ ] `US-0155` — **Opt-in notification on blocked / done** while the tab is not visible.
  Off by default, a setting, rate-limited, names the tab and Space, never includes `msg`
  unconfirmed. **Acceptance:** setting off sends nothing; setting on sends one toast per
  transition, at most the limiter's rate. Depends on `US-0152`.

Not proposed: mapping OSC 9;4 onto the root record (OneTerm's progress bar is a separate
surface and is not a record; see Q5); moving 7501 into the engine as a built-in (Q2).

## Architecture and Boundary Questions

- Runtime and owning boundary: parsing and records in `oneterm-terminal` (the policy side of
  the engine seam, beside `osc_agent`); display in `oneterm-state` / `agent-ui` /
  `terminal-view`, as for 20308. The engine is untouched unless `US-0153` is accepted.
- Data ownership and lifecycle: records are per session, in memory, never persisted, and
  dropped with the session.
- Auth, security, privacy, or audit: see the security analysis; `msg` may carry remote paths
  or command text and is not logged above `debug`.
- External systems and side effects: one fixed reply on the PTY / SSH channel; no other effect
  in `US-0152`.
- Public interfaces and compatibility: a new reply OneTerm sends to programs (a client-visible
  contract); a new `SessionEvent` variant (workspace-internal); no `oneterm-vt` API change
  unless `US-0153`.

## Open Decisions and Questions

- [ ] **Q1 (owner, blocking): support at all?** Recommended **yes, receiver only** (`US-0152`);
  see the HLD's Recommendation.
- [ ] **Q2 (owner): engine or adapter?** Recommended: adapter now, with the `Forward` route and
  no vt API change. Revisit a built-in `VtEvent::ProgramStatus` for `oneterm-vt` embedders
  once the spec reaches a stable revision, or when an embedder asks (libghostty-vt chose
  built-in parsing). The spec is at 0.3 and three days old.
- [ ] **Q3 (owner): 20308's future.** Keep both (recommended), deprecate 20308's `state` in
  favour of 7501, or propose 20308's rich types as 7501 extension keys upstream?
- [ ] **Q4 (owner): one source of truth per terminal.** When a terminal has live 20308 cards
  *and* 7501 records, hide the 7501 card (recommended; 20308 § 5 already forbids two sources
  for one agent), or show both?
- [ ] **Q5 (owner): OSC 9;4 interplay.** Leave the progress bar alone (recommended), or hide
  it while a 7501 root record carries `progress`?
- [ ] **Q6 (owner): `RIS`.** Accept `US-0153` (engine variant), or record the deviation?
- [ ] **Q7 (owner): idle records at prompt start.** The spec allows dropping them;
  recommended to drop them, so a finished program's card does not linger as idle.
- [ ] **Q8 (verification, not owner): ConPTY ordering.** Unverified whether conhost forwards
  the program's DA1 or answers it itself before OneTerm's 7501 reply. `US-0152`'s first E2E
  step settles it; if conhost wins the race, Claude Code stays silent on local Windows tabs
  and the packet needs a documented limitation, or a different approach.

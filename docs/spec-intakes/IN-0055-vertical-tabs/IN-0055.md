## Source

Owner request, 2026-10-20 (translated from Vietnamese): "I want a new layout in vertical-tab
form. This layout can be activated by an option in Settings. Design and write the documentation
first."

The coordinator's brief adds the questions this intake must answer: where tabs live today and
what the vertical layout replaces; data ownership; the setting (name, default = today's
horizontal layout, which persisted file, compatibility with older builds); live switch or
restart; interaction with Spaces/splits, the docks and the `IN-0054` right-dock-follows-tab-kind
behaviour, the title bar, zoom, the lock screen, broadcast channels, the OSC 7501 status icon
(`US-0193`), tab drag/reorder and drag-into-Space, context menus, keyboard tab navigation,
overflow with many tabs, width (resizable, persisted, collapsible), themes/contrast, and
accessibility.

**No packet file is created and no code is written until the owner rules on the open questions
below.** The design is in [`high-level-design.md`](high-level-design.md).

### Facts this intake rests on (read 2026-10-20 against main @6a5c2c82)

- **Where the tabs are drawn.** The centre of the `DockArea` is `v_split` > `tabs` holding one
  `TerminalPanel` per Terminal Tab (`crates/workspace/src/layout/workspace/layout.rs:40`,
  `docs/gui-layout.md` § Dock composition). The workspace forces the kit's tab bar even for one
  tab (`dock_skin.set_panel_style(PanelStyle::TabBar)`, `layout/workspace/mod.rs:192`). The strip
  is drawn by the kit's `TabGroupSkin::render_tabs`
  (`reference/gpui-kit/crates/component/src/dock/tab_panel.rs:433-687`): one kit `Tab` per panel
  whose child is the panel's own `title()` element, a trailing group with the active panel's
  `title_suffix` (OneTerm's `+` menu), the zoom button and the `...` menu (`:275-357`), and the
  right-dock toggle on the top-right group (`:211-271`).
- **OneTerm already owns the seam.** `OneTermTabGroupSkin` wraps the kit renderer and overrides
  `render_tab_bar` (it returns nothing for the SSH Client group, `dock_skin.rs:105-141`). The
  base trait lets a skin draw its own tab bar: `TabGroupContext` hands it the panels, the active
  index and callbacks for select, close, zoom, drag payload and drop
  (`reference/gpui-kit/crates/base/src/dock/tab_group.rs:768-893`), and the presentation half is
  reachable through the public `PanelHandle::of` (`.../component/src/dock/panel.rs:233-235`).
- **The kit cannot draw a vertical strip, and base fixes the order.** The component `TabBar` /
  `Tab` have no vertical mode (`.../component/src/tab/`, no axis option). Base lays every group
  out as a **column**, tab bar first and content below, applied after the skin's frame
  (`tab_group.rs:691-709`), so a skin cannot turn the group into a row. The design therefore
  places OneTerm's own rail absolutely inside the group frame and offsets the content region
  (HLD § Rendering seam). The base `Tabs` / `Tab` elements are unstyled and carry the
  `TabList` / `Tab` roles, `aria_selected` and position-in-set (`.../base/src/tabs.rs:149-234`);
  the rail is built from them.
- **The tab row is OneTerm's code.** `render_tab_strip` (`crates/terminal-view/src/panel/tab_title.rs:207-345`)
  draws the channel chips, the recording dot, the OSC 7501 status icon, the label (double-click
  renames), the `×`, middle-click close, the right-click menu, and the drag source for
  drag-into-Space (`DragTerminalTab`, `:271-281`). It is sized for a horizontal strip: 100-220 px
  wide (`:253-254`), an active bar along its **top** edge (`:257-267`) and a -5 px right margin
  (`:268`).
- **Two drags start from a tab today.** The whole title row (chips, recording dot, status icon,
  label; not the `×`, which stops left mouse-down, `tab_title.rs:330-332`) starts a
  `DragTerminalTab` and stops propagation (`tab_title.rs:271-281`); its only drop target is an
  empty Space (`crates/terminal-view/src/space/render.rs:283-287`). The kit `Tab`'s own
  `DragPanel` (reorder and dock moves, `tab_panel.rs:580-593`) starts only from the tab's padding
  outside the title row (12 px, kit `tab/tab.rs:72-89`). Confirmed against gpui's dispatch order
  by the advisor review ([`evidence/IN-0055-spec-review.md`](evidence/IN-0055-spec-review.md)).
- **No keyboard tab navigation exists.** There is no next/previous/select-tab action
  (`crates/actions/src/lib.rs`, Settings > Key Bindings); kit tabs are not tab stops.
- **Settings pattern to copy.** `show_fps` is an optional `ui_config.json` field omitted while
  `false`, written only by `UiConfig::set_show_fps`, which persists and refreshes every window
  (`crates/settings/src/ui_config.rs:58-61`, `:326-333`), and shown as a switch in Settings >
  General > Interface (`crates/settings-ui/src/general.rs:53-65`).
- **`ui_config.json` compatibility.** Unknown fields are ignored on load and dropped on the next
  write; a field of the wrong type fails the whole document, which is then quarantined, unless the
  field parses leniently as `lock_after_idle_minutes` does (`ui_config.rs:89-100`,
  `crates/core/src/schema.rs:86-105`, test `a_config_from_the_agent_panel_era_loads_and_heals`).
- **Contrast.** The kit strip draws an inactive label in `tab.foreground` on `tab_bar.background`,
  a hovered one in `tab.active.foreground` on the same fill, and the selected tab on
  `tab.active.background` (`.../component/src/tab/tab.rs:128-140`, `:172-184`, `:221-225`).
  `scripts/check-theme-contrast.py` measures `tab.active.foreground` only on
  `tab.active.background`, so the hover pair is not measured today.

## Requested Outcome

A user turns on **Vertical Tabs** in Settings and, without restarting, every Terminal Tab moves
from the strip above the terminal into a list on the left of the terminal area; turning it off
brings the strip back. Everything a tab does today (select, close, rename, menu, status icon,
channel chips, recording dot, drag into a Space, reorder, the `+` menu, zoom) works the same in
both layouts, and the choice survives a restart. The default stays the horizontal strip.

## Prior Art (from knowledge, not re-checked on the web)

- **Microsoft Edge**: vertical tabs on the left, switched from the tab menu or Settings; the pane
  collapses to icons and is resizable.
- **Tabby**: Settings > Appearance offers the tab bar on any side (top, bottom, left, right).
- **VS Code**: no vertical editor tabs; the "Open Editors" view is a vertical list beside the
  editor, and tabs can wrap.
- **WezTerm**: the tab bar can move to the bottom; no vertical bar.
- **Warp**: tabs along the top; no vertical layout is relied on here.

What OneTerm takes from them: left side, a setting that applies live, collapse-to-icons and a
resizable width as later steps.

## Lane

field in a document OneTerm already writes. No secret, no authentication, no migration, no
schema bump, no external effect, no public contract (`docks.json`, panel names, `oneterm-vt` API)

remains empirical is how base lays out an absolutely placed rail beside an offset content region
and the one terminal resize that follows, so the first step of `US-0196` is a short spike; see
Q8.

## Persistence and Safety Analysis

1. **One additive field.** `ui_config.json` gains `vertical_tabs`, an object omitted while it
   equals the default (`{"enabled": false}`); `US-0197` adds `width`, `US-0198` adds `collapsed`.
   `schema_version` stays 1.
2. **Lenient parse.** A hand-edited value of the wrong shape loads as the default with a warning
   and never quarantines the document (a bad value must not cost the user their key bindings).
   Out-of-range numbers are clamped on read without rewriting the file.
3. **Older builds.** v0.6.10 and earlier ignore the field on load and drop it on their next write
   of `ui_config.json` (a theme change, a key binding). Running an older build after a newer one
   can therefore turn vertical tabs off; nothing else is lost. This is the documented behaviour of
   every additive `ui_config.json` field (`right_dock_mode`, `IN-0054`).
4. **Elevated window.** Reads the field and shows the chosen layout; a change made in its
   Settings window applies in memory only and is refused on write by `UiConfig::write_refusal`
   (`DEC-0019` M4), exactly like Show FPS Monitor.
5. **No data at risk.** Switching layout rebuilds no panel and ends no session: the same
   `TerminalPanel` entities are drawn in a different chrome. The terminal area changes width, so
   each visible terminal is resized once, as when the right dock opens.
6. **Writes off the UI thread** through `UiConfig::persist` (`docs/agents/persistence.md`);
   `US-0197` writes the width once at the end of a drag, never per frame.

## Architecture and Boundary Questions

- Runtime and owning boundary: the rail is drawn by `oneterm-workspace`'s tab-group renderer;
  the row content stays the panel's `title()` in `oneterm-terminal-view`. The shell still names
  no feature type (R4): it reaches the row only through `PanelHandle`.
- Data ownership and lifecycle: `UiConfig.vertical_tabs` (owner `oneterm-settings`) is the only
  new state; written by `UiConfig::set_vertical_tabs_*` setters only (Settings switch; `US-0197`
  drag end; `US-0198` collapse button). Per-group scroll position lives in the renderer object,
  in memory, as the kit's strip keeps it.
- Auth, security, privacy, or audit: none.
- External systems and side effects: none beyond `ui_config.json`.
- Public interfaces and compatibility: `ui_config.json` gains an optional field (see Persistence
  and Safety Analysis). No `docks.json`, panel-name or `oneterm-vt` change.

## Open Decisions and Questions

**Resolved 2026-10-20.** Owner ruling ("as proposed", given in Vietnamese): every question Q1-Q9 is accepted as
recommended. Left rail only; one **Vertical Tabs** switch in Settings > General > Interface, default off,
live; `US-0196` at a fixed 220 px (`US-0197` resize and `US-0198` collapse stay proposed packets);
rail header holds `+` and zoom only (no `...` menu, no dock toggle); "Close Tabs Below" while vertical;
one rail per all-terminal centre group; a 12 px leading grip (`AppIcon::GripVertical`, open-hand cursor)
for reorder. Q8 is not an owner question: it is the first step of `US-0196`. The list below keeps each
question with its recommendation, which is now the ruling.

- [x] **Q1 (owner): which side?** Recommended **left only**. The right dock already owns the
  right edge; a rail there would sit between the terminal and the SSH Client panel. Alternative:
  a Left / Right choice (Tabby's model), one more setting and a mirrored layout to test.
- [x] **Q2 (owner): the control and its entry points.** Recommended a **Vertical Tabs** switch in
  Settings > General > Interface beside Show FPS Monitor, default off, and nothing else in
  `US-0196`. Alternatives: a "Tab Layout: Horizontal / Vertical" dropdown (fits Q1's
  alternative); also an app-menu checked item and an unbound "Toggle Vertical Tabs" action, as
  Show FPS Monitor has (about 20 lines; listed as a follow-up).
- [x] **Q3 (owner): width.** Recommended a fixed 220 px in `US-0196` (the strip's tab ceiling, so
  a label fits exactly as much as today), then `US-0197`: drag to resize between 140 px and
  400 px, persisted, and at most 35 % of **its own tab group's** width (the right dock's share),
  so a split centre (Q7) or an open right dock narrows each rail instead of starving the
  terminals. Alternatives: bound by the window (simpler, but two rails in a split centre can
  leave the two terminals 150 px between them at 1000 px), or stop at the fixed width (then
  `US-0196`'s 220 px per rail is the permanent limit).
- [x] **Q4 (owner): collapse to icons, and what a collapsed row shows.** Recommended **yes, as
  `US-0198`, after `US-0196` / `US-0197`**, rows showing the tab's **position number** (1, 2, 3 ...)
  with the status icon as a badge and the label in a tooltip. Numbers never collide; terminal
  tabs have no icon of their own, and two-letter monograms collide ("PowerShell", "PowerShell").
  Alternatives: a monogram of the label; drop `US-0198`.
- [x] **Q5 (owner): the rail header.** Recommended `+` (the existing New Terminal menu) and the
  zoom button only. The strip's `...` menu is dropped in vertical mode: its tab list duplicates
  the rail, and its other row is the zoom the button already offers. The right-dock toggle stays
  in the status bar and on `Ctrl+Shift+B`, not in the rail (the rail is on the far side from the
  dock). Alternative: keep `...` for parity.
- [x] **Q6 (owner): menu wording.** Recommended the tab menu's "Close to the Right" reads
  **"Close Tabs Below"** while the layout is vertical (same command, same tabs). Alternative:
  one wording, "Close Tabs After", in both layouts.
- [x] **Q7 (owner): a split centre.** Dragging a tab to the edge of the terminal area can split
  the centre into two tab groups (kit default; OneTerm does not lock it). Recommended: **each
  group draws its own rail**, exactly as each draws its own strip today, each rail bounded by its
  own group's width from `US-0197` (Q3). Until `US-0197` each rail is a fixed 220 px, so a split
  centre spends 440 px on rails. Alternative: one rail listing every group's tabs, which needs a
  design for showing groups and is not proposed.
- [ ] **Q8 (verification, not owner):** the `US-0196` spike proves, in a gpui test and on screen,
  that a rail placed absolutely as the frame's first child, with the content frame offset by a
  left **margin** of the rail's width, lays out correctly inside base's forced column, and that
  switching layout resizes each visible terminal once instead of overlapping it. Drop measurement
  against the content frame is already proven by base's own test
  `the_content_frame_is_what_a_drag_is_measured_against` (`tab_group.rs:1764-1784`); the drag
  order and the contrast pair are `US-0196` acceptance tests, not gates. If the spike fails, the
  fallback is HLD § Rendering seam option B2 with its drop caveats.
- [x] **Q9 (owner): the reorder handle.** In the rail almost the whole row is the title row,
  whose drag moves a tab into an empty Space; dropping it on another row does nothing (the shell
  cannot accept that drag type, R4). Recommended: keep reorder on the row's leading edge, as on
  the strip, but make it visible: a 12 px edge (the strip's padding) showing a grip glyph and an
  open-hand cursor while the row is hovered. Alternative: reorder by dragging the label itself
  (the listed follow-up), which needs `oneterm-terminal-view` to accept its own `DragTerminalTab`
  on a row and move the panel, in both layouts.

## What the User Sees (scenario walkthrough)

1. Settings > General > Interface: a new switch, **Vertical Tabs**, off. The user turns it on.
2. The main window changes on the next frame: the strip above the terminal is gone and the
   terminal starts right under the title bar; a 220 px list now runs down the left of the terminal
   area. Its first row holds `+` and the zoom button; below it one row per tab: `PowerShell`
   (selected: lighter fill, accent bar on its left edge), `web-01` (an SSH tab) with a spinning
   working icon,
   `cmd` with a red recording dot and an `A` channel chip. The terminal reflows a few columns
   narrower, as when the right dock opens.
3. Clicking `web-01` shows it; the SSH Client dock opens on the right because it is an SSH tab
   (`IN-0054`, unchanged). Right-click a row: Rename..., Duplicate, Close, Close Others,
   Close Tabs Below. Middle-click closes it (a rail row has no `×`: the OSC 7501 status icon sits at the right end of its second line, which also shows the current directory, owner rework 2026-10-21; the strip keeps its `×`).
4. With 40 tabs the list scrolls under the wheel; a tab opened from `+` scrolls into view as it
   becomes the active one.
5. Dragging a row (anywhere but its grip) onto an empty Space moves that tab into the
   Space, as from the strip. Hovering a row shows a grip on its left edge; dragging the grip onto
   another row reorders the tab. Dropping a row's label on another row does nothing (Q9).
6. The zoom button fills the window with the terminal panel; the rail stays (it is the panel's
   chrome, as the strip is today) and the button now restores.
7. After the idle timeout the lock screen covers everything; after unlocking, the rail is back as
   it was.
8. On restart the vertical layout is still on. Turning the switch off brings the strip back with
   the same tabs, still running.

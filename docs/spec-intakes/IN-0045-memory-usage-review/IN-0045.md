# Spec Intake: Memory usage review

ID: IN-0045
Date: 2026-09-25
Type: change_request (maintenance)
Lane: normal

Document number: 45.

## Source

Owner report, 2026-09-25: "after many updates, memory usage has reached 350 MB; before it
was around 200 MB." The owner runs the release build from `dist/`. The ask is a full review
aimed at reducing memory. This intake records only measurement and attribution. It changes
no code and opens no packets.

## Requested Outcome

- Know which number the owner read.
- Know which release the growth came from, and what it is made of.
- Have a memory budget that future work is held to, and a ranked list of reductions with
  expected savings.

Evidence: [`research/memory-attribution.md`](research/memory-attribution.md). Protocol:
[`research/measure.ps1`](research/measure.ps1). Raw data:
[`research/measurements.csv`](research/measurements.csv).

Findings in one paragraph:

- **What the owner read.** The status bar `MEM` value is commit charge (`PrivateUsage`),
  not Task Manager's private working set. On main with one idle tab it reads 182 MB while
  Task Manager shows 49 MB.
- **No leak, no drift.** Closing tabs returns memory, and two idle minutes add 0.1 MB.
- **The one regression.** It came in the v0.4.2 → v0.5.0 window: the terminal view's
  glyph cache preallocates a 4096-entry hash table of 3 KB buckets. That is 23.6 MiB
  committed per tab and per split pane. It becomes resident once output fills it.
- **The ballast.** 64 MiB of commit is the OOM ballast (v0.4.1). It is never resident.
- **Stable since v0.6.0.** Every release since v0.6.0 is flat within 0.5 MB. v0.6.0
  itself lowered memory under output by 14 MB.
- **What likely adds up to 350.** Several tabs at 26.6 MB of commit each, plus 7.5 MB per
  full 10,000-line history, plausibly reaches 350 MB. This is an estimate until the owner
  confirms.

Phase 2 (2026-09-25), after the owner confirmed two tabs running `claude` and a 10,000-line
limit. Evidence: [`research/agent-load-phase-2.md`](research/agent-load-phase-2.md) and
[`research/history-storage-assessment.md`](research/history-storage-assessment.md). Load:
[`research/tui-mimic.py`](research/tui-mimic.py), `measure.ps1 -Mode S6`.

- **Two tabs under a claude-like load.** Status bar `MEM` (commit):
  - 237.8 MB at the default 10,000 lines, 1280x800;
  - 275.7 MB at 1920x1040;
  - 298.1 MB at 50,000 lines;
  - 360.6 MB at 100,000 lines.

  346 MB matches about 88,000 lines at 1280x800. At 10,000 lines the rest of the gap is
  unexplained. Likely causes: the window size or DPI, split panes, and session length.
- **The glyph table does not double under this load.** The largest entry count was 1,435
  of 7,168, with no growth in 20 views. It stays 23.6 MB committed, 7 to 8 MB resident
  when busy.
- **OOM ballast.** `DEC-0020` proposes 16 MiB after `BUG-0078` (32 MiB if it slips).
  - The largest routine allocation after `BUG-0078` is 6.3 MB: the ring at 100,000 lines.
  - The heaviest net commit growth over 3 s is 10.2 to 15.9 MB.
- **History storage.**
  - `US-0138` saves 3.2 MB per busy tab at the default: fix later, with a trigger.
  - `US-0139` saves 0.75 MB per tab only until history fills: do not fix.

## Project Impact

- **Surfaces.** Status bar resource widget (`crates/workspace/src/widgets/resource.rs`), the
  terminal view's render state (`crates/terminal-view/src/render/glyphs.rs`), the VT
  engine's history storage (`crates/vt/src/grid/`), the OOM allocator
  (`crates/app/src/oom.rs`).
- **Contracts.**
  - `oneterm-vt` is an external contract (`docs/PROJECT.md`). A change to history storage
    must keep its public API and reply bytes.
  - The OOM ballast behaviour is documented in `crates/app/src/oom.rs` only.
- **Users.** Anyone with many tabs or split panes (commit and, after output, resident
  memory), and anyone who reads the status bar.

## Candidate Work Packets

Not created. Proposed, in order of value for effort:

- [x] [`BUG-0078`](BUG-0078-glyph-cache-preallocates-its-table.md) — **Glyph cache does not preallocate its table.** The per-view
  `GlyphCache` starts empty and stores the shaped line behind an `Arc` (or equivalent), so
  a bucket is tens of bytes, not 3,024.
  - Expected: −23 MB commit per tab and per pane at idle; about −20 MB private WS per busy
    tab (estimate).
  - Effort S, risk low. Proof: `measure.ps1` S1/S2/S3 plus the existing render bench.
  - No dependencies.
- [x] [`US-0137`](US-0137-status-bar-private-working-set.md) — **The status bar shows the
  memory figure Task Manager shows** (private working set). Owner ruling 2026-09-25: the
  private working set, no label change.
  - Expected: the displayed number drops by 130+ MB. Real usage does not change.
  - Effort S, risk low. Needs the owner's wording choice.
- [ ] `US-0138` — **History rows are stored trimmed to their occupied cells** in
  `oneterm-vt`. **Deferred: fix later, with a trigger** (phase 2,
  [`research/history-storage-assessment.md`](research/history-storage-assessment.md)).
  - Measured per row: ring share + 8 B × columns. That is 791 B at 89 columns and 10,000
    lines.
  - Expected saving:
    - 40 % for the S6 mimic (55 % of cells used, an estimate): −3.2 MB per full tab at
      10,000 lines, −32 MB at 100,000;
    - 79 % for S3-style short lines;
    - 0 for wrapped prose.
  - Cost:
    - `RowRef::cells` / `Row::cells` change meaning (a minor bump; `vt-public-api.py`
      cannot see it);
    - one scan and one shrinking `realloc` per scrolled line (estimate: 3 to 8 % of
      `scrolling` throughput);
    - a second width invariant in the `vt-paranoid` walk.
  - Trigger: the default limit rises above 10,000, a large-limit user reports memory, or an
    embedder asks. Then write `low-level-design/history-storage.md` first.
- [ ] `US-0139` — **The history ring grows with the history** instead of being
  preallocated to the limit. **Do not fix** (phase 2 assessment).
  - Measured: the ring is 786,432 B at 10,000 lines, 3,145,728 B at 50,000 and
    6,291,456 B at 100,000.
  - It saves that amount only until a tab's history first fills. In S6 that took seconds,
    so the saving there was 0.
  - Cost: restating R-30 (the ring length is a session constant), and `ring_len()` /
    `ring_mask()` changing mid-session.
  - Reopen if the default limit reaches 100,000 or more.
- [ ] `US-0140` — **Sixel images have a per-terminal byte budget.**
  - Expected: bounds a worst case of 64 MiB per image × 256 placements. Nothing measured
    on typical use.
  - Effort S-M, risk medium.
- [ ] `DEC-0020` (decision, not a packet) — **OOM ballast size and form.** Drafted as
  proposed: [`DEC-0020`](../../decisions/DEC-0020-oom-ballast-size.md).
  - Recommended: 16 MiB, with or after `BUG-0078`; 32 MiB if `BUG-0078` slips.
  - Expected: −48 MB commit and status bar `MEM`, 0 private WS.
  - Reserve-only gives no headroom and is rejected.

## Architecture and Boundary Questions

- **Runtime and owning boundary.**
  - The glyph cache is terminal-view render state, one per `TerminalView`.
  - History storage is `oneterm-vt`.
  - The displayed figure is the workspace status bar.
  - The ballast is the app binary.
- **Data ownership and lifecycle.**
  - Per-tab memory is freed when the tab closes (measured, S4).
  - Nothing grows with time at idle (measured, S5).
- **Auth, security, privacy, or audit.** None.
- **External systems and side effects.** None. Children (OpenConsole, cmd) are separate
  processes and cost 3.5 MB private WS per tab. They are out of scope.
- **Public interfaces and compatibility.** `US-0138` and `US-0139` leave
  `public-api.*.txt` unchanged. `US-0138` still changes what `RowRef::cells` returns for a
  history row, which is a semantic change to the public API (phase 2 assessment § 4.1).
